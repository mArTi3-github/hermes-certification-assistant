# Долгоживущие скиллы: защита от куратора без пинов

Задача-класс: «скиллы такой-то папки/категории не должны архивироваться и консолидироваться».

## Главное

Защиты «по папке» или «по категории» в Hermes нет: в конфиге (`curator.*`) нет ни исключений, ни
glob-списков. Зато всё, что куратор вообще видит, приходит из `tools/skill_usage.py::curated_report()`,
а она собирает **agent-created скиллы плюс запиненные**. Поэтому защита — это состояние записи
скилла в `skills/.usage.json`:

| Как скилл попал в профиль | `created_by` | Куратор его видит |
|---|---|---|
| копирование из репозитория (`sync.sh`, `hermes profile update`) | нет маркера | нет |
| передний `skill_manage(create)` в сессии, `/learn` | `learn` | нет |
| установка из Skills Hub | `installed` | нет |
| создание фоновой ревизией сессии | `agent` | **да** |
| `hermes curator adopt <имя>` / `adopt --all-unmanaged` | `agent` | **да** |

Неуправляемый скилл не «пропускается» свипом — он в него не попадает: сроки `stale_after_days`
(14) и `archive_after_days` (30), `hermes curator prune` и LLM-консолидация к нему не применяются.
Обратной команды `unadopt` в CLI нет: управляемость снимается только правкой `.usage.json` вручную.

## Что от чего защищает

| Угроза | Кто исполняет | Что защищает |
|---|---|---|
| Старение и архив по неактивности | `apply_automatic_transitions` | отсутствие маркера `created_by: agent`; для управляемого — `pinned` |
| Массовый архив по простою | `hermes curator prune` | то же |
| Слияние в умбреллу | LLM-проход куратора | то же |
| Переписывание содержимого | фоновая ревизия сессии | только `lock`; ни пин, ни отсутствие маркера не помогают |
| Физическое удаление | `hermes curator purge` | наступает только вручную: «explicit only — never automatic», по умолчанию выключен (`curator.archive_ttl_days` = 0), требует подтверждения и пишет блобы в журнал |

## pin и lock — рычаги для управляемых скиллов

| | `hermes curator pin <name>` | `hermes curator lock <name>` |
|---|---|---|
| Авто-переходы куратора (stale/archive) | снимает | снимает |
| Правки содержимого агентом (`skill_manage`, `write_file`, `patch`, terminal) | **разрешены** | запрещены (только пользователь) |
| Кому подходит | скилл, который завела фоновая ревизия | замороженный скилл, окно публикации |

**Неуправляемый скилл пинить не надо.** Пин вносит его в `curated_report()`, то есть в список
кандидатов LLM-прохода, где защита держится на инструкции модели «pinned=yes — не трогать». Без
пина скилла в этом списке нет вовсе. Ответ `pin` «recorded; this skill is unmanaged —
auto-transitions never consider it» говорит именно об этом: запись создана, защищать нечего.

Скиллы, на которые ссылается cron-задача (`cron=yes`), защищены автоматически — куратор считает их
используемыми.

## Практика профиля

- `hermes curator adopt` для скиллов профиля не запускается — ни по одному, ни списком. Подсказку
  «adopt one with … / adopt --all-unmanaged» в конце вывода `list-unmanaged` игнорировать.
- Проверка состояния: `hermes curator list-unmanaged` (все авторские скиллы) и
  `hermes curator status` (`no curator-managed skills`). Пинов быть не должно.
- Правило живёт в `SOUL.md` профиля: он подставляется в каждую сессию, входит в
  `distribution_owned`, куратор его не трогает. В скилл такое правило не пишут — скилл-носитель
  можно переписать.

## Если скилл всё же стал управляемым

- Публикация не помогает: `sync.sh` копирует каталоги скиллов и `.usage.json` не трогает, поэтому
  у автора маркер остаётся, а у коллег скилл приезжает неуправляемым.
- Быстрое лечение — `hermes curator pin <имя>`: скилл перестанет стареть и останется видимым в
  отчётах куратора, что для управляемого скилла нормально.
- Снять управляемость — только правкой поля `created_by` в `.usage.json` вручную при остановленном
  Hermes; команды для этого нет.

## Проверка, что скилл не состарится

```bash
hermes curator list-unmanaged                    # скилл в списке → авто-переходы его не видят
hermes curator status                            # no curator-managed skills
scripts/verify_skill_pins.py --days 400 <скилл>  # только для управляемого: держит ли пин
```

`verify_skill_pins.py` симулирует свип с датой в будущем и подменённым отчётом, поэтому трогает
только перечисленные записи. Для неуправляемого скилла проверка избыточна: свип его и так не
видит. `hermes curator prune --dry-run` доказательством не служит — когда управляемых скиллов нет,
он пуст независимо от состояния записей.
