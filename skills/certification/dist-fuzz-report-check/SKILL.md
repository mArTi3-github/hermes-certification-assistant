# Проверка материалов фаззинг-тестирования (DIST.FUZZ)

Класс задач: разработчик передал архив с результатами фаззинг-тестирования
компонента продукта, а испытательной лаборатории нужно проверить его на
соответствие формальным требованиям «Методики выявления уязвимостей и
недекларированных возможностей» (Методика ВУ) и выдать заключение по каждому
пункту требований.

Скилл не делает фаззинг, а только проверяет переданные материалы: что реально
лежит в отчете, чего в нём нет, и какие пункты требований из-за этого не
выполнены.

Главный принцип: **все числа считать из первичных артефактов** (`fuzzer_stats`,
`plot_data`, журналы фаззеров, HTML-отчёты покрытия, файлы `crashes/`/`hangs/`),
а не переписывать из сопроводительного файла `Readme`. **Readme разработчика — заявление стороны, а не доказательство.**

Текст требований встроен в скилл — `references/dist-fuzz-requirements.md`
(7 пунктов + дополнительные требования п. 7). При типовой проверке файл
требований запрашивать не нужно; если заказчик передал свою редакцию — сверить
нумерацию и цитировать по ней.

## When to Use

- Пришёл архив (или каталог) с результатами фаззинг-тестирования компонента —
  нужно заключение «соответствует / не соответствует» по пунктам Методики ВУ.
- Надо понять, чего в материалах не хватает, и сформулировать запрос разработчику.
- Надо пересчитать критерии завершения фаззинга (пп. 5, 6) по `fuzzer_stats`
  или восстановить их по журналам, если статистики нет.
- Надо разобрать `crashes/`/`hangs/` и понять, есть ли необъяснённые находки.
- Не для: собственно проведения фаззинг-тестирования, написания отчёта по
  приказу № 76.

## Prerequisites

- Текст требований отдельно не нужен: он встроен в скилл
  (`references/dist-fuzz-requirements.md`).
- `python3` (stdlib достаточно; для HTML-версии отчёта нужен модуль `markdown`).
- `unzip`/`zipinfo` для точечной распаковки; `sha256sum` для фиксации хеша материалов.
- Свободное место: материалы легко занимают 20+ ГиБ в распакованном виде —
  **распаковывать выборочно** (см. шаг 3), не «unzip всего».
- Рабочие материалы (распаковка, выборки, промежуточные файлы) — **только в рабочем
  каталоге под `$TMPDIR`**, созданном `scripts/fuzz_workspace.py create` (у этого
  инструмента своя база по умолчанию — `$TMPDIR/fuzzcheck`); не рядом с архивом
  (сетевая шара) и не в `output/`. В `output/` попадают только отчёт и приложения, он
  лежит рядом с переданными материалами. Если материалов файлами не передавали (на
  входе только текст запроса), отчёт идёт в `~/work/<продукт>-fuzz-<ГГГГ-ММ>/`, а рабочий
  каталог — по-прежнему в `$TMPDIR`.
- Архив часто лежит на сетевой шаре (vmhgfs/NFS): чтение медленнее, `unzip -t`
  на 2,6 ГБ идёт минуты — запускать в фоне.

## Quick Reference

```bash
# рабочий каталог проверки: проверка свободного места + маркер для безопасной уборки
scripts/fuzz_workspace.py create --need-gib 23 --label sflow-28.1 --archive sflow-28.1-cert.zip
scripts/fuzz_workspace.py list --older-than 1
scripts/fuzz_workspace.py purge --older-than 1 --dry-run

# инвентаризация архива без распаковки (central directory)
scripts/fuzz_artifact_inventory.py <archive.zip> --top 12

# метрики одной цели + расчёт пп. 5, 6 (seeds — из журнала или вручную)
scripts/afl_stats_report.py <misc_dir> --engine-log <engine.log> --json stats.json
scripts/afl_stats_report.py <misc_dir> --seeds 1

# восстановление динамики покрытия по журналу, когда fuzzer_stats нет
scripts/afl_log_timeline.py <engine.log> --min-plateau 2

# профиль корпуса: версии формата, num_samples, распределение размеров
scripts/corpus_profile.py <corpus_dir> --sflow

# Markdown-отчёт -> автономный HTML (оглавление, подсветка вердиктов, печать)
# --kicker/--footer обязательны: в шаблоне скрипта зашиты строки прошлой проверки
scripts/md_report_to_html.py report.md --kicker "Проверка … · Методика ВУ" \
  --footer "<под текущий комплект: архив, числа получены разбором первичных артефактов>"
```

## Procedure

1. **Взять требования и разложить на проверяемые утверждения.**
   Текст уже в скилле — `references/dist-fuzz-requirements.md`; запрашивать файл
   у пользователя не нужно. Каждый пункт превратить в вопрос, на который можно
   ответить «да/нет» по артефактам; подробный разбор —
   `references/vy-metodika-checklist.md`. Если пользователь передал свою редакцию
   требований — сверить нумерацию, при расхождении цитировать по ней.
   *Готово, когда* у каждого пункта есть: что искать, где искать, чем доказать.

2. **Инвентаризация архива без распаковки.**
   `scripts/fuzz_artifact_inventory.py <zip>` даёт объём, группы, крупнейшие
   файлы, наличие описательных документов, `fuzzer_stats`/`corpus`/`crashes`/
   `hangs`/`coverage` по каждой цели, вложенные архивы.
   *Готово, когда* известно: сколько целей, есть ли вообще описательная часть,
   у какой цели нет `fuzzer_stats`, и где лежат журналы.

3. **Создать рабочий каталог и распаковать только нужное.**
   ```bash
   WORK=$(scripts/fuzz_workspace.py create --need-gib <объём из шага 2> \
            --label <компонент>-<версия> --archive <имя.zip> --quiet)
   unzip -o -q <zip> "results/Readme" "results/input/*" \
     "results/*/results/misc/*/*" -d "$WORK/ext"
   ```
   Объём для `--need-gib` брать из инвентаризации (шаг 2). Если он с запасом 15 %
   не влезает в свободное место, распаковывать **по группам**: сначала метаданные
   и `misc/`, затем по одной цели, удаляя группу сразу после разбора
   (`rm -rf "$WORK/ext/<группа>"`). Журналы на гигабайты — по одному и удалять
   после разбора; вложенные `results-*.zip` вскрывать по мере необходимости
   (в них `corpus/`, `crashes/`, `hangs/`, иногда дубли журналов).
   *Готово, когда* в рабочем каталоге лежат только метаданные (`fuzzer_stats`,
   `plot_data`, `fuzzer_setup`, `cmdline`), отчёты покрытия и выборки образцов, а
   `fuzz_workspace.py list` показывает один каталог — этой проверки.

4. **Определить фаззер, цели и число стартовых образцов.**
   `fuzzer_stats` → `afl_version`, `command_line`, `target_mode`; `fuzzer_setup`
   → все `AFL_*` переменные и роли `-M`/`-S`; журнал → `Loaded a total of N seeds`.
   Число стартовых образцов — ключевая величина: от неё зависят оценки по пп. 2 и 5.
   *Готово, когда* для каждой цели выписано: фаззер и версия, число инстансов,
   power schedules, число seeds, таймаут `-t`, лимит памяти `-m`.
   Если фаззер не AFL (Jazzer.js/libFuzzer для JS/TS и т. п.), `fuzzer_stats` и
   `plot_data` в комплекте нет: цели, seeds и словари берутся из документации и дерева
   `corpus/`, а метрики — из журнала фаззера. Карта артефактов и разбор строк прогресса —
   `references/jazzer-libfuzzer-artifacts.md`; скрипты `afl_stats_report.py` и
   `afl_log_timeline.py` к таким материалам не применять.

5. **Собрать метрики и пересчитать критерии (пп. 5, 6).**
   `scripts/afl_stats_report.py` печатает таблицу по инстансам и сам считает:
   `5«а»` (пути против seeds), `5«б»` (финальное покрытие против первой точки
   `plot_data`), `6` (`time_wo_finds`). Если `fuzzer_stats` нет —
   `scripts/afl_log_timeline.py` восстанавливает плато по журналу.
   У libFuzzer-целей плато и кратность считаются из строк `#<runs> NEW cov: … ft: …
   exec/s: …`: `t = runs/exec_s`, `плато = (фактическая длительность − t)/3600`.
   Считать **обе** метрики (`cov` — рёбра, `ft` — признаки покрытия) и приводить обе:
   вердикты по ним расходятся.
   *Готово, когда* по каждой цели есть числа и явно указано, выполняется критерий
   или нет, и **по какому подпункту** принято решение.

6. **Разобрать находки: `crashes/` и `hangs/`.**
   Подсчитать файлы, распределение размеров, при известном формате — разобрать
   заголовки (`scripts/corpus_profile.py --sflow`) и поискать заведомо
   «дорогие» поля (например, `num_samples` в миллиардах). Сравнить таймаут `-t`
   с медианным `exec_us` из журнала: если `-t` в сотни раз больше, превышение
   таймаута — не артефакт строгой настройки.
   *Готово, когда* по каждой находке сказано: сколько, какие, есть ли в материалах
   анализ и подтверждение воспроизведения (обычно — нет).

7. **Проверить структурное покрытие (п. 7).**
   Разобрать HTML gcovr по каждой цели и суммарный: строки/функции/ветви,
   список файлов, дата генерации. Отдельно отметить файлы с нулевым покрытием и
   расхождение «карта AFL 5–8 %» против «строки 80–90 %».
   *Готово, когда* есть таблица «файл × цель × суммарно» и вывод о применимости
   льготы «90 % строк / 80 % базовых блоков» **по каждой цели**, а не по сумме.

8. **Проверить датчики (п. 1) и параметры сборки.**
   Искать в материалах явную фиксацию: перечень санитайзеров, флаги, компилятор,
   скрипт сборки, хеш бинаря. Переменные `ASAN_OPTIONS`/`MSAN_OPTIONS` в
   окружении фаззера — только косвенный признак, доказательством не являются.
   *Готово, когда* вывод сформулирован как «зафиксировано / не зафиксировано»,
   без догадок о том, что «наверное, собирали с ASan».

9. **Собрать отчёт.** Структура — пять разделов по `templates/review-report.md`:
   итог → таблица «требование | результат | обоснование» → замечания («что не так /
   чем подтверждено / что исправить») → что запросить → технические доказательства
   только по спорным выводам. Стиль и границы — раздел «Формат заключения».
   HTML-версия — `scripts/md_report_to_html.py` с `--kicker` и `--footer`.
   *Готово, когда* каждый пункт требований имеет вердикт из фиксированного словаря
   и обоснование с конкретным артефактом в архиве.
   Если просят **обновлённую (сокращённую) версию уже сданного заключения** — новый
   файл кладётся рядом со старым (`-v2` в имени), старый не правится и не удаляется;
   числа считаются заново из артефактов, а не переносятся из старого текста. Если
   способ счёта даёт другое значение (например, плато по `runs/exec_s` вместо
   средней скорости), в отчёте приводится один метод, второй — оговоркой, а
   расхождение со старым текстом называется вслух.
   *Готово, когда* старый и новый файлы лежат в одном каталоге и sha256 обеих копий
   (рабочей и на шаре) совпадают.

10. **Проверить отчёт на согласованность.** Все числа в тексте должны совпадать
    с приложениями и с выводом скриптов; доли и кратности — пересчитаны, а не
    прикинуты; утверждения о дублировании/объёмах — подтверждены сравнением
    размеров файлов, а не именами.
    *Готово, когда* ни одно число в отчёте не взято из `Readme` без сверки.

11. **Убрать рабочий каталог.** `scripts/fuzz_workspace.py clean "$WORK"` —
    печатает освобождённый объём; отчёт и приложения к этому моменту уже в
    `output/`. На автоочистку `$TMPDIR` не рассчитывать: Hermes убирает записи
    только при простое > 24 ч, а 20 ГиБ успевают занять диск за часы.
    *Готово, когда* `fuzz_workspace.py list` не показывает каталогов проверки, а в
    отчёте есть строка «временные материалы удалены, освобождено N».

## Формат заключения (Caveman Technical)

Коротко и проверяемо: минимум текста — максимум фактов.

Правила стиля:

- короткие предложения; один абзац — одна мысль;
- одна и та же информация не повторяется в разных разделах: требование, его
  обоснование и вывод не пересказываются трижды;
- ход рассуждений не описывается — только результат и факт, которым он подтверждён;
- общеизвестные термины не расшифровываются;
- полные журналы и большие фрагменты логов в текст не переносятся: остаётся
  строка-доказательство;
- таблицы предпочтительнее длинных описаний; приложения, перечни файлов и
  расчётные таблицы — только те, на которые опирается спорный вывод.

Структура — ровно пять разделов в этом порядке (шаблон `templates/review-report.md`):

1. **Итог.** Общий результат, сколько требований выполнено и не выполнено,
   главная причина отрицательного результата.
2. **Проверка требований.** Таблица `Требование | Результат | Обоснование`. В
   обосновании — один конкретный факт: путь в архиве, поле, число. Требования не
   объединять и не сокращать. Колонку «Результат» показывать цветом: «Соответствует» —
   зелёный, «Соответствует частично» — жёлтый, «Не соответствует» — красный.
   Если пункт закрывается **любым** из альтернативных подпунктов (п. 5: «а» или «б»),
   вердикт «Соответствует по «а»; «б» не подтверждено» красить зелёным: требование
   выполнено, а упоминание «б» остаётся в тексте для протокола. Сиреневый (`v-mixed`)
   держать для частичного выполнения по составляющим одного пункта (2 из 4 в п. 7),
   не для альтернатив. Вердиктные ячейки генератор красит сам, по первой
   фразе; для чисел и статусов без вердикта цвет задаётся меткой в начале ячейки —
   `@@good@@`, `@@warn@@`, `@@bad@@`, `@@mixed@@` (метка в HTML не попадает).
   Красить только отклонения: значение, равное норме (плато 2,00 ч), оставлять
   нейтральным, иначе цвет перестаёт что-либо выделять. Ячейку без формального
   порога (доли строк/ветвей/функций) не красить вовсе: красный там означает
   придуманный проверяющим критерий — порог предложить пользователю и ждать решения.
3. **Замечания.** По каждому: что не так → чем подтверждено → что исправить.
   Замечаний нет — так и написать.
4. **Что запросить у разработчика.** Только конкретные недостающие артефакты и
   доработки.
5. **Технические доказательства.** Только данные для спорных выводов (расчёт
   покрытия, сходимость метрик, таймлайн). Полный перечень файлов и журналов сюда
   не переносится.

Границы (нарушать нельзя):

- требования Методики не сокращать и не переформулировать «по смыслу»;
- отсутствие доказательства не превращается в «соответствует»;
- разные требования не объединяются в одну строку таблицы;
- числа, пороги, критерии и исключения сохраняются как в требовании;
- разделять фактически установленное, предположение и неподтверждённое;
- неоднозначная трактовка требования указывается явно;
- недостатки материалов не скрываются ради краткости.

Шапка отчёта (до раздела 1) остаётся фактической: объект, размер, SHA-256,
целостность, перечень требований, дата проверки. Состав архива и таблицы метрик
уходят в раздел 5 — и только если на них опирается спорный вывод.

**Замечание — это нарушение требования или процедурный дефект** (нет триажа, нет
журналов воспроизведения, не зафиксирован датчик, остановка по таймеру). Всё, что
не нарушение — объём журнала, способ снятия покрытия, «можно было бы сделать
лучше» — в замечания не попадает: это сноска или строка в разделе 5. Раздувание
списка замечаний и есть то самое «нагромождение», на которое жалуются при вычитке.

**Сводка «что проверено — чем подтверждено» и перечень ключевых артефактов при
этом формате не нужны:** их роль выполняет колонка «Обоснование» в разделе 2.
Держать их в отчёте — значит трижды повторить одни и те же ссылки.

Таблица требований с обоснованием — **одна на отчёт**. В подробном варианте (раздел
«Проверка по пунктам» с подразделами) она стоит в «Итоге», а в самом разделе проверки
сводной таблицы нет: подразделы идут сразу после заголовка. Две таблицы требований с
одними и теми же ссылками читатель воспринимает как дубль, и правки в них расходятся.

## Партия модулей (несколько архивов за один заход)

Комплект по нескольким компонентам (`<модуль>-<версия>-cert.zip` × N) проверяется
той же методикой, но с общей структурой работы:

1. Инвентаризовать все архивы сразу, без распаковки: `fuzz_artifact_inventory.py`
   плюс `unzip -Z1 <zip> | cut -d/ -f2 | sort -u` — состав корня сразу показывает,
   какие архивы плоские, а какие с вложенными `results-*.zip`.
2. Каждый архив — в свой workspace (`--label <модуль>-<версия>`): имена целей и
   инстансов (`LA000`) в материалах разных модулей совпадают, общий каталог их
   смешает и подменит статистику.
3. Свести первичные данные в один `dataset.json`: размер и SHA-256 архива, текст
   Readme, по каждой цели — инстансы с `fuzzer_stats` целиком, seeds, состав
   `corpus/`/`crashes/`/`hangs/`, покрытие из gcovr.
4. Отчёты генерировать скриптом из `dataset.json`, а не писать по одному руками:
   одинаковый словарь вердиктов, одна правка чинит все модули, числа в тексте
   берутся только из данных. Шаблон отчёта при этом остаётся один и тот же.
5. После генерации сверять текст с данными программно (число файлов находок,
   покрытие, `time_wo_finds` должны встречаться в MD в отформатированном виде) —
   такой объём глазами не проверяется, а расхождения копятся именно в числах.
6. HTML собирать по каждому модулю отдельно; сводную таблицу по партии предлагать
   пользователю отдельным документом, а не вклеивать в модульные отчёты.

## Критерии по пунктам (что считается доказательством)

| Пункт | Доказательство «выполнено» | Типовой пробел в материалах |
|---|---|---|
| 1. Санитайзеры | Явный перечень датчиков и параметров сборки в материалах; сборка C/C++/Rust/Go с ASan/UBSan/MSan | Перечень не зафиксирован; есть только переменные окружения; нет бинаря и флагов |
| 2. Коллекции / правила | Коллекция на каждый интерфейс, сформированная разработчиком, с описанием принципов; либо правила порождения | Стартовый корпус = 1 файл; итоговый корпус — продукт самого фаззера; словарей нет |
| 3. Анализ журналов | Таблица триажа находок + подтверждение воспроизведения в штатном режиме | Есть только сырые журналы; `hangs/` не разобраны; воспроизведение не описано |
| 4. Генетические алгоритмы | Инструментирование подтверждено обратной связью по покрытию, есть прирост путей | Не указан тип инструментирования (исходники/LTO/бинарь) |
| 5. Критерий завершения | Пути ≥ 2× seeds **или** покрытие ≥ 2× стартового; либо льгота 90 % строк / 80 % блоков (у libFuzzer «пути» — это `ft` или `cov`, см. `references/jazzer-libfuzzer-artifacts.md`) | Покрытие от стартовых образцов не измерено; льгота считается по сумме целей, а не по цели |
| 6. ≥ 2 ч без новых путей | `time_wo_finds` ≥ 2 ч у каждого инстанса (или плато по журналу) | По части целей нет `fuzzer_stats`; прогон прерван без финальной статистики AFL |
| 7. Покрытие + параметры | HTML/XML покрытие по каждой цели, параметры сборки, принципы коллекций и словарей | Параметры сборки и принципы коллекций отсутствуют |

## Словарь вердиктов

Держать формулировки одинаковыми во всём отчёте — по ним сверяются между собой
пункты и приложения.

- **Соответствует** — артефакты прямо подтверждают требование.
- **Соответствует частично** — подтверждена часть составляющих пункта
  (в п. 7 их четыре: покрытие по цели, покрытие суммарно, параметры сборки,
  принципы коллекций) — указывать «N из M».
- **Не соответствует** — артефакты прямо противоречат требованию.
- **Не подтверждено материалами** — проверить нельзя, потому что нужного
  артефакта в материалах нет. Это **не** то же самое, что «не соответствует»:
  разработчику запрашивается артефакт, а не переделка работы.

Формулировать про материалы, а не про людей: «материалы не содержат …» вместо
«проверка не выполнялась». Второе — упрёк, который по архиву не проверяется, и
разработчик справедливо возразит, что анализ у него есть, просто не приложен.

## Pitfalls

- **WuppieFuzz: `objectives` в отчёте ≠ файлов в `crashes/`.** Отчёт считает срабатывания
  (одна последовательность может дать десятки), а в `crashes/` лежит по файлу на
  тест-кейс: 715 objectives ↔ 691 файл. Плюс почти каждому входу сопутствует
  скрытый двойник `.<хеш>` размером 1 байт (содержимое — символ `1`) в `crashes/`,
  `queue/`, `corpus/initial/`, из-за чего при подсчёте «глазами» число находок
  удваивается. Метаданные `.<хеш>_N.metadata` пусты (`executions: 0`,
  `exec_time: null`, `map: {}`) — по ним ничего не проверить.
- **WuppieFuzz: группировка `faults` — по операции, а не по причине.** Шесть
  «fault-групп» в `report.json` могут быть четырьмя причинами: одна причина даёт
  срабатывания на нескольких операциях, один endpoint — две разные причины.
  Триаж делать по причинам, а не по `operationId`.
- **WuppieFuzz: сервис не пишет 5xx в свой журнал.** Записи `Http.Input.Response`
  фиксируют только успешные/4xx ответы; 500 подтверждается записями
  `An unhandled exception was thrown` и кадрами `at IAM.*(...) in .../src/...:line N`.
  Расхождение «в журнале нет ни одного 500» — не противоречие отчёту, а свойство
  логирования; проверять надо равенство числа исключений числу срабатываний
  (в разобранном случае 716 = 716) и непрерывность PID процесса.
- **SQLSTATE бывает буквенно-цифровым.** `Npgsql.PostgresException (0x...): 2201X:
  OFFSET must not be negative` — регулярка `\d{5}` такие коды пропускает, и они
  молча схлопываются в «прочее» (в разобранном случае 67 из 326). Брать `\w{5}`.
- **`md_report_to_html.py` режет первые 8 строк.** Метаданные он берёт из
  `lines[1:8]`, а тело начинает с `lines[8:]`, поэтому таблица, попавшая в шапку,
  из HTML исчезает. В шапке — только 6–7 строк вида `**Метка:** значение` подряд,
  таблицы — начиная с раздела 3.
- **Не распаковывать архив целиком.** 2,6 ГБ сжатого превращаются в 21–23 ГиБ;
  на типовой VM это половина диска. Сначала `unzip -l`/инвентаризация, потом
  точечная распаковка по шаблонам.
- **Рабочие каталоги не должны накапливаться.** `$TMPDIR` (scratch Hermes) чистится
  только при простое > 24 ч, а распакованные 20 ГиБ успевают забить диск ВМ за
  часы (здесь 17 ГБ свободно из 40). Правило: `purge --older-than 1` в начале
  новой проверки, `clean` — в конце.
- **`/tmp` — не место для материалов.** На этой ВМ `/tmp` — tmpfs на 3,7 ГиБ, то
  есть RAM: распаковка туда съест память и всё равно не влезет. `/var/tmp` — на
  диске, но при перезагрузке **не** чистится (в `tmpfiles.d` правило `q`, а не `D`),
  так что «очистится после ребута» — неверная посылка; очистку обеспечивает только
  явный `clean`/`purge`.
- **Не распаковывать рядом с архивом.** Архив обычно лежит на vmhgfs/NFS: запись
  туда засоряет шару заказчика и идёт медленнее локального диска.
- **Дубли ищутся по паре «имя + размер», а не по имени.** Одноимённые
  `plot_data`/`fuzzer_stats` у 20 инстансов — это разные файлы. Настоящий дубль —
  совпадение имени и размера (например, журналы и распакованные, и внутри
  вложенного `results-*.zip`).
- **`fuzzer_stats` может отсутствовать у части целей.** Это не повод писать
  «метрики недоступны»: покрытие и плато восстанавливаются по журналу фаззера
  (`afl_log_timeline.py`), а в отчёте указывается, что это реконструкция.
- **Нет строки `Statistics: ...` в журнале — прогон прерван.** Штатное завершение
  AFL печатает финальную статистику; её отсутствие означает kill контейнера, и
  причину остановки по материалам установить нельзя. Это отдельное замечание.
- **`ASAN_OPTIONS`/`MSAN_OPTIONS` в окружении ≠ сборка с санитайзерами.**
  Переменные ставит оркестратор; в одном бинаре ASan и MSan несовместимы, так что
  по ним нельзя определить, что реально включено. Пункт 1 требует явной фиксации.
- **Один стартовый образец делает п. 5«а» вырожденным.** 3400 путей против 1 seeds
  формально даёт кратность 3400×; это надо назвать прямо, а не предъявлять как
  доказательство достаточности фаззинга. Достаточность проверяется по «б» и по
  абсолютному покрытию.
- **Покрытие карты AFL и покрытие gcovr — разные величины.** 5 % по карте при
  90 % по строкам — нормально (карта шире, чем файлы модуля, попавшие в gcovr).
  Сравнивать их нельзя, а расхождение надо объяснять в отчёте.
- **«Ветви» gcovr ≠ «базовые блоки» Методики.** gcovr не даёт покрытие по базовым
  блокам, поэтому вторую половину льготы (80 % блоков) по таким отчётам оценить
  невозможно — так и писать.
- **Льгота 90 %/80 % применяется к цели, а не к сумме целей.** Объединённое
  покрытие двух целей всегда выше каждой по отдельности и маскирует слабую цель.
- **Таймаут сравнивать с реальным временем исполнения.** При `-t 1000` мс и
  медианном `exec_us` 500–1500 мкс превышение в 1000 раз — это не «строгий
  таймаут», а вероятное зависание; при `exec_us` ~1000 мс те же таймауты, наоборот,
  артефакт настройки. Медиану брать из строк `exec_us=` журнала.
- **Корпус фаззера ≠ сформированная коллекция.** Итоговый `corpus/` из тысяч
  мутированных файлов выглядит разнообразно, но он продукт фаззера, а не
  коллекция разработчика; п. 2 проверяет именно стартовый корпус и принципы.
- **Числа из `Readme` перепроверять.** Сопроводительный файл обычно содержит
  только сводку покрытия и умалчивает о зависаниях, отсутствии статистики и
  нулевом покрытии отдельных файлов; таблицу gcovr в нём стоит сверить с HTML
  (обычно совпадает), а вот выводы Readme — не источник.
- **Заголовки таблиц и единицы.** В отчётах фигурируют и ГиБ, и ГБ: 21,8 ГиБ и
  23,4 ГБ — один и тот же объём. Указывать обе величины, чтобы не спорить с
  разработчиком о цифрах.
- **Плоская раскладка ломает `afl_stats_report.py`.** В части архивов статистика
  лежит как `misc/engine.LA000.fuzzer_stats` без каталога-инстанса, а скрипт ждёт
  `<misc>/LA0NN/fuzzer_stats` и показывает «нет инстансов». Собрать
  `statview/LA000/` копиями `misc/engine.LA0NN.fuzzer_stats` и подать `statview`.
- **Jazzer-специфика собрана в `references/jazzer-libfuzzer-artifacts.md`.** Там: контроль
  датчика на пустом корпусе (SSRF-детектор срабатывает на loopback-подключении самого
  харнесса), смысл `--disableBugDetectors` в `target.conf`, запуск `fuzz()` без Docker и
  Jazzer.js, разбор `corp: …/151Kb`, `--mode regression`.
- **`validator-log.txt` — не протокол триажа.** Это журнал оркестратора (кто
  поднялся, когда сохранялись образцы); ссылаться на него как на «анализ находок»
  нельзя. Триаж — таблица с классификацией и воспроизведением.
- **Заявление Readme «находки ложные, при триаже не подтвердились» — не триаж.**
  Если файлы в `hangs/` лежат, а таблицы и протокола воспроизведения нет, вердикт
  по п. 3 остаётся «не соответствует», как бы уверенно ни был написан Readme.
- **Вердикт — первой фразой ячейки, иначе цвет не встанет.** `md_report_to_html.py`
  красит любую ячейку `<td>`, текст которой начинается с вердикта (жирный не нужен):
  «Соответствует» → `v-good` (зелёный), «Соответствует частично» → `v-warn`
  (жёлтый), «Не соответствует» → `v-bad`, «Соответствует по…» + «не подтверждено»
  → `v-mixed` (сиреневый), «ложное срабатывание» → `v-good`. Пояснение перед словом
  «Соответствует» оставит ячейку неокрашенной, а пояснение вместо вердикта — скроет
  его среди текста. Числовые отклонения и статусы без вердикта помечать в начале
  ячейки `@@good@@`/`@@warn@@`/`@@bad@@`/`@@mixed@@`. После пересборки проверять
  `grep -o 'td class="v-[a-z]*"' f.html | sort | uniq -c` — число цветных ячеек
  должно равняться числу пунктов требований **плюс** числу помеченных отклонений, а
  `grep -c '@@' f.html` — нулю (незаменённая метка видна читателю).
  **Словарь префиксов у копии генератора бывает неполным:** если в
  `VERDICT_CLASSES` нет «не применимо», такие ячейки молча остаются нейтральными, а
  «Соответствует / Не применимо» красится зелёным. Перед сборкой посмотреть сам
  кортеж (`grep -n -A8 'VERDICT_CLASSES' <скрипт>`) и дописать нужный префикс
  (`не применимо` → `v-mixed`, перед `не соответствует`), а не перекрашивать готовый
  HTML. Заодно проверить, есть ли в этой копии поддержка `@@…@@`: набор меток мог не
  дойти при синхронизации профиля, и тогда строить раскраску на них нельзя. Ожидание
  формулировать арифметикой: зелёные + жёлтые + сиреневые = число вердиктных ячеек;
  после повторной сборки сверять именно сумму, а не только зелёные.
- **Широкие таблицы транспонировать.** 12 колонок «инстанс × метрика» не влезают
  в страницу и рвутся при печати; вид «Показатель | `LA000` | `LA001`» (12 строк)
  читается без горизонтальной прокрутки. В таблицах результата держать не больше
  пяти колонок: длинные значения (флаги `NODE_OPTIONS`, пути, команды) расширяют
  ячейки так, что таблица вылезает за контейнер (`scrollWidth` 811 при
  `clientWidth` 719), и флаги/команды/перечни доказательств выносить списком под
  таблицей. Прокрутку проверять у каждой таблицы (`t.parentElement.scrollWidth >
  t.clientWidth`), а не у первой — переполняется обычно самая насыщенная.
- **Объём рабочего каталога замерять до генерации финальных HTML.** `clean` только
  печатает освобождённый объём, а строка «временные материалы удалены,
  освобождено N» — часть Verification; иначе отчёты придётся перегенерировать
  ради одной строки. `clean` отказывается удалять каталог, если `cwd` внутри него
  (`ОТКАЗ: это … текущий каталог`) — запускать из `$TMPDIR`. Сам генератор отчёта
  держать в постоянном каталоге вне `$TMPDIR` (например `…/cache/gen/`), а не только
  вне workspace: `clean` удаляет workspace вместе с генератором на 300–400 строк, и
  пересборка после доработки материалов означает переписать его заново. При повторной
  проверке числа пересчитываются тем же генератором и сверяются assert'ом против
  прежнего HTML.
- **`stability` < 100 % завышает `edges_found`.** Нестабильная карта даёт ложные
  «новые пути»: при 40–80 % п. 5«а» выполняется формально, и это надо оговорить.
  Вывод по п. 4 при этом сохраняется — форк-сервер, CmpLog и прирост путей видны
  и без детерминизма.
- **Таймаут в сотни секунд отключает обнаружение зависаний.** `-t 200000` мс при
  медиане исполнения 120–170 мс означает, что зависанием считается только
  двадцатиминутный цикл: пустой `hangs/` не доказывает устойчивость цели. Это
  замечание к пп. 3 и 6, а не признак качества.
- **Формулировка «не подтверждено» экономит цикл.** Требование «перечень датчиков
  фиксируется в материалах» нарушено отсутствием записи, а не отсутствием
  санитайзеров; в запросе должно быть «приложите перечень и параметры сборки», а
  не «переделайте фаззинг».

- **`cov` и `ft` — разные метрики, и вердикты по ним расходятся.** `cov` — покрытые
  рёбра, `ft` — признаки (рёбра + данные сравнений). У цели с большим стартовым
  корпусом `ft/seeds` может быть 9×, а `cov/seeds` — 1,2×: п. 5«а» выполняется только
  для той метрики, которую выбрали. Считать обе, указывать выбор и запрашивать
  у разработчика, какая величина у него считается «уникальными путями».
- **Прогон длиной ровно 2 ч не означает плато 2 ч.** Если тестирование шло 7 200 с,
  то «2 ч без новых путей» возможно только при последнем приросте в первые секунды.
  Искать момент последнего **прироста** `cov` и `ft` по отдельности на любой строке
  прогресса, а не только `NEW`: прирост признаков печатается и на `REDUCE`
  (минимизация корпуса добирает данные сравнений), поэтому фильтр по `NEW` сдвигает
  плато в прошлое. Журналы libFuzzer содержат двоичные байты — `grep` без `-a`
  отвечает «binary file matches» и обрезает вывод; искать только `grep -a`.
  В отчёте приводить строку журнала, номер запуска и `exec/s`, чтобы плато
  пересчитывалось одной формулой: на вопрос «прогон же длился 2 ч» ответ — арифметика,
  а не пересказ.
- **Смена вердикта в готовом HTML — не одна правка.** Когда недостающий артефакт
  приложен, вердикт меняется минимум в шести местах: ячейка сводной таблицы, абзац
  первого раздела, итоговый вывод, таблица состава материалов, раздел «чего нет»,
  список запросов и приложения со ссылками на файл. Плюс сам приложенный документ:
  его вводная фраза и вывод («таблицы в материалах нет», «процедурно остаётся
  частично») начинают противоречить заключению — их править тоже. Замена текста
  внутри `<td><strong>…</strong></td>` класс не меняет: подсветка остаётся от
  прежнего вердикта (`v-warn` на зелёной строке). Править `<td class=…>` вместе с
  текстом и сверять `grep -o 'class="v-[a-z]*"' file.html | sort | uniq -c` с
  ожидаемым числом зелёных/жёлтых ячеек.
- **Футер и кикер генератора — из шаблона прошлой проверки.** В HTML остаются имя
  чужого архива и перечень `fuzzer_stats`/`gcovr`; для сертификационного документа
  это дискредитирующий артефакт. Передавать `--kicker` и `--footer` в командной
  строке, а после сборки всё равно `grep` по HTML на имена архивов, `AFL`, `gcovr`.
  Если запуск падает с `unrecognized arguments: --kicker` — в копии скрипта старая
  версия: добавить аргументы в `argparse` и подстановки `{kicker}`/`{footer}` в
  HTML-шаблон, а не править собранный файл руками (иначе следующая пересборка
  вернёт чужой подвал).
- **Триаж, выполненный проверяющим, — не триаж разработчика, пока он вне комплекта.**
  Если лаборатория сама разобрала находки и приложила таблицу отдельным файлом рядом
  с заключением, п. 3 остаётся «соответствует частично»: содержательная часть закрыта
  приложением, процедурная — нет (в комплекте разработчика таблицы нет). Как только
  таблица и протокол перенесены внутрь комплекта (`docs/triage/…`), вердикт п. 3 —
  «соответствует», а авторство остаётся замечанием, а не основанием для «частично»:
  «триаж составлен проверяющим — в деле это стоит подписать». Не оставлять «частично»
  из-за авторства после включения файлов и не поднимать вердикт, пока их нет.
  Переносить нужно таблицу и протокол прогонов; редактируемая версия (`.md`) — по
  желанию, но если она остаётся рядом с заключением, в таблице состава это надо
  указать, иначе комплект и приложение дублируются.
- **Правка собранного HTML — regex по словам, не по точной строке.** В готовом
  отчёте текст переносится по строкам, поэтому поиск точной фразы даёт ноль
  совпадений (и `assert` падает, если он есть). Строить шаблон как
  `r'\s+'.join(map(re.escape, phrase.split()))` и проверять число замен через
  `re.subn(...)[1]`; перед пачкой правок сохранять копию файла. После правок
  прогонять проверку баланса тегов (`html.parser`, стек незакрытых) — незакрытый
  `<div>`/`<table>` на скриншоте не виден, но рвёт печать.
  Просьбу «добавь колонку» начинать с инвентаризации шапок всех таблиц
  (`re.findall(r'<th[^>]*>(.*?)</th>')` по каждой `<table>`): нумерация разделов в
  сокращённой и основной версиях разная, и «п. 2» у пользователя может означать
  любую из двух таблиц требований. Прежде чем дописывать данные, проверить, не
  спрятана ли колонка за горизонтальной прокруткой: `table.getBoundingClientRect().width`
  против `parentElement.clientWidth`, плюс печать в PDF (`Page.printToPDF` →
  `pdftoppm` → просмотр) — на A4 таблица печатается целиком, а в узком окне
  обрезается, и тогда править нечего. Новая колонка = `<th>` в шапке + ровно один
  `<td>` в каждой строке тела; число строк и ячеек сверять `assert`'ом, иначе
  последняя строка съезжает молча. Сразу задавать ширины через `<colgroup>`
  (№ — 46 px, требование 31 %, вердикт 21 %, обоснование — остальное): без них
  длинные ссылки в новой колонке сжимают «Требование» в узкий столбик. Заодно
  искать опечатки вида «не подтверждено))» — двойная скобка переживает правку.
- **Входы из корпуса разработчика не удалять без пересчёта покрытия.** Стартовый
  корпус — база, на которой снято покрытие (`coverage/seeds/regression.log`: число
  прогонов) и записаны счётчики в `docs/collections-and-dictionaries.md`; удаление
  даже трёх «лишних» файлов меняет seeds (29 → 26) и расходится с уже снятыми
  числами, а переснять их без Docker нельзя. По умолчанию оставлять файлы и
  закрывать вопрос триажем; если изъятие требуют — переносить в
  `docs/triage/excluded-inputs/<цель>/` с README и править все счётчики, а не
  удалять, и фиксировать это в замечаниях.
- **Перенос блоков из сокращённой версии (`-v2`) в основную.** Таблицу
  «требование | результат | обоснование» переносить в раздел «Итог» вместе с колонкой
  «Обоснование», а не вставлять второй таблицей перед подробными подразделами: две
  таблицы требований с одними ссылками — тройной повтор. Список
  запросов принимать в порядке v2. Числа при переносе
  сверять с журналом: в основной версии могут остаться значения от прежнего
  расчёта (540/72 с против 532/65 с), и перенос — повод их исправить, а не
  скопировать. Разделы сопоставлять по названию, а не по номеру: «Проверка
  требований» в сокращённой версии — раздел 2, а в основной та же таблица живёт
  внутри раздела 3, и перенос «по номеру» ставит её не туда. После переноса
  проверить, что таблица требований осталась одна: сводную таблицу в разделе проверки
  удалить вместе с подводкой («Сводка по пунктам…»), а подразделы оставить сразу
  после заголовка раздела.
