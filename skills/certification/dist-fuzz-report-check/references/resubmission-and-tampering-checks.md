# Повторная проверка комплекта и сверка с прежней передачей

Когда модуль приходит второй раз (каталог `<модуль>_2`, `-final`, `-improved`,
`-v2`), работа начинается не с инвентаризации, а со сверки с прежним комплектом:
разработчик мог как перезапустить кампанию, так и поправить артефакты прошлой.
И то и другое меняет вердикты, и различить их можно только сравнением файлов.

## Где взять прежние материалы

- Соседние каталоги в каталоге заказчика: `<модуль>`, `<модуль>_2` — прежний архив
  и его `output/` лежат рядом, заключение называется `*-check.md` и содержит
  SHA-256 прежнего архива в шапке.
- Если заключения нет — прежний архив всё равно годится как база сравнения.
- Новое заключение писать в `output/` **нового** каталога; прежнее не править и не
  удалять. В шапке указать SHA-256 обоих архивов и сослаться на предыдущее
  заключение.

## Порядок сверки

```bash
sha256sum <прежний.zip> <текущий.zip>
unzip -Z1 <прежний.zip> > old.list; unzip -Z1 <текущий.zip> > new.list
diff old.list new.list && echo "состав записей совпадает"
diff old/fuzzer_stats new/fuzzer_stats                 # поля и значения
diff -u old/README.md new/README.md                    # что дописано/вычеркнуто
cmp old/<журнал> new/<журнал>                          # первый различающийся байт
```

Корпус и отчёт покрытия сравнивать хешами файлов (имя → sha256), а не размерами:
у пересобранного архива mtime и порядок записей меняются, содержимое — нет.

```python
# журнал: сколько строк изменено, совпадают ли префикс и хвост
a=open('old/log','rb').read(); b=open('new/log','rb').read()
i=...  # первый различающийся байт из cmp
print(a[:i]==b[:i])                      # префикс до правки
La,Lb=a.split(b'\n'),b.split(b'\n')
print([(k+1,x[:120],y[:120]) for k,(x,y) in enumerate(zip(La,Lb)) if x!=y])
print(La[k+1:]==Lb[k+1:])                # хвост после правки
```

## Как отличить новый прогон от правки

| Признак | Новый прогон | Тот же прогон, артефакты правили |
|---|---|---|
| `start_time`, `last_update`, `run_time`, `execs_done` | другие | совпадают побайтово |
| корпус (`corpus-final/`), отчёт покрытия | другие хеши файлов | те же файлы тех же размеров |
| `saved_hangs` / `total_tmout` / `last_hang` | новые значения | обнулены или уменьшены |
| итоговая строка `[*] Statistics: …` | новое число находок | одна строка изменена, файл короче/длиннее на единицы байт |
| `build.log.txt` | может отличаться полностью | отличается только флагами и/или шапкой |

Правило: совпали `start_time` + `execs_done` + хеши корпуса — кампания не
перезапускалась, и любые расхождения в числах находок, `fuzzer_stats` или
журнале — правка первичных доказательств.

## Журнал сборки: пересборка или правка

- Строка `-- Configuring done (N s)` различает конфигурации: у реальной
  переконфигурации время другое (в разобранном случае 53,5 с против 133,5 с) и
  другой порядок строк сборки; у копии с подменёнными флагами время совпадает
  байт в байт.
- Отсутствие шапки журнала (`Setting env AFL_USE_ASAN=1`, `AFL_DONT_OPTIMIZE=1`),
  которая есть в исходном журнале, — тоже признак другой выгрузки.
- Разные флаги при одинаковых артефактах прогона означают: сборка с датчиком в
  текущем комплекте к этому прогону не относится. Вердикт по п. 1 — «не
  подтверждено материалами» (журнал сборки есть, привязки к прогону нет), запрос —
  хеш бинаря, `ldd`/`nm` на libasan, `ASAN_OPTIONS` и указание, какой из журналов
  относится к фаззинг-бинарю. Не писать «не соответствует»: противоречие между
  двумя журналами сборки само по себе не доказывает, что датчика не было.

## Что писать в заключении

- В шапке — оба архива и их SHA-256, одна строка «повторная проверка,
  предыдущее заключение — <путь>».
- Раздел 5.1 — таблица «файл | прежний комплект | текущий | что изменено» с
  размерами и конкретными полями; она и есть доказательство правки.
- Замечание формулировать про материалы, без обвинений: «Материалы содержат
  правку первичных артефактов: значения зависаний заменены нулями в
  `fuzzer_stats` и в итоговой строке журнала, прогон при этом не перезапускался».
  Дальше — что подтверждено (поля, номера строк, размеры), затем что исправить:
  восстановить исходные артефакты и приложить находки.
- Вердикт п. 3 в такой ситуации — «не соответствует» (находки есть и не
  разобраны), а не «частично»: удаление находок не заменяет триаж.
- В запросе — исходные (неотредактированные) `fuzzer_stats` и журнал, файлы
  находок, таблица триажа и протокол воспроизведения, объяснение расхождения,
  если правка была следствием ошибки выгрузки.
- Не переносить числа из прежнего заключения: они пересчитываются из артефактов,
  а совпадение с прежним текстом проверяется отдельно.
