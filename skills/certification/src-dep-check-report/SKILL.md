# Анализ отчётов по уязвимостям заимствованных компонентов

Размеченный отчёт (csv/xlsx с колонками `component`, `id`, `severity`, `status`, `detail`)
проходит две стадии: сначала **правка** — из отчёта уходят строки вне high/critical, правится
орфография, а всё спорное по разметке собирается в отдельный HTML-отчёт рекомендаций; потом
**генерация** — согласованные рекомендации переносятся в итоговый файл.

| Этап | Что делает | Выход в `src-dep-check-report` |
|---|---|---|
| 1. Правка отчёта | поиск файла, опись полей, удаление строк вне high/critical, орфография, сбор рекомендаций | `<имя>_filtered.xlsx` (промежуточный), `recommendations.html`; список пунктов для этапа 2 — в рабочем каталоге `~/.cache/src-dep-check-report/work/` |
| 2. Генерация отчёта | применяет согласованные пункты рекомендаций к промежуточному файлу | `<имя>_итоговый.xlsx` |

## When to Use

- «проверь отчёт по заимствованным компонентам», «проанализируй уязвимости компонентов»,
  «подготовь отчёт для сертификации».
- Пришёл xlsx или csv с колонками `name, version, purl, component, id, severity, status, detail`
  либо `ancestor_component_name/version/purl, component_purl, vuln_id, severity, status, detail`.
- Просьба без файла: отчёт ищется в шаренной папке (этап 1, шаг 0), а не запрашивается сразу.
- Не для: сборки SBOM и сведения списка CVE с деревом компонентов — здесь проверяется уже
  размеченный отчёт.

## Железные правила

1. **`id` уязвимости и purl компонента не переписываются никогда** — переносятся как есть,
   даже при явной опечатке. Расхождение становится находкой, а не правкой ячейки.
2. **Этап 1 меняет в отчёте три вещи:** удаляет **все** строки с `severity` вне {high, critical}
   (сохранить их можно только флагом `--keep-all-levels`); правит орфографию и лишние пробелы
   в `detail`; задаёт оформление листа, собранного из csv.
   **Строки в отчёте не подсвечиваются** — что именно поправлено, видно в разделе «Внесённые правки»
   HTML-отчёта; листа «Изменения» и листа «Журнал» в xlsx не бывает. Цветом помечена только шапка
   (заливка, белый жирный шрифт) — это оформление, а не признак правки. Формулировки не переписываются:
   ни расширение, ни дополнение обрывков, ни пунктуация: всё это только предложения
   в файле рекомендаций. Статусы, порядок строк и `id` тоже не трогаются, иначе промежуточный
   файл перестаёт быть проверяемым.
3. **Всё остальное — рекомендация в отдельном файле, а не правка.** Смена статуса, переписанное
   или дополненное обоснование, пунктуация, замечания к разметке — в `recommendations.html`
   и `recommendations.json`, у каждого пункта: строка, компонент, `id`, «сейчас», «предлагаю»,
   основание и источник. В отчёт они попадают только на этапе 2.
4. **Статус меняется только по согласованию.** Даже `na → fp` по диапазону версий — предложение;
   в итоговый файл оно попадает только после «да» по номеру или по классу, и это видно в журнале.
5. **«Не используется» — ошибка разметки.** Тезис о неиспользуемости компонента (как и любая фраза
   о том, что компонент/функция не применяется, код недостижим) — не проверяемое основание. Такие
   строки идут в раздел «Ошибки разметки»; шрифт в таблицах чёрный, а красным (подложка + полоса
   слева) помечаются только строки с ошибками человека: неиспользуемость, недопустимые значения
   полей, удалённый мусор. Дефекты выгрузки (служебные строки, одноколоночный CSV, кодировка)—
   отдельный раздел «Дефекты файла» без цвета: это не ошибки человека.
   Своих формулировок про неиспользуемость не предлагаем вообще — ни в тексте, ни в советах:
   проверяющий не должен получать довод, который нельзя проверить.
6. **Решающий признак fp/na — версия, а не тон текста.** Поставленная версия вне затронутого
   диапазона → `false_positive`; в диапазоне и функциональность не задействована → `not_affected`.
   Источник диапазона — NVD `cpeMatch`; OSV по purl для `apk`/`deb` пуст всегда.
7. **Результаты — в `src-dep-check-report`** рядом с исходным отчётом, исходный файл не перезаписывается
   и в каталог не переносится.
8. **Числа в ответе берутся из прогона скрипта**, а не из глазомерной оценки.

## Этап 1 — правка отчёта

```bash
python3 <скилл>/scripts/check_report.py <отчёт.xlsx> --outdir <шара>/src-dep-check-report
```

Скрипт делает шаги 1–6 и печатает JSON со счётчиками; каждый шаг продублирован строкой журнала.

0. **Отчёт ищется самостоятельно, если его не приложили.**

   ```bash
   python3 <скилл>/scripts/find_report.py --json <scratch>/report_candidates.json
   ```

   Скрипт читает `/proc/mounts`, находит точки шары (`vmhgfs/9p/cifs/vboxsf/nfs`), перебирает
   xlsx/csv и оценивает файл по колонкам-признакам и имени. Коды выхода: `0` — кандидаты есть,
   `2` — шара не смонтирована, `3` — смонтирована, отчёта нет.

   - **Код 2** — поднять шару: `sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other`
     (VirtualBox — `sudo mount -t vboxsf <имя_шары> /mnt/<точка>`). Автомонтирования в этой среде
     нет: `/mnt/hgfs` пуст после перезагрузки и после приостановки ВМ, причём шара отваливается
     и посреди сессии — файл, который читался минуту назад, даёт `FileNotFoundError`. Поэтому
     перед ответом «файла нет» — проверить `/proc/mounts` и поднять шару заново.
   - **Один кандидат** — брать его и записать путь в журнал.
   - **Несколько кандидатов** — спросить по номерам, какой файл брать: рядом могут лежать
     выгрузки по другим продуктам. **Отчёты не объединяются никогда:** один запрос — один файл;
     если имени/выбора нет, а в шаре несколько отчётов, сначала вопрос, потом работа. В результат
     идут только данные выбранного файла — чужие строки в `_filtered` и в рекомендации не попадают.
   - **Код 3** — спросить человека, назвав проверенные каталоги (`roots` из JSON).

   `…_filtered`, `…_итоговый` и каталог `src-dep-check-report` — свои результаты, входами не считаются.

1. **Опись входа.** Шапка ищется по словарю колонок (в выгрузках над ней бывает служебная
   строка `Column1…Column8`). Обязательные поля: продукт, версия, purl продукта, `component`,
   `id`, `severity`, `status`, `detail`. Нет колонки или пустая ячейка — перечислить находки
   и спросить, продолжать ли разбор по остальным полям. Формы файлов — `references/report-formats.md`.

   **Лист выбирается по объёму данных, а не по порядку.** В выгрузках первый лист нередко
   оказывается обрывком на десяток строк, а полный отчёт — на следующем, и наоборот. Скрипт
   берёт лист с наибольшим числом заполненных строк. Лист-одна-колонка с CSV-текстом
   (экспорт в ячейку, часто в cp1251 — `РњС‹ РЅРµ`) разбирается как таблица: сначала обычное
   перекодирование, затем побайтовое — выгрузки бывают перекодированы дважды, а байты без
   пары в cp1251 остаются управляющими. После восстановления данных исходный одноколоночный
   лист в результат не переносится — вместо него чистый лист «Отчёт».

   **CSV читается с явным выбором кодировки.** В csv кодировки нет: скрипт пробует
   `utf-8-sig`, `utf-8`, `cp1251`, `cp1252` по байтам файла, а двойное перекодирование
   («РњС‹ РЅРµ») снимает поячеечно — иначе обоснование триажа приезжает в xlsx мойибаке
   и читается как мусор. В xlsx текст пишется в UTF-8; русское обоснование проверяется чтением
   ячейки обратно, а не просмотром файла в редакторе. Разделитель определяется по шапке
   (`;`, `,`, табуляция).

   **Внешние данные нейтрализуются, а не сносятся.** Выгрузки часто сделаны запросом
   (`connections.xml`, `xl/queryTables/*`, таблица `tableType="queryTable"` + скрытое имя
   `ExternalData_*`). openpyxl эти части не переносит, и Excel на открытии просит восстановление
   («часть внешних данных повреждена»). Убирать таблицу нельзя — на ней цвета полос и фильтры:
   снимаем `tableType`, ссылки на поля запроса и имена `ExternalData_*`, а потом прописываем
   таблице и автофильтру новый диапазон и имена колонок по шапке. Результат: полосы, фильтры,
   ширины и шрифты как в источнике, внешних данных и имён нет.

   **Служебная строка `Column1 … Column8` удаляется.** В выгрузках над шапкой почти всегда стоит
   такая строка — в отчёт она не попадает: скрипт удаляет её вместе с пустыми строками, шапка
   поднимается вверх, номера строк дальше считаются от новой разметки. Признак — все непустые
   ячейки строки вида `ColumnN`; настоящая шапка под этот признак не попадает. Любой список
   строк, посчитанный до удаления (мусорные, пустые, строки вне high/critical), после
   `delete_rows` недействителен: его пересчитывают сразу после удаления. Иначе следующая
   выборка съезжает на сдвиг и в файле остаётся мусор при «успешных» счётчиках в журнале.

   **Аудит файла.** Идёт по всем листам книги до правок: мусорные строки над шапкой, строки без
   названия продукта, компонент не в формате purl, уровни опасности и статусы вне словарей,
   пустой `status` и `not_set`. Удаление таких строк — по правилу следующего шага; в выборку
   high/critical попадает только строка с валидным уровнем, а нечитаемые строки в отчёте
   остаются и уходят в рекомендации замечаниями (см. шаг 2).
2. **Уровень опасности и удаление строк.** Строки с валидным уровнем вне {high, critical}
   удаляются все — это и есть выборка отчёта, и в журнал идёт `оставляю только high и critical —
   удалено M из K`. Ноль удалённых — тоже запись. После прогона проверяется, что в файле
   не осталось ни одного другого уровня: счётчик в журнале и содержимое листа сверяются,
   иначе часть medium/low/none остаётся в отчёте при «успешных» числах. Сохранить все уровни
   можно только прямым флагом `--keep-all-levels` — тогда в журнале
   `уровни сохранены — строки вне high/critical не удалялись: high 15, medium 3`.

   **Нечитаемая строка не удаляется никогда.** Признак: нет продукта, компонент не в формате
   purl, идентификатор не CVE/GHSA, либо нет ни компонента, ни идентификатора. Такая строка
   остаётся в файле — это чужая разметка, решение за владельцем — и в проверки не идёт: ни статус,
   ни обоснование, ни диапазоны по ней не считаются. Каждая такая строка — отдельное замечание
   с номером в исходнике, содержимым и предложением «исправить строку или удалить её».
   Автоматически нечитаемые не удаляются ни при каком количестве — ни при четырёх, ни при всех
   строках листа: если удалять нечего проверять, отчёт так и говорит, а не вычищает файл.
   Строка с валидным purl и CVE/GHSA не удаляется никогда, даже
   если уровень пуст: это ошибка разметки, а не мусор. В журнале — `нечитаемых строк: N —
   оставлены в отчёте, вынесены в замечания`.
3. **Орфография и лишние пробелы.** Только опечатки по словарю и двойные пробелы — без
   согласования, каждая правка идёт в раздел «Внесённые правки» HTML-отчёта. Пунктуация, перестановка слов и любое
   переписывание формулировки сюда **не входят**: это рекомендация. Цветом ничего не помечается.
4. **Рекомендации по статусу.** Для каждой пары (компонент, `id`) — диапазон из NVD `cpeMatch`.
   Кэш — `~/.cache/src-dep-check-report/<CVE>.json`, ключ `--no-nvd` отключает сеть. NVD без ключа
   пускает 5 запросов за 30 секунд: запросы идут с паузой ~6,5 с и `User-Agent`, а при отказе
   сети берётся `references/version-ranges.json` (нет файла — собрать его
   `scripts/refresh_ranges.py <отчёт>`) — прогон не должен зависеть от доступности NVD.
   Версия вне диапазона при статусе не `fp` → предложение `false_positive`; версия в диапазоне
   при `fp` → замечание «разобрать достижимость»; текст называет чужой продукт → предложение
   `false_positive`.   Порядок величин и режим прогона: 70+ уникальных CVE — несколько минут, 500 CVE без ключа —
   около часа. Поэтому прогон идёт двумя заходами: быстрый с `--no-nvd` сразу даёт файл и HTML,
   а полный уходит фоном в отдельные `--outdir` и `--workdir`, чтобы не затереть готовый результат;
   после прогрева кэша повторный прогон в основной каталог занимает секунды и даёт те же числа.

   **CVE без `configurations` в NVD диапазоном не закрывается.** У части номеров в NVD только
   текстовое описание или перечень версий: тогда версию с источником сверить нечем, и для `false_positive`
   нужно другое доказательство — поиск файлов компонента (`find_component.py`, путь в дистрибутиве
   и образе). В отчёте такие строки — отдельный класс замечаний «нет данных для сверки», а не
   молчание и не «не подтверждено»: на большом отчёте их бывает больше половины (163 из 343 `fp`).
   Рецепт заполнения `version-ranges.json` и разбор ответов NVD — `references/vex-status-fp-na.md`.
   Формат файла — `{CVE: {"products": {«продукт»: [интервалы]}}}`, и это важно: один CVE часто
   описан для нескольких продуктов, и без разбивки «вне диапазона» считается по чужой ветке
   версий. Плоская запись `{"ranges": [...]}` читается как один безымянный продукт — только
   как совместимость со старым файлом, фильтр по продукту в ней теряется.
5. **Рекомендации по обоснованию.** Предлагается только то, что выводится из самого текста
   или из данных об уязвимости: обрывок без подлежащего («Исправлено 3.9.2-1» → «исправлена
   в версии X; поставленная версия Y содержит исправление»), формулировка, называющая чужой
   продукт. Пустое поле сюда не входит: им занимается раздел «Пустые поля», отдельного пункта
   «правка обоснования» для пустого `detail` не создаётся. **Утверждения о неиспользуемости
   не предлагаются ни в какой форме.**
   Готовые тексты по конкретным CVE — словарь `COMPLETIONS` в `check_report.py`: он пополняется,
   а не переписывается на каждом прогоне.

   **Основание у каждого предложения называется вместе с текстом.** Шаблон по версии («Исправлено
   X» плюс версия из purl) и упоминание чужого продукта — сильные: их проверяет сам отчёт.
   Тексты словаря `COMPLETIONS` написал агент по описаниям уязвимостей, автоматической сверки
   с бюллетенями нет — им ставится «необходимо утвердить», а не «сильная», чтобы проверяющий
   не принял формулировку за подтверждённую. Обрывок, не покрытый ни шаблоном, ни словарём,
   остаётся пометкой без предложения: дописывать недостижимость или неиспользуемость нельзя.
6. **Замечания к разметке.** Утверждение о применимости при `fp`/`na` («эксплуатация возможна…»),
   версия в тексте против версии компонента, `status` вне словаря — отдельные пункты «прочее».

   **Версия в тексте — только рядом с именем компонента.** Первое число в обосновании часто
   чужое: версия образа («в образе 6.3.4.2653»), версия другого пакета, адрес (`127.0.0.1`),
   номер протокола (`HTTP/1.1`). Такие кандидаты отбрасываются: версия считается версией
   компонента, только если имя компонента стоит в 60 знаках перед ней, и никогда — если совпадает
   с версией продукта или похожа на адрес. Без этого правила прогон на 2225 строках дал 105
   замечаний вместо 11. **Компонент всегда рассматривается
   вместе с контейнером:** один и тот же purl законно встречается в разных модулях продукта,
   и обоснования там могут отличаться — расхождение текстов между контейнерами дефектом не является
   и замечанием не становится. В пункте рекомендации контейнер указан отдельной колонкой;
   одинаковые пары в разных контейнерах — разные пункты. Готовые срезы — `references/cross-checks.md`.
7. **Сборка.** `check_report.py` пишет промежуточный `_filtered.xlsx` — **только сам отчёт,
   без новых листов**: рабочие листы «Изменения» и «Журнал» в документ не добавляются никогда.
   Правки и журнал живут только в `<отчёт>_recommendations.html` (разделы «Внесённые правки»
   и «Журнал этапа»). Форматирование источника сохраняется: ширины колонок, шрифты, заливки,
   таблица с полосами и кнопками фильтра. Таблица запроса не удаляется, а нейтрализуется
   (см. шаг 1); после удаления строк её диапазон и автофильтр пересчитываются на новый.

   **У листа из csv оформления нет — оно берётся с образца.** csv не несёт ни ширины, ни шрифтов,
   ни фильтров. Образец ищется так: `--template <файл>`, затем каталог `пример` рядом с отчётом
   (берётся первый xlsx без `~$`), затем встроенный `assets/report-template.xlsx`. С образца
   переносятся ширины колонок, стиль таблицы (`TableStyleMedium7` с полосами и кнопками фильтра,
   автофильтр от таблицы), закрепление и высота шапки; строки данных отдельно не красятся —
   цвет даёт стиль таблицы. **Тема книги тоже копируется с образца:** цвет встроенного стиля
   задан акцентами темы, и на теме openpyxl по умолчанию тот же `TableStyleMedium7` выходит
   оранжевым (accent6 `F79646`) вместо зелёного `70AD47` из образца. Проверяется не на глаз,
   а чтением `xl/theme/theme1.xml` результата: имя схемы и `accent6` должны совпасть с образцом.
   Свой вид (заливки, рамки «на глаз») не выдумывается: если образца нет, об этом пишется в журнал. У исходного xlsx оформление берётся из самого файла.

   **Сначала перекодировать и оформить, потом анализировать.** Порядок жёсткий: csv читается
   с выбором кодировки и снятием мойибаке, лист собирается и получает оформление образца,
   и только затем идут проверки, правки и удаление строк. Иначе удалённые строки и оформление
   считаются от разной разметки, а анализ видит не тот файл, который уйдёт человеку.

   Разделы HTML — по одному на каждое число статистики и на каждое замечание, без повторов:
   «Состав отчёта» (строк по контейнерам), «Удалённые строки: уровень опасности» (каждая
   удалённая строка: номер, контейнер, компонент, CVE, уровень), «Смена статуса», «Правка
   обоснований», «Пустые поля», «Неиспользуемость в обосновании», «Недопустимые значения полей»,
   «Нечитаемые строки», «Прочие замечания к разметке», «Дефекты файла», «Внесённые правки»,
   «Журнал этапа». **Карточка статистики —
   ссылка на свой раздел**, а не отдельное число: каждое число проверяется списком строк под ним.
   В «Пустые поля» — только
   строки с пустыми `severity`/`status`/`detail`, все пустые поля строки в одном пункте; полностью
   пустые строки просто удаляются и описываются только в журнале. **Пустое обоснование пунктом
   «правка обоснований» не становится** — оно уже в «Пустых полях», а другой текст для него
   не предлагается: дублей в рекомендациях быть не должно.

8. **Тон и заголовки.** Отчёт пишется как рабочий документ проверяющего, а не как ответ модели:
   никаких «передать человеку», «требует решения владельца», «показать человеку». Формулировки —
   «необходимо утвердить», «провести дополнительный анализ», «необходимо заполнить». Заголовки
   разделов — по делу («Статусы к утверждению», «Обоснования к уточнению»), без "Предложения ИИ"
   и подобного.

## Этап 2 — генерация отчёта

```bash
python3 <скилл>/scripts/build_report.py <шара>/src-dep-check-report/<имя>_filtered.xlsx \
  --spec ~/.cache/src-dep-check-report/work/<имя отчёта>.json --approve 3,7,12
# --approve-all — принять всё; --reject — отклонить отдельные номера
# → <шара>/src-dep-check-report/<имя>_итоговый.xlsx
```

Машиночитаемый список пунктов (`~/.cache/src-dep-check-report/work/<имя>.json`) — технический файл,
в сдачу не идёт: HTML читает человек, JSON читает этап 2, и в нём же остаются решения
(`decision`) по каждому пункту — отклонённое не исчезает между прогонами.

- **Согласование.** Пункты называются номерами из HTML-отчёта. Ответ принимается словами и
  пачкой по классу («все zlib/musl/busybox по диапазону — да»); «принимаю всё, кроме №…» —
  законный ответ. Решение записывается в `recommendations.json` (`decision`), поэтому отклонённый
  пункт виден следующей итерации, а не исчезает.
- **Что применяется.** Только пункты с решением `approve`: `status` и `detail`. Замечания
  («прочее») правкой не являются — они закрываются решением человека и остаются в отчёте
  рекомендаций.
- **Сверка после записи.** Результат сверяется с **исходным отчётом**, а не с копией
  промежуточного файла: сравнивать выход со входом этапа 2 — тавтология, такой гейт проходит
  всегда. Пары `(component, vuln_id)` должны существовать в исходнике, а `status` в результате —
  быть либо исходным, либо согласованным предложением. Иначе — ненулевой код выхода, файл
  результатом не считается.
- **Если рекомендаций нет** — этап 2 не запускается: промежуточный `_filtered.xlsx` и есть
  результат, у него уже исправлена орфография и убраны лишние строки.
- **Листов в итоговом файле не прибавляется.** Применённые правки и журнал этапа дописываются
  разделом «Этап 2 — итоговый отчёт» в HTML-отчёт этапа 1 и в `recommendations.json` (`stage2`);
  листов «Изменения» и «Журнал» в xlsx нет.
- **Пункт про группу строк к ячейке не применяется.** У ошибок разметки вместо номера строки
  стоит группа («1 стр.», «—»): такой пункт согласуется, но пропускается с причиной — эти строки
  правятся в отчёте вручную.

## Журнал операций

Строка журнала — `<шаг> — <действие> — <числовой результат>`:

```
оставляю только high и critical — удалено 0 из 463
проверяю орфографию — правлено 6 ячеек
статусы, id и purl не изменялись: предложения вынесены в recommendations.html
рекомендаций: статус 32, обоснование 21, замечания 118
этап 2: применено согласованных правок 20 из 171 предложения; отклонено 3
```

Журнал идёт в раздел «Журнал этапа» HTML-отчёта и коротким блоком в ответ человеку; листа
«Журнал» в xlsx нет — документ содержит только сам отчёт.

## `false_positive` или `not_affected`

Две корзины, а не вкусовое решение:

- **fp** — находка ошибочна по идентификации: CVE относится к другому продукту **или**
  поставленная версия вне затронутого диапазона (исправление пришло раньше поставленной версии).
- **na** — CVE относится ровно к поставленной версии, но уязвимая функциональность в продукте
  не задействована («не используется», «недостижим», «только 32-битная сборка»).

«Исправлено в 1.26.12» при поставленной 1.26.18 — это fp, хотя читается как «не затронут».
Основание «вне диапазона» сильнее «не используется»: если верны оба, статус fp.
Проверка по идентификатору и ловушки (пустой OSV для apk/deb, `1.3.1-r2` → `1.3.1.2`) —
`references/vex-status-fp-na.md`.

## Частые ошибки

- **Править статус в промежуточном файле.** Этап 1 статусы не трогает вовсе: `na → fp`
  по диапазону — рекомендация, иначе человек не увидит, что разметка изменилась.
- **Требовать одинакового обоснования у одной пары компонент+уязвимость.** Компонент может
  входить в разные модули и контейнеры, и причины там разные: расхождение текстов — не дефект.
- **Склеивать несколько отчётов в один результат.** Каждый файл — отдельный прогон, отдельные
  `_filtered`/HTML/спецификация. Несколько отчётов — сначала вопрос, какой берём.
- **Дописывать «не используется» в обоснование.** Тезис о неиспользуемости — ошибка разметки,
  а не основание: такие строки помечаются красным в разделе «Ошибки разметки», а в своих
  рекомендациях формулировки про неиспользуемость не предлагаются вообще.
- **Объявлять строку ошибкой из-за краткости текста.** Краткость сама по себе — не дефект;
  ошибка — именно тезис о неиспользуемости, а не длина фразы.
- **Подсветка и заливка в отчёте.** Их нет вообще: правки видны в разделе «Внесённые правки»
  HTML-отчёта, иначе файл читается как переписанный.
- **Сравнивать компоненты без контейнера.** Один purl в разных модулях — разные строки и разные
  причины; сводить их к одной формулировке или одному статусу нельзя.
- **Переносить расширение обоснований в промежуточный файл.** Промежуточный `_filtered` —
  это орфография и удаление строк; новые формулировки ждут согласования на этапе 2.
- **Собирать HTML руками или править его после прогона.** `recommendations.html` —
  производный файл: он перезаписывается каждым прогоном этапа 1.
- **Применять рекомендации «по очевидности».** Без `decision=approve` (или `--approve`)
  пункт остаётся предложением.
- **Брать первую строку за шапку.** В выгрузках над шапкой стоит служебная строка
  (`Column1…Column8`) или название таблицы; шапка ищется по совпадению имён колонок, а после
  удаления лишней строки номера остальных пересчитываются — иначе следующие удаления бьют
  не по тем строкам и мусор остаётся в файле.
- **Считать регулярку по «актуальна» вердиктом.** «Эксплуатация возможна только при…» —
  отрицание; такие строки подтверждает человек.
- **Закрывать строку по тексту разметки, не сверив версию с источником.** Текст разметки —
  утверждение автора отчёта, а не доказательство: 94 строки одного отчёта получили `na`
  при версии вне диапазона.
- **Считать ответ пустого поиска доказательством.** OSV по purl `pkg:apk/alpine/...` и
  `pkg:deb/debian/...` возвращает 0 на всё: истина в NVD.
- **Править purl или `id` «для красоты».** Даже верное по существу исправление рвёт связь
  отчёта со SBOM и сканером.
- **Править опечатку «на глаз» регуляркой.** Замена подставляется целым словом и проверяется
  чтением одной исправленной ячейки, а не счётом. Регулярка, которая «чинит пунктуацию», легко
  меняет смысл: замена `:\s*` на пробел удаляет само двоеточие. Если после правки текст надо
  перечитать и сравнить с исходным, это уже не орфография — это рекомендация.
- **Сверять результат с копией входа этапа 2.** Такой гейт верен тривиально: подменённый
  в копии статус не ловится. Сравнение идёт с исходным отчётом и с списком согласованных
  пунктов — тогда подмена видна.
- **Молча удалять дубли и спорные строки.** Удаление сверх правила 2 — только по согласованию.
- **Спрашивать «пришлите файл», не поискав его.** Отчёт лежит в шаренной папке хоста;
  вопрос человеку — только после кодов 3 или «кандидатов несколько».
- **Пропустить монтирование шары.** В этой среде `/mnt/hgfs` пуст после перезагрузки:
  `find_report.py` вернёт код 2, и шару надо поднять самому.
- **Взять `_filtered` или `_итоговый` за исходник.** Суффиксы `_filtered`/`_итоговый` — признак
  производного файла; вход — только файл из корня шары.
- **Оставлять оборванную формулировку и спрашивать «что имелось в виду».** Она дополняется
  по контексту, с записью в журнал.
- **Проверять правило на фикстуре, где purl лежит не в `component`.** `unreadable()` считает строку
  мусором, если `component` не начинается с `pkg:`: фикстура с компонентом вида `zlib@1.2.13-r1`
  даёт «нечитаемы все строки», и любая проверка подтверждает сама себя. В фикстуре purl кладут
  и в `purl`, и в `component`.
- **Оставлять в отчёте medium/low.** Выборка отчёта — только high и critical: после прогона
  лист сверяется со счётчиком удалённых, иначе часть строк вне области проверки остаётся.
- **Удалять строки «по привычке» без сверки.** Удаление — только по уровню опасности; суммы
  в журнале и число строк на листе должны сходиться.
- **Удалять нечитаемые строки по счётчику.** Нечитаемая строка остаётся в отчёте
  и описывается замечанием при любом количестве.
- **Запускать долгий прогон через `nohup … &`.** Долгий прогон (NVD на сотни CVE) запускается
  фоновым процессом инструмента, а не амперсандом в командной строке: оболочка возвращает ошибку,
  и прогон не стартует, хотя выглядит запущенным. У фонового прогона свои `--outdir` и `--workdir`,
  иначе он перезапишет готовый быстрый результат.
- **Считать первое число в тексте версией компонента.** Версия образа, соседнего пакета, адрес
  или номер протокола дают ложное замечание: версия в тексте учитывается только рядом с именем
  компонента и не совпадающая с версией продукта (иначе на большом отчёте получаются сотни лишних
  замечаний вместо десятков).
- **Копировать стиль таблицы без темы.** `TableStyleMedium7` зелен в теме образца (`accent6`
  `70AD47`) и оранжев в теме openpyxl по умолчанию (`F79646`): тему надо переносить вместе
  со стилем, иначе «цвет как в примере» не получается.
- **Давать в статистике число без списка.** Цифра «удалено 3» без раздела с этими тремя
  строками — непроверяемое утверждение: у каждого числа свой раздел со ссылкой с карточки.
- **Отдавать xlsx из csv без оформления.** csv не несёт оформления: вид берётся с образца
  (`пример` рядом с отчётом или `assets/report-template.xlsx`) — таблица со стилем, ширины,
  автофильтр; свой вид на глаз не выдумывается.
- **Дублировать пустое поле вторым пунктом.** Пустое `detail` уже есть в разделе «Пустые поля»:
  отдельной «правки обоснования» для него не создаётся.
- **Анализировать до перекодирования и оформления.** Сначала кодировка и образец, потом проверки:
  иначе счётчики и оформление считаются от разной разметки.
- **Читать csv только как utf-8.** Кириллица в выгрузке обычно в cp1251 или перекодирована дважды:
  сначала перебор кодировок и снятие мойибаке, потом разбор.
- **Писать результат поверх файла, открытого в Excel.** Рядом лежит замок `~$<имя>.xlsx`, запись
  падает `PermissionError`, хотя числа уже посчитаны: результат кладут в подкаталог `new/` рядом
  с заблокированным файлом и говорят об этом, а не перезапускают прогон, пока файл не отпустят.
- **Класть результаты рядом с исходником.** Место результатов — каталог `src-dep-check-report`.
- **Отдавать файл без журнала и без списка правок.** Человеку нужно видеть, что и на каком
  основании изменено, иначе отчёт не проверить: правки и журнал идут в HTML-отчёт, а не
  подсветкой и не отдельными листами в самом файле.

## Интерпретатор

`check_report.py`, `build_report.py`, `srcdep_lib.py` и `check_markup.py` пишут/читают xlsx через
openpyxl — запускать интерпретатором инструментов профиля
(`~/.hermes/tools/python-3.14*/bin/python3`). `find_report.py`, `src_dep_probe.py` и
`check_markup.py` в режиме чтения обходятся stdlib, но проще держать один интерпретатор:
системный `python3` падает с `ModuleNotFoundError: No module named 'openpyxl'`.
