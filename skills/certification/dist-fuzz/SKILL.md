# Проведение фаззинг-тестирования компонента (DIST.FUZZ)

Класс задач: нужно **самому** провести фаззинг компонента продукта и сдать материалы так,
чтобы проверка по 7 пунктам Методики ВУ дала «Соответствует». Проверяющая сторона — скилл
`dist-fuzz-check-report`: оттуда берутся текст требований, словарь вердиктов, скрипты подсчёта
и формат заключения. Здесь — как получить артефакты, которых эта проверка требует.

Правила, которые действуют всегда:

1. **Сначала готовые харнессы, потом свои.** Для крупных OSS-компонентов фаззинг обычно уже
   есть — в OSS-Fuzz, а не в репозитории продукта. Доработка существующего набора дешевле и
   правдоподобнее, чем кампания с нуля (`references/harness-discovery.md`).
2. **«Приемлемое качество на критичных участках» важнее максимума покрытия.** 6–8 целей,
   вход в которые доступен без аутентификации и содержит недоверенные данные. Формальные
   пункты считаются per-target, поэтому расширение списка целей их не улучшает.
3. **Каждый пункт закрывается артефактом, а не текстом.** Отчёт без таблицы триажа,
   без покрытия по каждой цели и без зафиксированных параметров сборки проверку не пройдёт,
   сколько бы часов ни шёл фаззинг.
4. **Этапность.** Этап 1 — анализ входных данных и предложение подхода; следующие этапы —
   только по подтверждению пользователя. Ответы на вопросы и принятые допущения ложатся в
   `output/brief.md`, чтобы этапы 2–4 не переспрашивали.
5. **Качество важнее скорости.** Кампания считается запущенной не тогда, когда контейнер
   стартовал, а когда она пережила аварийный выход и перезапуск: фаззер по умолчанию
   останавливается на первой находке или зависании (`references/jvm-jazzer-campaign.md`,
   раздел «Управление длинным прогоном»). Статус докладывается числами из журналов (cov, ft,
   плато, exit-код), а не «всё идёт»; при сомнении — перепроверить, а не доложить.

## When to Use

- Нужно провести фаззинг компонента (Java/JVM, C/C++, JS/TS) и сдать материалы по Методике ВУ.
- Надо решить, что фаззить, на чём и как уложиться в диск/время/CPU.
- Нужно понять, каких артефактов не хватает до начала кампании, а не после.
- Не для: проверки чужих материалов (это `dist-fuzz-check-report`); не для HTTP-фаззинга
  веб-приложения как самостоятельной задачи (там другой инструментарий и другие артефакты).

## Порядок работы

1. **Бриф.** Скиллы `task-clarification` + `interview`: карточка `clarify`, рекомендуемый
   вариант первым. Слоты, которые реально меняют результат: уровень фаззинга (in-process
   харнессы vs внешний HTTP), состав целей, **где вести кампанию — локально или на отдельной
   ВМ** (раздел «Где вести кампанию» ниже), бюджет времени на кампании, форма отчётных
   документов. Пропущенный вопрос = рекомендованный вариант, и это называется вслух.
   *Готово, когда* ответы и допущения записаны в `output/brief.md`.

2. **Требования → артефакты.** Взять 7 пунктов из скилла проверки (файл требований внутри
   `dist-fuzz-check-report`) и выписать для каждого: какой файл его докажет. Для JVM сразу
   зафиксировать формулировку по п. 1 (`references/jvm-jazzer-campaign.md`) — иначе потом
   переписывать отчёт.

3. **Инвентаризация наработок компонента** — `references/harness-discovery.md`. Дерево
   репозитория на нужном теге через GitHub API без клонирования; затем OSS-Fuzz-проект и,
   для JVM, `cncf/cncf-fuzzing`. Фиксируется: сколько харнессов, у каких есть seeds и словари,
   когда харнессы правились последний раз (это оценка риска дрейфа API). Тут же — аудит
   достижимости: найденный харнесс может быть мёртвым (моки вычерпывают буфер, тестируемый
   документ всегда пустой). Проверка и лечение — раздел «Проверка, что харнесс доходит до
   кода» того же файла; мёртвую цель дешевле отбросить, чем фаззить сутки.

4. **Изолированное окружение.** Контейнер (Docker Engine) с фиксированными версиями и
   смонтированными каталогами `/src`, `/out`, `/corpus`; кампании — с `--network none`.
   Где он работает — на рабочей машине или на отдельной ВМ — решается в брифе (раздел
   «Где вести кампанию»); от этого зависят только способ наблюдения и передача материалов,
   а структура каталогов и скрипты остаются одинаковыми.
   Проверить до установки: `/dev/kvm`, свободное место (`df`), RAM, наличие JDK/Maven.
   Вложенные ВМ и Docker Desktop требуют KVM; Linux-контейнеры работают на общем ядре —
   это ограничение фиксируется в отчёте, а не замалчивается.

5. **Сборка.** Образ: базовый JDK + Maven + фаззер фиксированной версии; в материалы идут
   Dockerfile, digest образа, лог сборки и хеши артефактов. Сборочный скрипт компонента
   берётся из OSS-Fuzz-проекта; обёртки фаззера правятся (убрать установку JDK и проверку
   «ровно openjdk 17» — внутри образа это падает).
   *Готово, когда* каждая выбранная цель компилируется и запускается на пустом входе.

6. **Корпуса и словари (п. 2).** Экспертным способом из тестовых ресурсов самого продукта
   (`*/src/test/resources`): это документируемое происхождение, а не «продукт фаззера».
   ≥5 образцов на цель, на каждую цель — описание принципов формирования; готовые словари
   из OSS-Fuzz-проекта переиспользуются. Если вход харнесса — не файл из репозитория
   (компактный JWS/JWT, JWK-JSON, URI, WebAuthn-JSON), образцы генерируются скриптом под
   контракт `fuzzerTestOneInput`: несколько вариантов структур/алгоритмов плюс заведомо
   битые. Провенанс каждого файла (target, имя, sha256, размер, источник) свести в
   `seeds-manifest.tsv` — это приложение к пп. 2 и 7. До кампании прогнать seeds через
   `CorpusRunner`: строка `files=N ok=N exceptions=0` — единственное доказательство, что
   харнесс работает, а не только компилируется.

7. **Кампании (пп. 4–6).** Длительность ≥ плато 2 ч + время выхода на плато (на практике
   4–5 ч на цель), параллелизм по CPU/RAM. Лог — построчно с таймстампами, иначе плато
   не доказывается. Параметры и разбор метрик — `references/jvm-jazzer-campaign.md`.

   **Плато — это сигнал остановки, а не только отчётная цифра.** Как только у цели плато
   достигло 2 ч (нет прироста `cov`), держать её дальше бессмысленно: бюджета на ней уже не
   вернуть, а ядро занято. Цель останавливают и переходят к следующей, где прогресс
   вероятнее. Реализация в queue-runner: `PLATEAU_STOP=7200` (секунды), в цикле ожидания
   контейнера вместо слепого `docker wait` — опрос `plateau.py` раз в минуту; при достижении
   порога `touch targets/<T>/plateau_stop`, `docker stop`, и супервизор выходит из цикла,
   не перезапуская цель (иначе `docker stop` выглядит как аварийный выход и цель поднимается
   снова). В журнале очереди — строка `target <T> завершена по плато Ns (п. 6 выполнен)`.
   Цели, не набравшие плато, продолжают работать до бюджета — именно они и дают ретрай.
   Ретрай включать только по исправленному расчёту плато: старая версия `plateau.py`
   считала от пробных прогонов и выдавала `0s`, из-за чего в повторный 4,5-часовой прогон
   попадала цель с плато 5,7 ч.

8. **Структурное покрытие (п. 7).** Отдельный прогон корпуса под инструментом покрытия
   (JaCoCo для JVM, lcov/gcov для C/C++), два среза: стартовые seeds (заодно даёт п. 5«б»)
   и финальный корпус. Отчёт — HTML + XML по каждой цели, сводка по файлам.

9. **Триаж (п. 3).** Дедупликация находок по стек-хешу, классификация (реальная ошибка /
   срабатывание детектора / OOM / StackOverflow / ожидаемое исключение), воспроизведение:
   сначала в режиме регрессии фаззера, затем вне фаззера — тем же раннером корпуса без агента.
   Таблица триажа и протокол прогонов обязательны **даже при нуле находок**.

   **Воспроизведение вне фаззера — через функцию продукта, а не только раннером корпуса.**
   Раннер повторяет вход тем же путём, что харнесс, и доказывает лишь устойчивость находки к
   перезапуску. Актуальность (то, что требует п. 3) устанавливается двумя шагами: путь от
   сетевой точки входа до места дефекта с проверкой, где стоит разбор относительно
   аутентификации и проверок, и прогон того же входа через функцию, которую вызывает эндпоинт,
   в образе сборки с `--network none`. Развёрнутый стенд для этого не нужен; рецепт, разбор
   модели нарушителя и формулировки для отчёта — `references/finding-actuality.md`.

   **Критерий завершения закрывается любым из подпунктов п. 5.** «а» — пути (или `cov`, `ft`)
   ≥ 2× seeds; «б» — финальное покрытие ≥ 2× стартового (снятого на seeds). Если «б» не
   достигается (типично при богатом стартовом корпусе), остановка по «а» допустима и
   считается выполнением требования: в отчёте вердикт формулируется «Соответствует по «а»;
   «б» не подтверждено» и красится сиреневым, а не зелёным. Добиваться «б» во что бы то ни
   стало не нужно — это лишние часы на цель, у которой кратность по «а» уже двузначная.

   **Контроль статуса кампаний** (особенно когда прогон идёт на другой машине):
   один скрипт читает `docker logs -t` каждой цели и пишет три файла — `status.json`
   (машинно-читаемый), `status.md` (таблица для чата и отчёта) и `status.html` (страница).
   Поля: seeds, cov, ft, cov/seeds, exec/s, плато в часах, число находок, вердикт по пп. 5–6
   («ИДЁТ, плато 1.4 ч, до критерия 0.6 ч» → «ЗАВЕРШЕНА, п. 6 выполнен»). Плато считать
   от таймстампа последнего **прироста** cov и от **глобального максимума** cov за все
   отрезки (в таблице — максимум, а не значение последней строки). Плато отсчитывается
   не раньше отметки старта кампании: queue-runner при запуске волны пишет время в
   `targets/<T>/campaign_start`, и расчёт берёт максимум из (последний прирост cov, старт
   кампании). Без этой отметки пробные 45–60-секундные прогоны, сделанные до кампании,
   дают «плато 8 ч» у цели, которая реально работает второй час, — цифра в отчёт не годится.
   Опорная точка для
   «сейчас»: текущее время, если журнал свежий; последняя строка журнала — если прогон
   завершён. У работающей цели `log.txt` дописывается только при остановке отрезка, и
   плато от последней строки не наберётся никогда; у завершённой — наоборот, от текущего
   времени оно растёт бесконечно. На удалённой ВМ
   скрипт ставится в cron каждые 10 минут и складывает файлы в общий каталог, который видит
   заказчик; локально те же файлы пересобираются после `rsync` каждой волны — заказчик видит
   и ход прогона, и момент, когда критерий выполнен. Журнал цели — append-only (`>>`), снимок
   пишется в отдельный `live.txt`: перезапись `>` в момент перезапуска контейнера стирает
   историю и обесценивает плато.

   В статусе два признака считаются по последней строке, а не по факту наличия строки:
   завершённость сбрасывается любой более поздней строкой прогресса (иначе `DONE` от
   пробного прогона помечает работающую цель «ЗАВЕРШЕНА, п. 6 не выполнен»), а прогоны
   короче часа подписываются «пробный прогон N с (не кампания)» — заказчик не должен
   читать smoke-проверку харнесса как провал критерия плато.

   **Сам агент** следит тремя механизмами, и они не заменяют друг друга: (1) cron-задача
   Hermes с `monitor`-скриптом раз в 30 минут — агент просыпается только при изменении
   состояния; (2) background-процесс `ssh 'docker wait …'` на каждую волну — даёт живое
   уведомление в момент завершения контейнеров; (3) queue-runner на самой ВМ — запускает
   следующую тройку целей без участия агента. Без (3) длинный прогон останавливается на
   границе волны, а без (2) cron-выдача на Desktop-клиенте не приходит live: она появляется
   только при следующем обращении к чату.

10. **Отчёт и самопроверка.** Отчёт разработчика (объект, методика, цели, параметры сборки,
    корпуса, результаты по целям, находки/триаж, покрытие, вывод) + таблица самопроверки
    по 7 пунктам в формате заключения. До сдачи прогнать по своему архиву скрипты
    `dist-fuzz-check-report` (`fuzz_artifact_inventory.py`, `coverage_info_summary.py`,
    `verify_deliverables.py`, `md_report_to_html.py`) и добиться «Соответствует» по всем пунктам.

    **Комплект должен быть прослеживаемым, а не только полным.** К отчёту прикладывается
    `evidence/build/INDEX.md` (сборка, харнессы с хешами, метрики по целям, покрытие, что и
    почему удалено), `SHA256SUMS` + `verify.sh` (проверка целостности одной командой),
    `corpora-digests.txt` (дайджест каждого корпуса). В самом отчёте — приложение
    «Прослеживаемость требований» (пункт → файл → раздел) и приложение «Состав и целостность»
    (каталоги, файлы, объёмы, команда проверки). Последний шаг перед сдачей — скрипт сверки:
    он парсит таблицы отчёта и сравнивает с `INDEX.md`, `SHA256SUMS` и манифестом коллекций.
    Числа в тексте правятся руками и расходятся молча. Рецепт — `references/evidence-package.md`.

    **Поставка — один архив в одной папке.** Пути в отчёте — текстом и относительно корня
    комплекта (отчёт рядом с `evidence/build/`), а не кликабельные ссылки: заказчик ищет файл
    по пути в архиве. Лишние папки-двойники с тем же комплектом на шаре удаляются, но сначала
    их файлы сверяются по SHA-256 с локальной копией — иначе вместе с дублем уходит
    единственный экземпляр рабочего документа.

    **Защита отчёта перед заказчиком — по одному вопросу за раз.** Замечания разбираются
    последовательно, и ответ на очередной вопрос начинается с проверки по коду и артефактам
    (прогон, поиск вызовов, разбор пути), а не с пересказа отчёта и не с правки текста.
    Правки в сданный отчёт вносить после согласования: вердикты и числа сверяются с предыдущей версией, и молчаливая переделка ломает эту сверку. Согласованное решение переносится в документ в том же цикле — вердикт пункта, подраздел с путями `файл:строка` и цифрами прогона, переклассификация строк триажа, доказательства в `evidence/build/proofs/` и пересборка HTML, — а не остаётся в переписке: заказчик читает отчёт, а не историю чата.

11. **Устранение — после подтверждения актуальности, а не вместо неё.** Три проверки по
    порядку: исправлено ли в апстриме и в какой версии; есть ли фикс в ветке, на которой
    стоит продукт (пин на минорную версию означает, что фикс в новой минорной ничего не даёт);
    закрывается ли вектор конфигурацией без смены версии. Каждый ответ — по коду и данным:
    сверка файла по тегам вместо чтения release notes, проверка регистрации провайдера/фичи
    в исходниках, проверка по журналу ingress, что уязвимая поверхность продуктом вообще
    используется. Результат — раздел «Устранение» в отчёте: CVE и версия с фиксом, минимальный
    diff для бэкпорта, таблица мер (что даёт / остаточный риск / статус), порядок действий.
    Рецепты и грабли — `references/remediation-assessment.md`.


## Где вести кампанию: локально или на отдельной ВМ

Место прогона — вопрос брифа, а не догадка агента: варианты различаются ресурсами, изоляцией
и способом наблюдения. Вопрос задаётся вместе с остальными слотами, ответ и параметры машины
записываются в `output/brief.md`.

| Критерий | Локально (рабочая машина) | Отдельная ВМ |
|---|---|---|
| Ресурсы | хватает RAM и диска на образ, корпуса и журналы (ориентир: ≥8 ГиБ RAM, ≥30 ГБ свободно на цель-волну) | машина выделена под кампанию, ресурсы не делятся с рабочей средой |
| Изоляция | кампания занимает CPU и диск, пока идёт; риск для текущей работы | рабочая машина свободна, прогон переживает закрытие сессии |
| Доступ к продукту | нужен только исходящий доступ к сети и образу | нужны SSH-доступ и способ копировать материалы (rsync/scp) |
| Наблюдение | статус-файлы и сторож запускаются в фоне на той же машине | queue-runner и cron остаются на ВМ, сторож — с локальной машины |
| Передача материалов | архив собирается на месте | архив собирается на ВМ и копируется одним файлом |

Правила выбора:

- Если на рабочей машине меньше ~8 ГиБ RAM или на диске нет ~30 ГБ свободно, рекомендуемый
  вариант — отдельная ВМ; иначе локально. Рекомендация называется вслух, выбор делает человек.
- В брифе фиксируются: адрес и ОС машины, число CPU, RAM, свободный диск, кто владелец, как
  передаются материалы и как забирать статус.
- **Реквизиты доступа в скилле не хранятся.** Адреса, логины, ключи и пароли запрашиваются
  у пользователя в сессии и передаются через хранилище секретов (`browser_vault` или
  эквивалент), а не текстом в чате; в материалы проверки они не попадают.
- Локальный вариант: контейнеры Docker, журналы и корпуса в рабочем каталоге проекта,
  длинные прогоны — через background-процесс или `tmux`, чтобы закрытие чата их не убивало.
- Удалённый вариант: SSH-ключ только для этой задачи, `rsync` в обе стороны, queue-runner и
  cron на ВМ, сторож `scripts/campaign-watch.sh` — с локальной машины; каталоги те же, что
  локально, поэтому скрипты статуса работают без правок.
- Кампания нагружает CPU на всё время прогона: при 1 доступном CPU цели запускаются
  последовательно, а не «в параллель ради скорости».

## Pitfalls (кратко)

Полный разбор 35 пунктов — `references/pitfalls.md`: симптом, причина, лечение. Здесь —
те, на которых теряют часы чаще всего.

- **Харнессы ищут в репозитории компонента и не находят.** Для Java они живут в
  `cncf/cncf-fuzzing`, сборка — в `google/oss-fuzz`; пустой поиск по дереву значит
  «здесь харнессов нет», а не «фаззинга нет».
- **Харнесс может быть мёртвым:** компилируется, крутится, даёт «0 находок», а моки
  вычерпывают буфер до тестируемого документа. Признак — десятки инструкций покрытия,
  а не сотни.
- **Собственный раннер ввода даёт ложные цифры покрытия.** Jazzer читает целые с конца
  буфера, строки — с начала; упрощённый раннер обнуляет все ранее снятые срезы.
- **Фаззер останавливается на первой находке и первом зависании.** Нужны
  `--keep_going=N` и супервизор с перезапуском, иначе 4,5-часовой прогон кончается
  за минуту.
- **`docker run` без `-t` теряет хвост журнала:** JVM буферизует stdout, и стек
  находки пропадает. Журнал писать в файл при остановке сегмента.
- **Плато считается по глобальному максимуму `cov`, а не по последней строке** —
  перезапуск обнуляет счётчики и выдаёт ложный «рост».
- **Число артефактов — не число дефектов.** Считать уникальные `DEDUP_TOKEN`;
  `slow-unit-*` — не находка.
- **Плато 2 ч — сигнал остановки,** а не повод досиживать бюджет.
- **Журнал XML-цели вырастает до гигабайт** (диагностика парсера на каждый вход):
  статус считать по хвосту, а не по всему файлу.
- **Корпус, собранный самим фаззером, п. 2 не закрывает:** проверяется стартовый
  корпус и принципы его формирования.
- **Шара vmhgfs — холодный склад:** дерево мелких файлов копируется часами, передавать
  одним архивом (`references/evidence-package.md`).
- **Успешность цели — три условия** (доходит до кода, есть прирост покрытия, исполняется
  целевая логика), и кратность покрытия не главное из них.
