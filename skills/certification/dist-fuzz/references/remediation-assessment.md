# Устранение находки: CVE, версия с исправлением, конфигурационные меры

Когда актуальность подтверждена (`references/finding-actuality.md`), следующий вопрос
заказчика всегда один и тот же: «что с этим делать». Ответ состоит из трёх независимых
проверок — исправлено ли в апстриме, исправлена ли та ветка, на которой стоит продукт, и
можно ли закрыть вектор без смены версии. Отвечать по документации нельзя: release notes
перечисляют issue, но не говорят, попал ли фикс в нужную ветку.

## 1. Сопоставление с CVE

```bash
curl -sS -H "Accept: application/vnd.github+json" \
  "https://api.github.com/advisories?cve_id=CVE-XXXX-YYYY" | python3 -c "
import json,sys; a=json.load(sys.stdin)[0]
print(a['ghsa_id'], a['severity'], a['cvss']['score'])
for v in a['vulnerabilities']:
    print(v['package']['name'], '| уязвимы', v['vulnerable_version_range'], '| патч', v['first_patched_version'])"
```

- Совпадение механизма (для CPU-цикла — «high CPU usage and worker thread starvation»)
  означает, что находка уже опубликована: в отчёте она называется по CVE, и это же
  подтверждает её значимость.
- CVE нет — значит находка новая; так и писать, без ссылок «возможно, это CVE-…».
- `first_patched_version` из GHSA — только начало проверки, дальше обязательна сверка кода.

## 2. Версия с исправлением — сверкой кода по тегам

Release notes дают подсказку (искать в теле релиза слова про компонент и «denial»), решение
даёт сравнение файлов:

```bash
U=https://raw.githubusercontent.com/<org>/<repo>
F=path/to/Fixed.java
for t in <текущая> <следующая-минорная> <патч-релизы> <последняя> main; do
  printf "%-8s %s\n" $t "$(curl -sS -m 25 \"$U/$t/$F\" | grep -c '<строка из исправления>')"
done
```

Строка-маркер — та, которой в уязвимой версии нет (например, ветка `else` с
`throw ... "Unexpected XML Event Type"`). Перебор тегов даёт точный патч-релиз: у соседних
номеров 0 и 4 совпадения — граница между ними.

**Ветку продукта проверять отдельно.** Продукт обычно пинит минорную версию, и исправление
в новой минорной ничего не значит: перебрать все патч-релизы той ветки, на которой он стоит.
Если там код не менялся — писать прямо: «в ветке X исправления нет», остаться на ней без
собственного патча нельзя. Это отдельный вывод и отдельная рекомендация.

Минимальный diff для бэкпорта получается вырезанием функции по тегам:

```bash
for t in <уязвимая> <исправленная>; do
  curl -sS "$U/$t/$F" | awk '/public static .* parseX\(/,/^    }$/' > fn_$t.txt
done
diff fn_<уязвимая>.txt fn_<исправленная>.txt
```

## 3. Закрывается ли конфигурацией

Проверять по исходникам, а не по документации.

- **Есть ли фича/флаг для отключения поверхности.** `grep -rn "<ПРОТОКОЛ>" --include=Profile.java .`
  и `META-INF/services/<...>LoginProtocolFactory`: если фабрика зарегистрирована безусловно,
  путь обслуживается для любого арендатора и «выключить провайдер в realm» не сработает.
- **Настройки пула и очереди** — в `quarkus/config-api/.../HttpOptions.java`:
  `http-pool-max-threads` по умолчанию `max(4·число CPU, 50)` (это и объясняет наблюдаемый
  порог: при лимите 1 ядро — ровно 50); `http-max-queued-requests` превращает ожидание в 503.
  Обе — полумеры: порог растёт линейно с числом запросов, а каждый зависший поток продолжает
  занимать ядро.
- **Пробы `liveness`/`readiness`** — не защита, а авто-восстановление: без них отказ живёт
  до ручного перезапуска.

Вывод формулируется как «конфигурацией эта версия не закрывается; единственная мера без
смены образа — блокировка пути на входном прокси».

## 4. Доказать, что поверхность продуктом не используется

Блокировку можно предлагать только с этим доказательством. Журнал ingress за сутки:

```bash
kubectl -n <ingress-ns> logs <ingress-pod> --since=24h > /tmp/ing.log
grep -E "^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+ - - \[" /tmp/ing.log > /tmp/acc.log   # ТОЛЬКО access-строки
grep "<путь>" /tmp/acc.log | sed -E 's/.*" "([^"]*)".*/\1/' | cut -c1-45 | sort | uniq -c | sort -rn
grep "<другой-путь>" /tmp/acc.log | sed -E 's/.*" "([^"]*)".*/\1/' | cut -c1-45 | sort | uniq -c | sort -rn | head
```

- **Грабли: nginx пишет error-строки в тот же поток.** Наивный `grep <путь> | grep -v curl`
  считает `upstream timed out` и прочие ошибки как «обращения продукта» и даёт десятки
  несуществующих запросов. Фильтр по формату access-строки (`^<IP> - - [`) обязателен,
  иначе вывод «продукт использует поверхность» будет ложным.
- Признак использования — регулярный трафик с осмысленными агентами (бэкенд продукта,
  браузеры) и коды 200/302; собственные тестовые `curl` из подсчёта вычитаются.
- Сопоставить с описанием архитектуры продукта (какой протокол заявлен) — совпадение
  укрепляет вывод, расхождение означает, что смотреть надо внимательнее.

## 5. Блокировка пути на nginx-ingress

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/server-snippet: |
      if ($request_uri ~ "^/realms/[^/]+/protocol/saml") { return 404; }
```

Правило проверяется на тестовом контуре (в частности, что OIDC-пути не задеты) и
согласуется: это изменение общего ingress, а не пода. Признак успеха — те же запросы
получают 404, а интерактивный вход и token endpoint работают.

## 6. Что попадает в отчёт

Раздел «Устранение» в конце отчёта:

1. **Апстрим:** CVE/GHSA, severity, диапазон уязвимых версий, версия с исправлением,
   отдельной строкой — есть ли фикс в ветке продукта.
2. **Минимальный diff** исправления (для бэкпорта, если обновление заблокировано).
3. **Таблица мер:** мера | что даёт | остаточный риск | статус. Полумеры называются
   полумерами, а не альтернативами.
4. **Рекомендация по порядку:** временная мера, которая снимает вектор сейчас; обновление как
   штатный путь; пробы как страховка от повторения.

Формулировки держать проверяемыми: «уязвимы < X», «исправлено в X», «в ветке Y исправления
нет», «за сутки обращений к пути от продукта — 0».
