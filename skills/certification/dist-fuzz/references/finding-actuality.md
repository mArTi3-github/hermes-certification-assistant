# Актуальность находки: код + повтор через функцию продукта

П. 3 требует «проверки воспроизведения фактов в штатном режиме». Развёрнутый стенд для
этого не нужен, если есть три вещи: путь от сетевой точки входа до дефекта, прогон того же
входа через функцию, которую вызывает эндпоинт продукта, и заявленная модель нарушителя.

Почему без этого нельзя: фаззер вызывает классы напрямую, харнесс строит собственное
окружение (свои фабрики парсеров, моки, TLS-контекст). «Найдено в харнессе» и «достижимо в
продукте» — разные утверждения, и проверяющий различает их первым же вопросом.

## Шаг 1. Путь от точки входа до дефекта

1. Найти точки входа, где недоверенные данные приходят без аутентификации:
   `grep -rn "@Path\|@POST\|@GET"` по ресурсам + `grep` по регистрации эндпоинтов
   (`createProtocolEndpoint`, сервлеты, фильтры).
2. Идти вниз по вызовам до места дефекта и на каждом шаге отмечать: нужна ли аутентификация,
   есть ли проверка типа/схемы/размера, какой парсер используется.
3. Отдельно зафиксировать **порядок**: разбор до проверки или после. Если документ
   разбирается до поиска клиента (типично для федеративных протоколов: SAML, WS-Fed,
   OpenID Connect request object), то ни настроенные клиенты, ни вход не нужны — этого
   одного факта достаточно, чтобы снять возражение «без стенда не проверить».
4. Идентификатор арендатора (realm/tenant/аккаунт) брать из URL страницы входа — он не
   аутентифицируемый секрет; HTTPS-терминация в продукте обычно уже есть.

## Шаг 2. Прогон через функцию продукта

Пишется класс на 15–20 строк, который вызывает ровно ту функцию, что и эндпоинт (не
класс-парсер напрямую), и три входа:

- **находка** — минимизированный вход из `crashes/`/`hangs/` или собранный по механизму дефекта;
- **контроль** — заведомо корректный документ того же формата: доказывает, что цепочка и
  classpath рабочие, и что зависание не от сломанного окружения;
- **проверка защиты** — тот же документ с запрещённой конструкцией (внешняя DTD, глубокая
  вложенность, внешняя ссылка): показывает, отказывает ли продукт и как быстро.

Пример для SAML-эндпоинта Keycloak (для другого продукта — та же функция, что вызывает эндпоинт):

```java
String b64 = new String(Files.readAllBytes(Paths.get(args[0])), "UTF-8").trim();
long t0 = System.currentTimeMillis();
try { org.keycloak.saml.SAMLRequestParser.parseRequestPostBinding(b64); }
catch (Throwable t) { System.out.println("ERR " + t.getClass().getName() + ": " + t.getMessage()); }
System.out.println("MS=" + (System.currentTimeMillis() - t0));
```

Запуск — в том же образе сборки, офлайн, с жёстким таймаутом:

```bash
docker run --rm --network none -v $BUILD:/out -v $DIR:/work -w /work <образ-сборки>:<тег> \
  bash /work/reach.sh    # javac -cp /out/classes:/out/jars/*:/out/fuzzer-dependencies/*
                       # timeout 30 java -cp /work:$CP Reach <base64-файл>
```

Чтение результата:

- exit 124 / нет вывода за 30 с — **воспроизведено** на функции продукта;
- отказ за единицы–сотни миллисекунд с сообщением защиты (`DOCTYPE is disallowed`) —
  **не воспроизведено**, механизм закрыт в продукте;
- контроль разобрался за сотни миллисекунд — цепочка рабочая.

Формулировать результат как «повтор на функции продукта `X.method()`», а не «сервис завис»:
прогон доказывает достижимость кода и поведение разбора, но не состояние процесса.

## Шаг 3. Модель нарушителя

Заявленная модель (её надо брать из брифа, а не придумывать) — только сетевой доступ, без
локального доступа и SSH. Классификация каждой находки:

| Путь | Классификация |
|---|---|
| Без аутентификации, снаружи | Актуально |
| Нужен admin API / токен динамической регистрации / preview-функция | Неактуально для модели; назвать условие включения |
| Только библиотечный API, не подключённый в сборке продукта | Неактуально; указать, что поверхность не используется |
| Требует локального файла/переменной окружения/SSH | Неактуально по условию задачи |

Последствие классифицируется отдельно: 500 на собственный запрос ≠ отказ сервиса ≠ RCE.
«Неактуально» — это не «нет дефекта»: дефект в коде остаётся, но в модель нарушителя не
попадает, и в отчёте он остаётся строкой с причиной, а не исчезает.

## Шаг 4. Что попадает в отчёт

Таблица: находка → путь (файл:строка на каждом шаге) → где разбор относительно проверок →
что показал прогон (вход, время, результат) → классификация.

Счётчики артефактов не пересчитываются в меньшую сторону: меняется классификация.
Пример масштаба: 4 766 срабатываний SSRF-детектора = 0 дефектов продукта (артефакт обвязки),
729 зависаний = 1 дефект (тот же цикл). Строка «N артефактов» и строка «M дефектов» живут
рядом и противоречием не являются.

Вердикт п. 3 при таком протоколе — «Соответствует»; единственное, что остаётся в замечаниях,
— ограничение области (например, HTTP-фаззинг серверной части не выполнялся), если оно есть.

## Когда стенд всё-таки нужен

Код не отвечает на три вопроса, и все три закрываются тремя запросами без аутентификации,
а не полноценным стендом: опубликован ли эндпоинт наружу (400 «invalid request» против 404
от reverse-proxy), подтверждается ли имя арендатора, уходит ли процесс в 100 % CPU на
зависшем входе. Предлагать стенд как единственный путь — переоценка задачи.

### Минимальный набор доступа

Если заказчик предлагает стенд, запрашивать ровно три вещи и назвать, чего не нужно:

| Нужно | Зачем |
|---|---|
| HTTPS-адрес сервиса (или ссылка на страницу входа) | точка входа и терминация TLS |
| имя арендатора (realm/tenant) | видно из URL страницы входа; не секрет |
| подтверждение сетевого пути (VPN/маршрут/разрешение в МЭ) | без него проверка не начнётся |

**Не нужны:** учётные данные и SSH. Эндпоинт, разбирающий документ до проверки клиента,
неаутентифицируемый — логин не добавляет ничего к проверке. SSH нужен только для одного
действия: `jcmd <pid> Thread.print` в момент зависания, чтобы в стеке был кадр цикла
(`SAML11ParserUtil.parseSAML11SubjectConfirmation`) — это переводит вывод из «curl не
ответил» в «поток крутится», но для отчёта достаточно и первого, если код уже проверен.

**Если имя арендатора неизвестно** (заказчик дал только адрес), его находят перебором
`.well-known`: провайдер не публикует список арендаторов, но отвечает 200 для существующего
и 404 для несуществующего — `https://<host>/<tenant-path>/<r>/.well-known/openid-configuration`
(у Keycloak `<tenant-path>` = `realms`; у других продуктов путь свой, его видно в ссылках
страницы входа). Практика: служебный арендатор (`master`, `admin`, `default`) обычно
существует всегда и служит индикатором, что перед вами не прокси; имя продуктового
арендатора угадывается по имени хоста и названию продукта (`<product>`, `<product>-dev`,
`<org>-<product>`); 15–20 кандидатов перебираются за минуту. Подтверждение — `issuer` в
`.well-known` и заголовок страницы входа (`Sign in to <tenant>`).

Протокол — три запроса:

1. `GET /realms/<realm>/protocol/<proto>` без параметров → 400 «invalid request»: эндпоинт
   опубликован. 404 — эндпоинт срезан прокси, и находка в этой поставке недостижима (тоже
   результат, его и писать).
2. `POST` с минимизированным входом, `curl --max-time 10` → клиент обрывает по таймауту.
3. Контрольный корректный документ → быстрый 400, затем повторный `GET` → сервис жив:
   зависает обработка одного запроса, а не весь процесс.

**Предупредить о влиянии до запуска — оно не заканчивается с таймаутом клиента.** Зависание
на CPU-цикле (`while (hasNext()) { peek() }` без ввода-вывода) не снимается обрывом
соединения: поток остаётся занятым, ядро крутится, и восстановление возможно только
перезапуском контейнера/пода. Поэтому согласие берут до запуска, команду восстановления
называют заранее, отправляют один запрос (максимум два), без параллельности, и проверяют
стенд после: медиана времени отклика до атаки и через несколько минут (0,34 → 0,53 с в
замере на живом стенде, эффект держался 4,5 минуты при живом сервисе). В отчёт идёт строка
«требуется перезапуск компонента»; в журналах останутся записи `INVALID_REQUEST` — сказать
о них заранее, чтобы их не приняли за инцидент.

Восстановление для заказчика (он должен суметь починить сам): перезапуск контейнера сервиса
или `rollout restart` деплоймента, затем контрольный `GET` эндпоинта — отклик должен
вернуться к исходным ~0,3 с. Если реплик несколько, залипла только та, что приняла запрос.

Если доступа к процессу нет, влияние измеряется снаружи: серия `GET` до и после, медиана
времени отклика, плюс контрольный запрос, который остаётся быстрым. Утверждение «ядро в
100 % и поток висит в цикле» при этом остаётся выводом из кода — так и писать, а не
выдавать за измерение.

## Границы отказа: исчерпание пула обработчиков

«Один запрос вешает поток» и «полный отказ» — разные утверждения. Второе измеряется, а не
предполагается: каждый вход занимает рабочий поток навсегда, потоков в пуле фиксированное
число, отказ наступает при их исчерпании.

Порядок измерения (Kubernetes; приёмы переносятся на docker):

1. Счётчик занятых обработчиков — число потоков в цикле:
   `kubectl -n <ns> exec <pod> -- jcmd 1 Thread.print | grep -c <метод из стека>`.
2. Наращивать ступенями (+1, +2, +4, +8, затем +30/+40), после каждой мерять не только
   целевой эндпоинт, но и заведомо блокирующие: token endpoint и
   `.well-known/openid-configuration`. Пока они отвечают — отказа нет, даже если время
   отклика выросло.
3. Зафиксировать порог. Размер пула не угадывается, а берётся из исходников: в Keycloak это
   `http-pool-max-threads` со значением по умолчанию `max(4·число CPU, 50)`
   (`quarkus/config-api/…/HttpOptions.java`), поэтому при лимите пода в 1 ядро порог ровно 50,
   а при 48 ядрах — 192. На пороге все блокирующие эндпоинты дают таймаут, а новые запросы
   встают в очередь и счётчик перестаёт расти — это признак исчерпания пула, а не «атака
   усилилась».
4. `kubectl top pod` (millicores) показывает, что при лимите 1 ядро один зависший поток уже
   занимает квоту целиком (985–1001m): деградация начинается с первого запроса, отказ —
   при исчерпании пула.

Что делает отказ устойчивым и что проверять в поставке:

- **Проб нет — восстановления нет.** `kubectl get pod <p> -o jsonpath='{.spec.containers[0].livenessProbe}'`
  с пустым ответом означает, что Kubernetes не видит недееспособность процесса: зависшие
  потоки живут до ручного перезапуска (наблюдалось 1,5 ч для одного потока и полный отказ
  без изменений 2,5 мин). Проба превращает отказ в самовосстанавливающийся ценой
  перезапуска — это рекомендация разработчику, её место в отчёте.
- **Всплеск не обязателен.** Потоки не освобождаются, поэтому 50 запросов можно растянуть
  по времени (по одному в минуту): защита от флуда не срабатывает, а сервис доходит до
  отказа. В отчёте это отдельная строка — она меняет модель угрозы.
- **Реплик одна — отказ полный.** При нескольких репликах отказывает только принявшая
  запросы; честная формулировка — «порог N на реплику».

Восстановление и его замер:

```bash
kubectl -n <ns> delete pod <pod>       # StatefulSet поднимет заново
kubectl -n <ns> get pod <pod> -o wide  # ждать Running с новым возрастом
```

`kubectl wait --for=condition=Ready` возвращает успех сразу: старый под ещё Terminating и
формально Ready. Признак готовности — новый возраст пода и первый внешний код 200 в
диапазоне ~2,5 мин после удаления; в это время ingress отдаёт 503/504, и это нормальный ход
перезапуска, а не продолжение атаки.

В отчёт идут: таблица ступеней (потоков в цикле → well-known → token → CPU), порог, факт
отсутствия проб, время восстановления, стек залипшего потока. Вывод формулируется как
«полный отказ в обслуживании достигается N одновременных запросов без аутентификации;
устраняется перезапуском компонента, самостоятельно не восстанавливается».

В минимальных контейнерных образах нет `ps` (в образе Keycloak его тоже нет): `kubectl exec … ps` падает с
`executable file not found`. Осмотр процесса — только через `jcmd 1 VM.version`,
`Thread.print`, `VM.system_properties`.

## Передача доступа к стенду

Если для дампа потоков нужен SSH, секрет не передаётся вообще: на рабочей машине
генерируется отдельная пара ключей, заказчику передаётся только **публичная** половина
(она не является секретом), он регистрирует её у себя и снимает после работы — отзыв
мгновенный, пароли менять не нужно.

Правила: просить учётную запись с правами только на перезапуск сервиса (docker/kubectl),
а не root; пароль в чат не писать никогда — он попадает в историю сессии и в контекст
модели; если хост пускает только по паролю, пароль передаётся файлом, читается скриптом
без вывода содержимого, файл удаляется, а пароль после работы меняется. Веб-логин
администратора для таких проверок не нужен: эндпоинт разбирает документ до проверок
подлинности. Vault-хранилище подставляет секреты только в веб-формы и для SSH не подходит.

## Как это ложится в отчёт

Согласованное в переписке решение переносится в документ сразу, а не остаётся в чате:
вердикт пункта (п. 3 → «Соответствует»), новый подраздел «Актуальность находок» с таблицей
находка → достижимость → проверка → вердикт и путями `файл:строка`, переклассификация строк
таблицы триажа, доказательства в `evidence/build/proofs/reach/` (класс, входы, журнал
прогона с цифрами). После правки — пересборка HTML и сверка: число вердиктов, отсутствие
переполнения таблиц, что старые формулировки («стенд не предоставлен») исчезли.

## Грабли

- **Собственная фабрика харнесса.** `XMLInputFactory.newInstance()` / `DocumentBuilderFactory`
  с умолчаниями внутри `fuzzerTestOneInput` даёт SSRF и XXE, которых в продукте нет: продукт
  разбирает через свою фабрику с `disallow-doctype-decl` и `SUPPORT_DTD=false`. В стеке такой
  находки видно `fuzzerTestOneInput` → `URLUtil.inputStreamFromURL` — это признак артефакта.
- **Раннер корпуса — тот же харнессовский путь.** Он полезен для устойчивости и минимизации,
  но актуальность не доказывает.
- **Образ без смонтированного каталога артефактов.** `/out` появляется только при `-v
  $BUILD:/out`; без него classpath пуст, и «ничего не найдено» ничего не значит.
- **Зависание на текстовом узле — не «медленный разбор».** Отличать по времени: медленный
  разбор растёт с размером входа, цикл виснет на входе в десятки байт.
- **Не путать «неактуально» с «ложное срабатывание».** Ложное — ошибка детектора; неактуальное
  — настоящий дефект вне модели нарушителя. В таблице это разные формулировки.
