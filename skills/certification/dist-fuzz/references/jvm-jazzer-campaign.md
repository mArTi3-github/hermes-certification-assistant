# JVM: кампания Jazzer и закрытие пунктов 1, 3, 5, 7

Jazzer = libFuzzer-движок + агент инструментирования байткода + bug detectors. Отсюда всё
остальное: метрики берутся из строк прогресса libFuzzer, структурное покрытие — отдельным
инструментом, а п. 1 формулируется через детекторы, а не через ASan.

## Сборка и обвязка

- JDK 17 (LTS-линия), Maven; версия JDK, Maven и Jazzer фиксируются в материалах.
- Classpath цели: jar-ы продукта + распакованные зависимости (`fuzzer-dependencies/`) +
  `jazzer-api.jar`; отдельные цели могут требовать доп. crypto-jar (FIPS) — список берётся
  из сборки OSS-Fuzz-проекта, не угадывается.
- Обёртка цели — тонкий скрипт вокруг `jazzer_driver --agent_path=… --cp=… --target_class=…`;
  из шаблона OSS-Fuzz удалить `apt install` и проверку «ровно openjdk 17».
- Память: `--jvm_args="-Xmx…:-Xss…"`; на 4 vCPU/7 ГБ реально 3–4 параллельные JVM
  по `-Xmx1g` + `-rss_limit_mb`, иначе OOM-килл выглядит как находка.

## Кампания

```bash
jazzer_driver --agent_path=jazzer_agent_deploy.jar --cp="$CP" --target_class=SamlParserFuzzer \
  -max_total_time=16200 -timeout=25 -rss_limit_mb=1500 -use_value_profile=1 \
  -print_final_stats=1 -artifact_prefix=/out/<T>/crashes/ 2>&1 \
  | while IFS= read -r l; do printf '%s %s\n' "$(date +%s)" "$l"; done > /out/<T>/log.txt
```

Лог с таймстампом на каждой строке — условие доказуемости п. 6; без него время последнего
прироста покрытия восстанавливается только через `runs/exec_s`, и это оспаривается.

### Управление длинным прогоном

- **Остановка на первой находке.** Jazzer по умолчанию прекращает работу после первой находки
  (`exit 77`, `SUMMARY: libFuzzer: no interesting inputs`). Флаги libFuzzer `-ignore_crashes=1`
  и `-ignore_timeouts=1` этого не меняют: продолжение задаётся `--keep_going=<N>` (по умолчанию 1).
  Ставить заведомо большим (`--keep_going=100000`), иначе кампания на часы заканчивается за десятки секунд.
- **Зависание тоже останавливает прогон** (`exit 70`, `SUMMARY: libFuzzer: timeout`), и
  `-ignore_timeouts` тут не помогает: таймаут обрабатывает сам Jazzer. Лечится супервизором и
  «разоружением» входа: артефакт `timeout-<sha1>` переложить в `hangs/`, а файл `corpus/<sha1>`
  удалить — иначе следующий отрезок снова начнётся с него же.
- **Супервизор на цель, а не на волну.** Фоновый работник держит цель до конца бюджета:
  `remaining = deadline - now`; запуск на `remaining`; ожидание выхода; при `exit != 0` — повторный
  запуск, при `exit == 0` — выход. Волна = N работников, затем `wait`. Иначе один аварийный
  выход обнуляет весь бюджет цели.
- **TTY обязателен для полноты журнала.** `docker run -d` без `-t` даёт буферизованный stdout:
  в `docker logs` попадает только хвост, а после kill — почти ничего. Запускать `docker run -dt`
  и складывать отрезки `docker logs -t <name> >> log.txt`.
- **Живой статус — в отдельный файл, журнал только дописывается.** `log.txt` — доказательство:
  его пишет супервизор (`docker logs -t <name> >> log.txt`) при каждой остановке цели, и никто
  другой в него не пишет. Снимок по cron идёт в `live.txt` (`docker logs -t <name> > live.txt`):
  перезапись `>` в `log.txt`, попавшая на перезапуск контейнера, стирает историю — плато после
  этого считать не по чему, а классы исключений «исчезают» и обманывают сторожей. Анализатор
  статуса читает оба файла, дедуплицирует строки и сортирует по времени.
- **Один экземпляр очереди.** Два запуска с одинаковыми именами контейнеров удаляют контейнеры
  друг друга (`docker rm -f` при старте), и волны «завершаются» мгновенно. Ставить `flock` на
  файл блокировки в начале скрипта. Останавливать очередь шаблоном `pkill -f 'queue[.]sh'`:
  обычная строка `pkill -f 'queue.sh'` попадает в собственную командную строку ssh и убивает
  сессию (`exit 255`).
- **Транзиентная ошибка демона при `docker run`** (`error reading from server: EOF`) — не повод
  падать: три попытки с паузой 5 с и записью в журнал.
- **Сторож должен срабатывать на событие, а не на движение.** Подпись состояния — без
  таймстампов: число уникальных `DEDUP_TOKEN`, набор классов исключений (хеш), плато как
  «да/нет», состояние очереди, свободная память порогом. Число файлов в `crashes/` — плохой
  сигнал: libFuzzer пишет файл на каждый вход, и один дефект даёт десятки «событий». Сторож
  выходит по событию и перевооружается; на Desktop уведомление о завершении фонового процесса
  приходит сразу, а cron-выдача — только при следующем обращении к чату.
- **Что сторож не должен считать событием.** (1) Кратковременное отсутствие контейнера:
  супервизор удаляет и создаёт его за 2–3 с при каждом аварийном выходе — считать событием
  `kcf_up` нельзя вообще, транзиент совпадёт с опросом рано или поздно. (2) Новые артефакты
  того же дефекта — уже покрыто `DEDUP_TOKEN`. (3) Застой у незапущенной цели: признак
  вычисляется только для работающих, иначе журналы от пробных прогонов вечно «застывшие».
- **Застой считать по самому свежему из `log.txt` и `live.txt`.** `log.txt` дописывается
  только при остановке отрезка, поэтому здоровый четырёхчасовой прогон без перезапусков
  выглядит застоявшимся через полчаса. И выводить застой отдельной строкой (`STALL <цель>`),
  которая существует только когда он реален: поле в каждой строке переключается `no`→`na` во
  время перезапуска и даёт ложные события.
- **Сторожа не итерировать бесконечно.** Набор правил выше закрывает все встреченные ложные
  срабатывания; новый вариант писать только при новом классе отказа, иначе каждая итерация
  стоит лишнего пробуждения и правок на живой кампании.

### Разбор аварийных выходов: дамп, а не догадки

- **Сначала дамп потока.** `docker exec <name> jcmd 1 Thread.print` через 10–20 с после старта
  реплея: `Thread.State: RUNNABLE` и `cpu≈wall` — незавершающийся цикл в коде продукта (взять
  верхний кадр и сверить с исходником); `WAITING`/`socketRead` — сеть, резолвер, блокировка.
  Без дампа «сетевые» правки (`resolv.conf`, отключение сети) — потеря времени: в разобранном
  случае цикл был в парсере SAML 1.1, а не в DNS.
- **Реплею нужен существующий `artifact_prefix`.** Обёртка цели часто содержит свой
  `-artifact_prefix=/out/findings/<T>/`; если каталога нет, Jazzer падает с
  `ERROR: The required directory ... does not exist` (exit 1) — это не зависание и не находка.
  Создавать каталог или передавать свой флаг позже (действует последний).
- **Найденный дефект не «лечат» правкой харнесса.** Исключение одного парсера из `switch`
  бесполезно, если тот же код достижим из соседних, а харнесс перестаёт соответствовать
  апстриму. Правильно: зафиксировать находку и стек, ограничить потерю коротким `-timeout`
  (единицы секунд — дефект уже доказан) и оставить супервизор; правку харнесса откатить,
  diff — в материалы.
- **`-fork=1` переживает таймауты, но меняет шкалу.** Режим форка печатает
  `oom/timeout/crash` и продолжает работу, однако `cov` считается по объединённому корпусу и
  несопоставим с прогонами без форка — переключаться на него в середине кампании нельзя.
- **Цена перезапуска растёт с корпусом.** Каждый аварийный выход — повторная инструментация
  JVM и загрузка корпуса (десятки секунд при тысячах файлов), поэтому при частых зависаниях
  цикл «зависание → перезапуск» съедает больше, чем сам таймаут.
- **`-timeout` выбирать по замеру, а не по интуиции.** В журнале очереди виден цикл
  «hang → stop → start → следующий hang»: полезное время = цикл − таймаут. При 30 с на
  бесконечном цикле теряется около половины бюджета, при 8 с — около пятой части, ниже
  упирается в стоимость перезапуска JVM. Замер занести в отчёт как обоснование параметра.
- **Пробный прогон не выдавать за кампанию.** 45–60-секундная проверка харнесса пишется в тот
  же журнал и в статусе выглядит как «завершена, п. 6 не выполнен». Различать по длительности
  (<1 ч — «пробный прогон»), перед кампанией отводить прежний журнал в `log-smoke.txt`.

## Метрики (пп. 4–6)

- Строка прогресса: `#<runs> ... cov: <X> ft: <Y> corp: <Z> ... exec/s: <S>`.
- `cov` — покрытые рёбра, `ft` — признаки (рёбра + данные сравнений). Считать **обе**
  величины: `cov/seeds` и `ft/seeds` расходятся в разы и дают разные вердикты по п. 5«а».
- Стартовое покрытие — первая строка после подачи seeds; финальное — последняя.
- Плато по п. 6 — разница между временем последнего **прироста** `cov` (не только строк с
  `NEW`: прирост признаков печатается и при минимизации корпуса) и временем остановки.
  Считать по **глобальному максимуму** `cov` за все отрезки: аварийный перезапуск начинает
  счётчики заново, и «рост» от нуля — это перезапуск, а не новый путь. В статусе показывать
  максимум, а не значение из последней строки.
  Опорная точка для «сейчас»: текущее время, если журнал свежий (цель работает), иначе
  последняя строка (прогон завершён) — иначе плато работающей цели набирается от последней
  строки, которая бывает старше на часы, а у завершённой растёт бесконечно. Прирост,
  случившийся до старта кампании, не считается: queue-runner при запуске волны пишет время
  в `targets/<T>/campaign_start`, и опорный момент роста берётся как максимум из
  (последний прирост `cov`, старт кампании). Иначе пробный 60-секундный прогон даёт
  «плато 8 ч» у цели, идущей второй час.
- **Читать хвост журнала, а не весь файл.** У XML/JSON-целей парсер печатает по строке
  `[Fatal Error] :N:N: ...` на каждый битый вход — 1,4 ГБ за два часа. Полный разбор с
  дедупликацией через словарь `{строка: время}` на таком файле занимает минуты; достаточно
  однопроходного поиска максимума `cov` по хвосту (≈64 МБ), потому что максимум монотонен
  и повтор строки его не меняет. Снимок для статуса — `docker logs -t --tail 50000`
  (мегабайты вместо гигабайта каждые 10 минут); полный `log.txt` остаётся доказательством
  п. 3 и сжимается gzip перед сдачей.
- Признак инструментирования для п. 4: `cov`/`ft` растут после старта, есть `exec/s` и
  срабатывания детекторов; тип инструментирования — байткод (агент), это и писать.

## Структурное покрытие (п. 7)

Jazzer структурного покрытия не выдаёт. Схема:

1. `CorpusRunner` — маленький `main`, который читает файлы каталога и вызывает
   `fuzzerTestOneInput(FuzzedDataProvider)`. `FuzzedDataProvider` — **интерфейс** в
   `jazzer-api.jar`, реализуется своим классом без фаззера (детерминированное потребление байтов).
2. Два прогона под JaCoCo: по стартовым seeds (заодно даёт покрытие для п. 5«б») и по
   накопленному `targets/<T>/corpus` — тому же каталогу, куда писала кампания (отдельный
   `corpus_final` не создавать: второй срез окажется пустым, `files=0 ok=0`):
   `java -javaagent:jacocoagent.jar=destfile=<T>.exec -cp "$CP" CorpusRunner <corpus>`.
   Стартовый прогон по seeds одновременно проверяет, что каждый харнесс вообще работает:
   строки `files=N ok=N exceptions=0` — это проверка обвязки перед многочасовой кампанией.
3. `jacoco:report` → XML + HTML на цель; сводка по файлам/строкам/ветвям, отдельно — файлы
   с нулевым покрытием.

Проверять схему пилотом на одной цели до кампании: если JaCoCo не дружит с обвязкой, дешевле
узнать это до 10-часового прогона.

Отчёт по всему classpath считает знаменателем все классы продукта (в Keycloak 26.5.2 — 3 653
класса, ~479 тыс. инструкций), поэтому абсолютные проценты выглядят нулевыми (0,1 %). Для
п. 5«б» брать отношение «финальное / стартовое» на одном и том же classpath, а в отчёте
дополнительно давать срез по пакетам модуля цели — иначе 0,1 % прочитают как «покрытия нет».

## Триаж и воспроизведение (п. 3)

- Дедупликация находок по стек-хешу; артефакты — в `crashes/` цели.
- Классификация: реальная ошибка / срабатывание bug detector (SQL, LDAP, XPath, инъекция
  команд, SSRF, десериализация, ReDoS) / OOM / StackOverflow / ожидаемое исключение
  (харнесс ловит `VerificationException`, `IllegalArgumentException` и т. п.).
- Дедупликация — по `DEDUP_TOKEN: <hash>`, который печатается рядом с каждым срабатыванием;
  разные входы с одним токеном — одна находка.
- Реплей по одному: тот же wrapper с `-runs=1 <файл артефакта>`; из вывода берутся
  `== Java Exception: <класс>` и первая строка сообщения. Jazzer рядом кладёт Java-репродуцер
  `Crash_<sha1>.java` — его и прикладывать к таблице.
- Воспроизведение в фаззере: `--mode=regression` на артефакте.
- Воспроизведение «в штатном режиме»: тот же вход через `CorpusRunner` без агента Jazzer —
  обычная JVM, без инструментирования. Протокол — таблица «артефакт → стек-хеш → причина →
  воспроизведён/нет».

## Формулировка п. 1 для JVM

«Датчики: встроенные bug detectors Jazzer (перечень с версией), контроль необработанных
исключений, OOM и переполнения стека. Memory-санитайзеры (ASan/MSan/UBSan) к управляемой
памяти JVM неприменимы; ASan в OSS-Fuzz-сборке относится к нативной части/JNI. Перечень
зафиксирован в материалах, сборка — Dockerfile + digest + версии JDK/Maven/Jazzer.»

Не писать «сборка с ASan» со ссылкой на `sanitizers: [address]` в `project.yaml` — это
утверждение о нативной части, а не о Java-коде.
