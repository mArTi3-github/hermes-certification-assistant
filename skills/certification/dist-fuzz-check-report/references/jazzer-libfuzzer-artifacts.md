# Карта артефактов Jazzer.js / libFuzzer (фаззинг JS/TS)

Когда цели собраны на Jazzer.js (встроенный libFuzzer), привычных `fuzzer_stats`,
`plot_data` и `crashes/`+`hangs/` в комплекте нет. Метрики берутся из журнала
фаззера и отчётов покрытия; скрипты `afl_stats_report.py` / `afl_log_timeline.py`
к таким материалам неприменимы.

## Что где лежит (типовая раскладка)

| Артефакт | Путь | Что даёт |
|---|---|---|
| Журнал фаззера | `results/<цель>/logs/*.log` | заголовок прогона, прогресс `cov`/`ft`/`corp`, финальная строка `DONE`, `Done N runs in S second(s)` |
| Находки | `results/<цель>/findings/` | артефакты `crash-*`/`timeout-*`; пустой каталог = находок нет (проверять `ls`, а не `findings.md`) |
| Рабочий корпус | `results/<цель>/corpus/` | файлы, накопленные фаззером; число файлов ≠ `corp` из журнала |
| Стартовый корпус | `corpus/<цель>/seeds/` | seeds для пп. 2 и 5 |
| Покрытие | `results/<цель>/coverage/{seeds,final}/coverage-summary.json` | строки/ветви/функции в двух состояниях |
| Бандлы | `build/out/*.cjs` (+ `.map`) | инструментированная цель; SHA-256 сверяется с параметрами сборки |
| Сводки | `results/_summary/*.md` | заявления разработчика — проверять, не переписывать |

## Формат журнала

```
# 2026-11-13T07:39:33Z target=T1 dir=T1-... seconds=7200 sync=1 dict=/work/dictionaries/T1/markdown.dict
INFO: using inputs from: /work/results/T1/corpus
#131072\tpulse  cov: 795 ft: 5947 corp: 990/156Kb lim: 4096 exec/s: 143 rss: 317Mb
#580123\tNEW    cov: 795 ft: 5948 corp: 991/154Kb lim: 4096 exec/s: 110 rss: 317Mb L: 2455/3862 MS: 4 ...
#877268\tDONE   cov: 795 ft: 5948 corp: 991/151Kb lim: 4096 exec/s: 121 rss: 317Mb
Done 877268 runs in 7213 second(s)
```

- Заголовок: `seconds=` (заданная длительность), `sync=` (0/1), `dict=` (словарь).
- Прогресс: `#<runs> <pulse|NEW|REDUCE|DONE> cov:<рёбра> ft:<признаки> corp:<единиц>/<объём>`.
  Ранние строки `pulse` могут идти без `cov:` — пропускать, а не падать.
- `Done N runs in S second(s)` — фактическая длительность; она отличается от `seconds=`
  на десятки секунд и именно она нужна для плато.

## Разбор: регулярное выражение и самопроверка

```python
stat = re.compile(r'^#(\d+)\s+(\S+)\s+(?:cov: (\d+) )?ft: (\d+) corp: (\d+)/([\d.]+[KMG]?b).*?exec/s: (\d+)')
```

- Объём корпуса приходит с суффиксом `Kb`/`Mb` (`151Kb`); шаблон `(\d+)b` молча
  отбрасывает все строки после первого килобайта, и «финальными» оказываются метрики
  первых секунд. Признак ошибки: `DONE` в журнале есть, а распарсенный финал не совпал
  с ним. Всегда сверять итог с последней строкой `DONE` и с `Done N runs`.
- Время события оценивается как `runs / exec_s` этой строки: `exec_s` — средняя
  скорость, поэтому точность — единицы минут. Так и писать в отчёте.

## Пересчёт критериев

**П. 6 (плато).** `t_last = N_last / exec_s`, `плато = (S − t_last)/3600`.
Два независимых показателя:

- `cov` — покрытые рёбра: «новый путь»;
- `ft` — признаки покрытия (рёбра + данные сравнений): сюда попадают «новые
  сравнения» без нового ребра.

Порог «2 ч без прироста» может выполняться по `cov` и не выполняться по `ft`.
Считать оба, показывать оба, вердикт давать по более строгой трактовке с оговоркой.

Сканировать **все** строки прогресса (`pulse|NEW|REDUCE|DONE`) и фиксировать отдельно
последнее увеличение `cov` и `ft`. Прирост признаков нередко появляется на `REDUCE`
(минимизация корпуса добирает сравнения) — `grep '\tNEW'` такие строки пропускает и
занижает плато. Журналы содержат двоичные байты, поэтому поиск — только `grep -a`:
без него `grep` печатает «binary file matches» и обрезает выдачу, показывая ранние
строки вместо последних.

Длительность прогона и плато — разные величины, и в отчёте их надо разводить явно:
при длительности ровно 2 ч плато равно 2 ч только если после старта не было ни одного
прироста; любой прирост сокращает плато на время до него, то есть прогон должен быть
длиннее 2 ч. В тексте заключения давать строку журнала, номер запуска, значения до/после
и `exec/s` — тогда замечание «у нас суммарно 2 ч» закрывается пересчётом, а не спором.
Пример расхождения: длительность 7 204 с, последний рост `cov` на 6 672 с (плато 532 с),
`ft` — на 7 139 с (плато 65 с), при этом до конца прогона шли исполнения и `REDUCE`,
то есть цель не «остановилась», а не успела стабилизироваться за отведённое время.

**П. 5«а» (кратность).** libFuzzer не считает пути: есть `cov` (рёбра) и `ft`
(признаки). В материалах обычно фигурирует `ft` — тогда и считать по `ft`, но
приводить и `cov/seeds`: у цели с большим стартовым корпусом (сотни образцов)
`cov/seeds` легко падает ниже 2× (пример: 661 образец, 795 рёбер — 1,20×) при
`ft/seeds` ≈ 9×. Вердикт «соответствует по «а»» в этом случае действителен только
для выбранной метрики, и выбор метрики должен быть оговорён.

**П. 5«б».** Покрытие seeds → final из `coverage-summary.json`; у Jazzer-целей
отношение обычно 1,0–1,1×, то есть «б» почти никогда не выполняется — решение
принимается по «а» или по льготе 90 % строк.

## Контроль датчика (пустой корпус)

Jazzer.js в `--mode regression` запускает цель и без единого входа. SSRF-детектор при этом
срабатывает на собственном loopback-подключении HTTP-харнесса (`send()` → `net.Socket.connect`),
то есть «сбой» есть при 0 входов и к содержимому входа отношения не имеет.

```bash
# если срабатывает на пустом каталоге — это транспорт харнесса, а не поведение продукта
jazzer build/out/<T>.cjs --mode regression <пустой каталог>
# и наоборот: с отключённым SSRF ни один вход не должен давать срабатывания
jazzer build/out/<T>.cjs --mode regression <каталог с одним входом> --disableBugDetectors=ssrf
```

Тем самым входы `regression-*` объясняются транспортом харнесса — именно поэтому в
`harnesses/<T>/target.conf` SSRF отключён. Сам по себе `--disableBugDetectors` — довод
«дефекта нет», но не замена таблице триажа: причину отключения надо восстановить и приложить.

Если таблица триажа приложена, сверить каждый вход с материалом по SHA-1
(`sha1sum corpus/<цель>/seeds/regression-*`): совпадение всех хешей подтверждает, что
разбирали именно переданные файлы, а расхождение означает, что триаж относится к другой
версии входа. В заключении так и писать: «SHA-1 сверены, N из N».

## Особенности Jazzer.js, влияющие на проверку

- Санитайзеров нет по определению (JS/TS): п. 1 закрывается **детекторами**
  (`command-injection`, `prototype-pollution`, `path-traversal`, `ssrf`) плюс
  оракулами харнесса; неприменимость санитайзеров должна быть записана в документах,
  а не подразумеваться.
- `--disableBugDetectors=ssrf|path-traversal` в `target.conf` — признание ложных
  срабатываний самим разработчиком; в отчёте это довод, но не таблица триажа.
- `--mode regression` — прогон корпуса без мутаций; им снимают покрытие и
  воспроизведение, но это инструментированная сборка, а не «штатный режим».
- Бандл самодостаточен: `fuzz()` вызывается обычным Node без Docker и Jazzer.js —
  так проверяют оракулы на машине проверяющего; входы подавать абсолютными путями
  (харнесс делает `process.chdir()`).
- «Ветви» в istanbul ≠ «базовые блоки» Методики: льготу 80 % блоков по таким
  отчётам оценить нельзя.
