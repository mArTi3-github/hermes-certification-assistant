# Структура отчёта «Тестовая документация» (приказ ФСТЭК № 76)

Карта документа и шаблоны блоков. Нумерация разделов в разных отчётах почти
повторяется, но номера таблиц/рисунков сквозные — брать их из документа, а не
из этого файла.

## Карта разделов

| Раздел | Содержание | Что оттуда берётся |
| --- | --- | --- |
| Содержание | поле TOC, дублирует заголовки стилями `toc*` | игнорировать при разборе |
| Сокращения | таблица определений (ОО = объект оценки) | расшифровки для ответа |
| Аннотация | ссылка на приказ № 76, уровень доверия (обычно 4), таблица «Соответствие требований разделам документа» | какие разделы закрывают требования к тестированию |
| 1. Испытательный стенд | ссылка на схему и конфигурацию в другом документе (Технический проект, прил. В) | стенд обычно не описан здесь |
| 2. Установка ОО | по эксплуатационной документации, каталог приложений | контекст прогона |
| 3. План тестирования | таблица «№ / Тест / Пункт документа» | список тестов и их разделов |
| 4. Проверка выполнения функциональных требований | 4.1 — требования к функциям безопасности, 4.1.N — отдельные тесты; возможны 4.2+ для иных групп | основной материал |
| 5. Свидетельство анализа покрытия тестами | интерфейсы функций безопасности ↔ тесты | полнота покрытия интерфейсов |
| 6. Свидетельство анализа глубины тестирования | модули, реализующие ФБ ↔ подсистемы ↔ тесты | полнота покрытия модулей |
| 7. Оценка влияния | влияние иных подсистем/модулей на реализующие ФБ, со ссылками на ЭП/ТП | оценка влияния |

## Шаблон блока теста (4.1.N)

```
4.1.N Проверка выполнения требований к <название> (<ID>, <ID>)

Проверяемые требования
  [таблица: одна строка на требование]
  <формулировка требования> (<ID>).
  / <чем изделие обеспечивает требование>

Предварительные настройки
  Не требуются. | <перечень настроек стенда>

Шаги тестирования и полученные результаты в соответствии с описанием требования <ID>
  1. <шаг>
     Рисунок N – Выполнение текущего шага тестирования
  2. <шаг>
     → <фактический результат своими словами>
  ...
  [подсерия шагов повторяется для каждого ID из заголовка]

Ожидаемые результаты
  Успешное выполнение шагов тестирования.

Вывод
  Ожидаемые результаты совпали с фактическими, тест завершен успешно.
```

Вариации, которые не являются ошибками:

- «Проверяемые требования» может быть таблицей (две строки и больше) или одним
  абзацем — в зависимости от возраста шаблона.
- В некоторых тестах заголовок «Шаги … и полученные результаты» один, а внутри
  несколько подряд идущих подсерий с указанием ID.
- Фактический результат может быть вписан отдельным абзацем после рисунка, а
  может подразумеваться («на рисунках ниже»).

## Шаблон таблицы плана тестирования (раздел 3)

| № | Тест | Пункт документа |
| --- | --- | --- |
| 1 | Проверка выполнения требований к <название> (<ID>) | 4.1.N |

Колонка «№» бывает не заполнена — тогда тест адресуется пунктом раздела.

## Таблицы покрытия и глубины (5–6)

- Покрытие (5): `Интерфейсы функций безопасности средства (из документа
  «Функциональная спецификация») | Тесты из текущего документа`. Типичные
  интерфейсы: «Графический интерфейс пользователя», «Интерфейс сбора данных».
  Один интерфейс может покрываться несколькими тестами.
- Глубина (6): `Модули, реализующие функции безопасности | Подсистема, к которой
  относится модуль | Тесты из текущего документа`.
- Ссылка в ячейке всегда в форме `Раздел 4.1.N, тест «<полное название теста>»` —
  при добавлении теста обновлять обе таблицы и раздел 3, иначе покрытие станет
  неполным (это первое, что замечает проверяющий).

## Чек-лист нового/исправленного теста

1. Тест занесён в раздел 3 (план) с пунктом `4.1.N`.
2. В заголовке теста — все ID требований, которые он закрывает.
3. На каждый ID — своя подсерия шагов.
4. Есть негативные кейсы, ожидаемый исход каждого сформулирован явно.
5. На каждый шаг — рисунок с подписью в едином формате, нумерация сквозная.
6. Блоки «Ожидаемые результаты» и «Вывод» — фиксированными формулировками.
7. Тест добавлен в таблицу покрытия (интерфейс) и в таблицу глубины (модуль,
   подсистема); при новом модуле — и в раздел 7.
8. Перечитан только что изменённый раздел
   (`docx_read_ordered.py --start "4.1.N" --end "4.1.N+1"`) и прогнан
   `docx_validate.py`.
