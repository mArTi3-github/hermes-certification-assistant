# Материалы модульного тестирования без разметки комплекта

Что делать, когда вместо `DIST.TST` с `results/junit.xml`, `readme.txt` и
`coverage-summary.*` принесли рабочий дамп: сохранённые страницы заданий CI,
журналы раннеров, HTML-отчёты покрытия, архивы отчётов, пустые каталоги.
Такой набор всё равно проверяем — числа берутся из отчётов покрытия и итоговых
строк журналов, а не из заявлений.

## 1. Признаки и что сообщать в отчёте

Признаки: нет `readme.txt`/`README`, нет `junit.xml`, нет манифеста, нет
`environment.txt`; вместо этого файлы вида `Build (#…) · Jobs · … · GitLab.html`,
`Allure Report*.html`, каталог `coverage*/`, архивы `*.zip` с отчётами, пустые
каталоги компонентов.

В шапке отчёта прямо: состав (файлов/байт), SHA-256 манифеста, что именно
отсутствует и что поэтому сверка «заявлено ↔ фактически» невозможна. Вердикт по
требованию оценивается по фактическим артефактам, а не по обещаниям: отсутствие
README — замечание об оформлении, а не основание считать требование нарушенным.

## 2. Сохранённые страницы CI → текст

```python
import re, html
def to_lines(path):
    t = open(path, encoding='utf-8', errors='replace').read()
    t = re.sub(r'(?is)<(script|style|svg)[^>]*>.*?</\1>', ' ', t)
    t = re.sub(r'(?s)<[^>]+>', '\n', t)
    lines = [re.sub(r'[ \t]+', ' ', l).strip() for l in html.unescape(t).split('\n')]
    return [l for l in lines if l]
```

Журнал задания в такой странице встроен в разметку целиком, поэтому искать по
нему можно как по тексту. Но часть строк — это склеенные команды линковки и
пути сборки длиной в десятки килобайт. Перед любым `grep` фильтровать по длине
(`len(s) < 300`) и печатать найденное обрезанным до 140–160 символов, иначе один
совпадение вытеснит весь остальной вывод.

Метаданные задания достаются теми же строками: `Commit` → хеш и сообщение,
`Pipeline` → номер и статус, `Duration:`/`Finished:`. Осторожно: `Duration:`
встречается несколько раз (длительность задания и длительности стадий) — если
значение не однозначно, длительность в отчёт не выносить, а брать только
коммит/пайплайн.

## 3. Разбор отчётов покрытия по инструментам

### coverage.py (`htmlcov/index.html`)

Колонки таблицы зависят от режима: `Module | statements | missing | excluded |
coverage` — когда ветви не измерялись, колонок `Branch`/`BrPart` нет вообще.
Строки — `<tr class="file">`, итог — `<tr class="total">`. Агрегат считать из
чисел, а не усреднять проценты: `1 - Σmissing / Σstatements`.
`htmlcov/status.json` — служебный индекс (в `index.nums` лежат числа только по
файлу, без процентов); читать его целиком нельзя — это десятки килобайт JSON,
который вытесняет контекст.

```python
rows = [cells(r) for r in re.findall(r'<tr class="file">(.*?)</tr>', t, re.S)]
# cells(): Module, statements, missing, excluded, coverage
```

Если колонок `Branch` нет — в отчёте писать «покрытие ветвей не измерялось»
(это замечание, а не нейтральная деталь: ветвистость разбора ввода — как раз то,
что проверяют).

### Istanbul (`coverage-final.json`) и `clover.xml`

Из JSON считаются три метрики независимо: `s` (statements), `f` (functions),
`b` (ветви, каждая запись — массив счётчиков). `len(x)` + число ненулевых.

`clover.xml` даёт проектную сводку одним тегом:
`<metrics statements="…" coveredstatements="…" conditionals="…" methods="…" files="…"/>`.

Знаменатели двух артефактов не обязаны совпадать (встречается разница в сотни
строк при совпадающем числе файлов). Тогда в отчёте: обе величины, вывод, что
расхождение на десятые доли процента на вердикт не влияет, и требование указать,
какой отчёт считать основным, плюс конфигурацию генерации.

### `go test -cover` (журнал задания)

Постраничные строки `pkg … coverage: 0.0% of statements` обманчивы: пакеты без
тестов тоже дают такую строку. Авторитетно только
`total: (statements) N%` — вывод `go tool cover -func=cover.out | tail -n1`.
Дополнительно считать: сколько пакетов `ok`, сколько `? … [no test files]`,
сколько строк покрытия и сколько из них `0.0 %` — медиана 0 % при итоге 1–2 %
это отдельное замечание о концентрации тестов в единичных пакетах.

### `lcov` / `genhtml`

Сводка в журнале — блок `Summary coverage rate:`:
`lines......: 66.5% (74534 of 112120 lines)`, `functions..: …`, `branches...: no
data found`. Строка `no data found` у ветвей = покрытие ветвей не снималось.
Если в журнале есть фильтрация (`coverage_filtered.info`), отметить, что состав
исключений не приведён.

### `meson test`

Итог — строки `Ok: N`, `Fail: N`, `Skipped: N`, `Timeout: N`, `Expected Fail: N`;
выше — список `1/79 … OK`. `Fail: 0` — это результат прогона, но не покрытие.

### pytest / CTest

pytest: `collected N items / … / M selected`, итог `= X passed, Y skipped,
Z xfailed, W xpassed …`; версии — в заголовке сессии (`pytest-6.2.5, pluggy-…`,
`plugins: …`). CTest: `100% tests passed, 0 tests failed out of N`.
Сумма слагаемых итога может не сойтись с «selected» на единицы (параметризация,
повторные запуски) — это замечание «просим пояснить», а не повод пересчитывать
итог.

### Allure

Из сохранённой страницы извлекаются только отрисованные числа: `TestRun #N`,
дата и длительность, `N test cases`, `%`, разбивка по наборам, категории.
В расширенном отчёте бывает строка `Status: 5 0 4776 0 0` — порядок
failed / broken / passed / skipped / unknown. Полные данные в HTML не
встраиваются, поэтому построчные статусы по всем прогонам не восстановить —
так и писать.
Вердикт: системные/функциональные прогоны — не модульное тестирование; они идут
в отдельное приложение и на покрытие компонентов не влияют.

## 4. Цитирование

В комплекте с машинными артефактами — путь + номер строки. В сохранённой
странице номера строк относятся к разметке, поэтому цитируется **фрагмент
журнала**: «страница `unit-tests (#…)`: `total: (statements) 1.3%`». В
приложении-карте артефактов одной строкой объяснить, почему для этих файлов
ссылка на фрагмент, а не на строку.

## 5. Ловушки

- **Процент в имени файла — заявление.** Архив `… (46.8%).zip` фиксирует цифру в
  названии; в самих HTML-отчётах `go tool cover` итога может не быть. В отчёте:
  «46,8 % указано в имени файла, в артефактах не подтверждено», рядом — то, что
  действительно измеримо (число пакетов с покрытием, медиана, минимум).
- **Пробелы в именах файлов ломают `xargs`.** Хеш манифеста для каталога с
  пробелами и кириллицей в именах: `find <dir> -type f -print0 | sort -z |
  xargs -0 sha256sum | sha256sum`. Без `-0` получаешь список «No such file or
  directory» и пустой хеш.
- **Один прогон может обслуживать два требования.** Покрытие по компоненту и
  покрытие ветвей снимаются разными ключами; отсутствие второго — отдельное
  замечание, а не «нет данных».
- **Пустой каталог компонента** фиксировать как «материалы не приложены либо
  компонент вне объёма» и ставить в запрос, а не молча пропускать.
- **Скрипты разбора писать в файл и запускать, а не собирать heredoc-ом в
  терминале**: heredoc с обращением к крупному JSON/бинарю может не пройти
  предварительную проверку команды. Файл в рабочем каталоге запускается без
  проблем, а заодно остаётся для повторного прогона.
- **Приложенный отчёт покрытия не доказывает прогон тестов.** Проверять, в каком
  задании он получен: если единственная страница задания — линт/типы/формат, а
  тестов в ней нет, то отчёт относится к неизвестному состоянию кода (тем более
  если в путях внутри JSON видна ветка разработчика). Это замечание о
  прослеживаемости, а не о качестве тестов.
