# Проверка PREP.INFO (сертификация ФСТЭК)

PREP.INFO — документ подготовки информации об изделии для сертификации.
В отчётах и замечаниях он называется только PREP.INFO; слово «анкета» в текст
заключения не попадает (см. правило 0.9).
Заполняет Dev, проверяет Cert. Блоки: 2.1–2.4, 3, 4, 5, 6.1–6.5, 7, 8.1, 8.2,
у каждого — подпункт «Примечания» и шапка «Заполняет / Проверяет / Информация
актуальна для: <версия>».

## When to Use

Задача — проверить PREP.INFO (документ подготовки информации об изделии) перед
сертификацией ФСТЭК: пройти пункты, сформулировать критерии, сверить
с ЭД и выдать замечания. Не для отчётов о тестировании по приказу № 76 — это
`stand-ftest`.

## Старт: что сказать при вызове

Скилл вызывается фразой «проверь PREP.INFO» (привычное пользовательское «проверь анкету по продукту X» означает то же самое).
До первого пункта — объявить, что делает скилл, и проверить входные данные.

**Что делает.** Проходит PREP.INFO по пунктам 2.1–2.4, 3, 4, 5, 6.1, 6.2, 6.4, 6.5
(пункт 6.3 исключён — раздел устарел и выводится из документа), сверяет каждый
пункт с эксплуатационной документацией (ЭД) и выдаёт заключение: вердикт по
каждому пункту, замечания с координатами в обоих документах, файлы `.md` и
автономный `.html`.

**Что нужно на входе:**

1. PREP.INFO (PDF) — обязателен; версия и SHA-256 фиксируются в шапке отчёта.
2. ЭД той же версии: руководства администратора и пользователя; руководство
   разработчика — если оно есть, по нему сверяются коды ответов API и поведение
   интерфейсов (пп. 4, 6.2).

**Если ЭД нет — не начинать молча.** Сказать прямо, что сверка с ЭД невозможна,
и предложить выбор: (а) запросить руководства (нужны минимум руководство
администратора и руководство пользователя той же версии, что PREP.INFO), или
(б) провести проверку только на внутреннюю согласованность — 2.1–2.4 между
собой, 3 ↔ 5 ↔ 6.1 ↔ 6.2 ↔ 6.4 ↔ 6.5, схема ↔ порты ↔ п. 2.2 — и в шапке отчёта
написать «ЭД не представлены, сверка не выполнялась; отчёт неполный». Выдавать
такую проверку за полную нельзя.

**Если ЭД есть, но другой версии** — сказать об этом, сверить с той, что дали,
и указать версию в шапке. **Если ЭД неполные** (например, только руководство
администратора) — перечислить, каких документов не хватает, и пометить, какие
пункты остались без сверки.

Скрипт инвентаризации входа (что нашли и чего не хватает):

```bash
python3 scripts/check_inputs.py <каталог с материалами>
```

Тип документа он определяет по титулу (первая страница), имя файла — только
подсказка: имена у всех разные, а титул называет документ своим именем. Если
имя и титул расходятся, побеждает титул, а расхождение попадает в
предупреждения. Что за файлы поданы, при постановке задачи обычно сказано
словами — этот перечень главнее и скрипта, и имени файла; если его нет, тип
берётся с титула. Файл, не опознанный ни по титулу, ни по имени, выводится как
«не распознано»: спросить, что это, а не угадывать по расширению.

**Шаблон первого сообщения:**

> Проверю PREP.INFO по пунктам 2.1–6.5 (6.3 исключён) со сверкой с ЭД.
> Нашёл: PREP.INFO — <файл, версия>; ЭД — <перечень>.
> Не хватает: <список> — без них сверка по <пункты> будет неполной.
> Могу (1) подождать руководства, (2) проверить только внутреннюю согласованность
> и пометить отчёт как неполный. Как поступим?

**Как показывать сам старт.** На вопрос «что выведется, когда я вызову скилл» ответ —
не пересказ этого раздела, а три реальных прогона `check_inputs.py` с их точным текстом:
полный вход (код 0), только PREP.INFO (код 1), пустой каталог (код 2). Описывать
поведение словами и не запускать скрипт нельзя: пользователь проверяет именно вывод,
а расхождение текста с фактическим прогоном читается как нерабочий скилл. Той же
оговоркой закрывается вопрос про обновление профиля: скилл виден вызывающему только
после того, как версия с этим именем доехала до профиля (`sync.sh` / `profile update`);
локальная правка у коллеги не появляется.

**Имя скилла — это имя каталога.** Вызывается как `<категория>/<имя>`; переименование =
`mv` каталога и `name:` во фронтматтере. Индекс скиллов в системном промпте
обновляется только в следующей сессии, поэтому в текущей сессии старое имя в списке
не означает, что переименование не сработало: проверять вызовом по новому имени.

**Имя называет пользователь, а не конвенция.** Имя скиллу даёт заказчик: сейчас это
`prep-info-check-report`, и любое «упорядочивание» без его просьбы откатывается
следующим же сообщением. Своё имя предлагают один раз и до первой публикации; после
неё смена имени — отдельный PR, в котором старое имя снимается, иначе у коллег
окажутся два каталога одного скилла.

## README скилла (то, что видно в GitHub)

`README.md` в каталоге скилла GitHub показывает при открытии папки — это первое, что
читает коллега, поэтому он есть у опубликованного скилла. Пишется по запросу
(«сделай README скилла»), состав ровно такой:

- заголовок `<имя скилла> — <что проверяет>` словами заказчика;
- «Что делает»: таблица проверяемых пунктов, что исключено (6.3), словарь вердиктов,
  имена выходных файлов;
- «Как вызвать»: фраза в чате и полное имя с категорией;
- «Что нужно на входе»: PREP.INFO и ЭД — руководства администратора и пользователя,
  разработчика если есть;
- «Если руководств нет»: два варианта и абзац про ЭД другой версии — на нём README
  заканчивается.

Не добавлять: ТУ и прошлую редакцию как обязательный вход, рамку проверки, запуск
`check_inputs.py`, «Связанные скиллы», «Границы» и любые разделы «для полноты» —
лишний объём заказчик читает как спор с постановкой и снимает; скрипт инвентаризации
остаётся в SKILL.md. Готовый текст дают в чат на согласование; ветка и PR — только
после «согласовано/публикуй».

## Как идёт проверка

0. **Прошлая редакция — не обязательный вход.** Рамку проверки не запрашивать и
   документы не требовать: проверяются все пункты 2.1–6.5 (6.3 исключён) по тому,
   что передано. Если эталонная редакция PREP.INFO лежит среди материалов, сверять
   с ней можно по собственной инициативе, но расхождение с прошлой редакцией
   блокером НЕ является (максимум наблюдение); отличия, о которых заказчик
   попросил отдельно, идут в замечания.
0.1. **Мелкие замечания не выбрасывать.** Опечатки, вёрстка (разрывы слов), путь
   к приложению, стилистика — фиксируются в журнале с меткой «мелкое»,
   блокерами не считаются, но и не снимаются: их разбирают после сводного
   отчёта. Исключение — если пользователь прямо сказал, что по конкретному
   пункту мелкие не принимает. Замечание-блокер —
   расхождение по содержанию (перечни, шифры мер, порты, ссылки на разделы ЭД,
   невыполненное требование шаблона).
1. **Пункт за пунктом, сверху вниз.** Требование к каждому пункту формулирует
   заказчик проверки; не выводить его самому и не забегать в следующие разделы
   (ссылка «это же не отражено в 6.4» в проверке 2.1 — забегание, замечание
   снимается). Сначала критерий пункта, потом текст.
2. **Сверка с ЭД — основной инструмент.** Информация в PREP.INFO должна
   совпадать с руководствами той же версии, что и проверяемый документ:
   - функции изделия — руководство администратора, раздел «О <продукт>»
     (в рук. пользователя он обычно продублирован);
   - аппаратные/программные требования и порты — рук. администратора, раздел
     «Аппаратные и программные требования».
   Чего в руководствах нет — того не требовать: критерий проверки не
   додумывается.
3. **Правило сертифицированной среды (пункт 2.2).** В PREP.INFO попадает только
   сертифицированная среда функционирования (обычно Astra Linux SE).
   Если в ЭД перечислены несертифицированные ОС и платформы (Debian, Hyper-V,
   KVM, мобильный модуль), а в PREP.INFO их нет — это не дефект: писать «в ЭД
   указаны также …, в PREP.INFO они не приведены» (см. 0.3), ничего не исключая
   от себя и не оценивая это решение. Дефект — неточная версия среды (1.8
   вместо 1.8.5).
4. **Пункт 2.3 — без формальных требований.** Проверяется описательность:
   перечень содержимого дистрибутива (установочные пакеты, архивы исходных
   текстов) и идентификаторы файлов. Чего в PREP.INFO быть не должно: описания
   у строки «Архив с исходными текстами» («-» — норма, из названия всё ясно),
   указания, один архив или их несколько (появятся другие — будут перечислены),
   конкретной версии/сборки (идентификаторы остаются с `*версия*`
   и `*номер сборки*`, их поясняет примечание). Для сверки с фактическим
   архивом просить листинг (`unzip -l`, `ls -l`/`makeself --list`), а не сам
   архив.
5. **Пункт 2.4 — список ФБ задаёт Dev (владелец продукта), проверяющий сверяет и не выдумывает.**
   Критерии: (а) включены ФБ, реализуемые ПО, а для ПАК — ещё и аппаратной
   платформой (у ПО-продуктов ФБ аппаратной платформы быть не должно);
   (б) шифры и формулировки мер сверяются со справочником «Группы мер защиты
   информации» на bdu.fstec.ru/threat-section/defenses (открывается только
   браузером: curl/extract получают 403/SSL-ошибку) — по каждой строке сравнить
   шифр и суть меры, расхождение оформлять как вопрос «откуда шифр», а не как
   ошибку; (в) орфография и только ЯВНЫЕ противоречия описания сути меры —
   к формулировкам не придираться: модальность, полнота пересказа, стиль
   замечаниями не являются; замечание только когда описание противоречит
   смыслу меры (мера про аутентификацию, а описание — про разграничение
   доступа); (г) рекомендации по добавлению мер — только технические,
   которые продукт точно выполняет по своим функциям из 2.1; организационные
   меры (регламентация, определение перечня, информирование должностных лиц)
   не предлагать.
   Справочник удобно выгрузить в файл (`document.body.innerText` →
   `defenses_raw.txt`) и распарсить в пары «шифр → название» (~500 мер), чтобы
   искать по группам АУД/ИАФ/УПД, а не глазами.
6. **Сквозная согласованность — обязательная часть проверки.** Имена подсистем,
   модулей, компонентов ОО и перечни портов должны совпадать во всех пунктах,
   где они встречаются: 2.2 (порты) ↔ 3 (схема) ↔ 5 ↔ 6.1/6.2 ↔ 7 ↔ 8.x.
   Три разных набора портов в 2.2, на схеме и в ЭД — типовой дефект; сверять
   построчно и фиксировать, какой источник верный. После прохода пункта
   сравнивать его данные с уже пройденными, а расхождения, касающиеся будущих
   пунктов, отмечать в журнале как «проверить при п.N», а не как замечание
   текущего.
7. **Пункт 3 «Архитектура».** Требование 1: графическое описание архитектуры
   на уровне крупных компонентов (подсистемы + внешние субъекты; модули внутри —
   допустимая детализация). Схема в PDF — картинка: `pdfimages -f N -l N -png`
   и просмотр глазами; пустой текст раздела не значит отсутствие схемы.
   Проверять: состав подсистем/модулей, подписи на связях (протокол/порт),
   отличия от схемы предыдущей редакции (`diff` картинок и просмотр обеих).
   Схемы в PREP.INFO не нумеруются, не подписываются и не имеют ссылок из
   текста — это принятый порядок документа, а не дефект (замечание снимается).
   Требование 2 к разделу — из методики; пока не получено, проверка идёт
   по требованию 1, а в скилле остаётся пометка «ждём требование из методики».
8. **Пункт 4 «Внешние интерфейсы».** Внешний интерфейс — тот, через который
   данные уходят за пределы продукта или через который пользователь/внешняя ИС
   получает доступ к функциям продукта. Обмен между компонентами самого
   продукта (сервер ↔ агент, Frontend ↔ Backend ↔ БД/S3) — внутренний, в раздел
   не попадает. API: если доступен только для работы веб-интерфейса и внешние
   системы к нему не обращаются сами — отдельным интерфейсом не выделяется;
   если к нему можно обращаться напрямую и полноценно работать — это
   самостоятельный внешний интерфейс. Проверять: (а) все подсистемы/модули
   из прошлых пунктов в таблице; (б) все ФБ из 2.4 перечислены; (в) полный
   перечень внешних интерфейсов (веб, сетевые взаимодействия с внешней
   инфраструктурой) и по каждому — поверхность атаки с причиной исключения;
   SSH-доступ к ОС — не интерфейс продукта, его отсутствие правильно;
   атакующие действия — тоже не внешний интерфейс: данные за контур продукта
   не уходят, наружу идут только задания атакующим приложениям;
   (г) интерфейсы, не влияющие на ФБ, — отдельный перечень; если таких
   интерфейсов нет вовсе, их отсутствие НЕ дефект (не минус и отсутствие
   пометок о них); отметить можно только как вопрос «а есть ли иные функции
   на этом интерфейсе», если продукт их заявляет; (д) ссылки на разделы ЭД
   сверять с актуальным оглавлением (номера разделов меняются между редакциями:
   параметры — разд. 5–6, ошибки — «Решение проблем»); (е) для ПО блоки про
   интерфейсы аппаратной платформы не применимы.
9. **Пункт 5 «Подсистемы».** Требования: (1) перечень подсистем,
   РЕАЛИЗУЮЩИХ ФБ; (2) перечень подсистем, ПОДДЕРЖИВАЮЩИХ выполнение ФБ;
   (3) перечень подсистем, не влияющих на ФБ; (4–5) проектирование подсистем;
   (6) способы взаимодействия подсистем с механизмом, исключающим влияние
   на ФБ. Критерий по перечням: должны быть подсистемы, реализующие все ФБ;
   наличие только поддерживающих без реализующих — дефект, а разделение
   «реализует/поддерживает» в одной колонке — нет. Подсистемы, не влияющие
   на ФБ, могут быть, могут не быть — не критерий проверки. Частая слабость:
   описание обмена без механизма невозможности влияния (изоляция,
   аутентификация) и без протокола/порта — для вердикта это не дефект,
   а рекомендация к заполнению (см. 0.7 и 0.16). Названия подсистем и покрытие ФБ
   сверять с 2.3, 2.4 и схемой п. 3.
10. **Пункт 6.1 «Модули — ФБ и поверхность атаки».** Требование: все модули
   продукта, по каждому — входит ли в поверхность атаки (да/нет/косвенно),
   с причиной исключения. Проверять: состав модулей = схема п. 3 и модули,
   упомянутые в 6.2/6.4; все ФБ из 2.4 покрыты хотя бы одним модулем;
   подсистемы совпадают с 5. **Если сверка с предыдущей редакцией согласована**
   (п. 0) — сравнить состав: модуль мог исчезнуть из таблицы, оставаясь
   в документе
   (модуль мог остаться в поверхности атаки в прошлой редакции, пропасть из 6.1
   в новой и остаться в инструментах тестирования).
   Одинаковая формулировка причины исключения у нескольких модулей — повод
   проверить, что она вообще объясняет изоляцию именно этого модуля.
11. **Пункт 6.2 «Модули — описание».** Главная проверка — колонки «Описание
   интерфейсов модуля» и «Возвращаемые в ответ на запросы значения» у модулей,
   РЕАЛИЗУЮЩИХ ФБ (сверить с 6.1): по шаблону они обязательны именно для них,
   и «-» у такого модуля — блокер, даже если у модуля поверхности атаки
   всё заполнено. Также: описание всех модулей (назначение + взаимодействия),
   связь с внешними интерфейсами из п. 4, механизм невозможности влияния
   при взаимодействии модулей, наличие модулей поверхности атаки в таблице.
   Сопоставление с подсистемами эскизного проекта — не блокер, если в PREP.INFO
   есть прямая ссылка на эскизный проект.
12. **Пункт 6.3 «Заимствованные компоненты» — из проверки исключён.** Раздел устарел и
   выводится из PREP.INFO решением заказчика: пункт не разбирается, строка из таблицы
   итогов убирается, замечаний по нему нет. Если раздел в документе ещё присутствует —
   отметить одной строкой в разделе готовности, что он подлежит удалению, без разбора
   содержания (ссылки на перечень компонентов, приложения, внешние реестры не проверять).
13. **Пункт 6.4 «Представление реализации».** Колонка «Интерпретаторы/среды
   выполнения (с указанием точной версии)»: «Node.js 22» или «.NET 8» — не
   точная версия, а мажор — требование не выполнено. Инструменты сборки
   (cmake, conan, gcc, msbuild) исполняются, но на этапе сборки (cmake — свой
   язык, conan — Python), поэтому замечание формулировать как «указаны
   инструменты этапа сборки вместо среды выполнения», а НЕ «это не код»:
   на формулировку «не среда выполнения» пользователь возражает (cmake/conan —
   тоже исполняемый код). Если Dev заявляет, что скрипты исполняются при
   РАБОТЕ модуля, требовать явного указания этапа — тогда строка законна
   и замечание снимается; окончательное решение — **на усмотрение проверяющего**,
   блокером не считать; для нативных
   бинарников (C++/Go/Rust) среда — ОС/рантайм, и «-» нужно пояснять, а не
   подменять инструментами сборки. Плейсхолдеры вида «<в процессе замены>»
   в сдаваемом документе — блокер. Логика парами: язык ↔ среда (TypeScript →
   Node.js, C# → .NET, C++ → нативно) должна сходиться; когда появится перечень
   заимствованных компонентов, сверить, что указанные интерпретаторы и версии в нём есть.
14. **Пункт 6.5 «Инструменты разработки».** Проверять не список, а **сверку
   версий с 6.4 по каждому модулю** — здесь чаще всего ловится противоречие
   (образ/рантайм в 6.4 против образа/компилятора в 6.5: СУБД 17.5 против 18.3,
   одно объектное хранилище против другого, cmake 3.20 против 3.25.1, .NET 8 против sdk 10).
   Также: перечислены ли ВСЕ инструменты, которые реально вызываются в командах
   (упаковщики makeself, CI-обёртки crossbuilder, docker — часто забывают),
   и раскрыты ли опции (многоточие «...» в команде = опции не проверяемы).
15. **Другой продукт / другая редакция шаблона.** Названия разделов
   без нумерации, роли «Заполняет/Проверяет» могут быть перевёрнуты, версии в шапках
   разные. Главные дефекты черновика ловятся механически: (а) имена подсистем и
   модулей в 6.5 не совпадают с 5/6.1/6.2/6.4 — там остались обозначения прежней
   версии продукта и модули из другого продукта;
   (б) в таблице требований значения скопированы не в ту строку (ОЗУ с текстом
   процессора), рекомендация меньше минимума; (в) в разделах 7–8 лежат примеры-спойлеры
   от другого продукта под заголовком «удалить спойлер»; (г) служебная переписка и
   «<вставить ссылку>» внутри текста. В отчёт добавить отдельный раздел «Готовность
   к передаче»: плейсхолдеры, статусы, служебные вставки, разделы к удалению.
16. **Сверка PREP.INFO с ЭД по продуктам с ролевой архитектурой.** Самое результативное — таблица
   портов и схема взаимодействия в руководстве администратора: в PREP.INFO порты почти
   всегда отсутствуют, а в ЭД есть полный перечень направлений (веб-интерфейсы,
   админские входы вроде pgAdmin/Grafana, внешние системы). Если в ЭД
   есть внешние системы на схеме, а в PREP.INFO только внутренние роли — это блокер п. 3.
   Проверять также: имена установочных архивов и сценариев (в PREP.INFO может быть
   несуществующее имя сценария вместо фактического), наличие модуля в ЭД
   (в PREP.INFO бывает компонент, которого в ЭД нет вовсе).
17. **Не приписывать ЭД того, чего в нём нет.** Перед замечанием «в ЭД есть, а в PREP.INFO
   нет» проверить grep по руководствам: перечней сообщений об ошибках в пользовательских
   руководствах обычно нет (только «отобразится сообщение об ошибке»), коды ответов
   есть только в руководстве разработчика. Отсылка PREP.INFO к «полному описанию ошибок»
   может вести на несуществующий раздел — это отдельное замечание.
18. **Вёрстка таблиц в HTML-отчёте.** Длинные идентификаторы без пробелов
   (слитные имена ролей и модулей, URL-пути API) растягивают таблицу за контейнер. Держать
   4 колонки в таблице замечаний (№, пункт, замечание с меткой характера, координаты),
   координаты писать сокращённо (PREP.INFO с. 4; рук. адм. с. 9–11) с легендой под таблицей,
   в ячейках писать имена с пробелами. После генерации проверять
   scrollWidth/clientWidth каждой таблицы через browser_exec.
19. **Сборка всех отчётов пакета сразу.** После изменения правил пересобирать все заключения
   одного пакета продуктов из их .md — иначе вердикты в них расходятся между
   собой и с правилами.

### Правила вердиктов (0.x) — применяются к каждому пункту

0.2. **П. 2.1 — сравнение количества, а не текста.** Дословное совпадение с ЭД не требуется.
   Требование: функциональных возможностей в PREP.INFO не меньше, чем в ЭД; больше — не минус;
   перечни не должны противоречить друг другу. Меньше — блокер с перечислением того, чего
   не хватает (пример: 6 функций против 8 в ЭД).
0.3. **П. 2.2 — сверка PREP.INFO с ЭД, и только.** Проверяется: (а) ОС и значения требований
   не противоречат ЭД; (б) нет расхождений между PREP.INFO и ЭД. Противоречия внутри самого
   ЭД (например, разные значения в таблице и на рисунке) в зачёт не идут и отдельным
   замечанием к PREP.INFO не оформляются. Если в ЭД есть ОС, которых нет в PREP.INFO (Debian
   и т.п.), писать «в ЭД указаны также …; в PREP.INFO они не приведены», без формулировок
   «я исключил» и без оценки этого решения — проверяющий ничего не исключает и не добавляет.
0.4. **П. 2.3 — в ЭД не обязаны быть все компоненты PREP.INFO.** В поставке бывает больше
   модулей (служебные пакеты, шины, сценарии). Отсутствие компонента в ЭД — примечание,
   вердикт остаётся «соответствует». Минусом остаётся только неполнота самого PREP.INFO
   (нет описания компонента). Направление расхождения называть «меньше/больше», а не «уже»
   (см. 0.12).
0.5. **П. 2.4 — ФБ и к продукту, и к ИС.** Оба варианта допустимы: ФБ самозащиты
   («ФБ_суть_меры») и ФБ, реализуемые для ИС (шифр меры). Наличие только «ФБ_…» — норма
   и вердикт «соответствует», замечание не пишется (см. 0.13). Рекомендация с техническими
   мерами ФСТЭК нужна только тогда, когда ФБ не сформулированы вовсе; организационные меры
   (шифры с индексом .0 — регламентация правил и процедур, назначение ответственных,
   разработка политик) не предлагать. Справочник мер — на bdu.fstec.ru (браузером);
   если он уже выгружен в локальный файл пар «шифр — название», искать по словам
   «инцидент», «регистрац», «аудит», «доступ», «аутентификац».
0.6. **П. 4 — порты не обязательны.** Внешний интерфейс описывается назначением, параметрами,
   действиями и ошибками; порт — желательное, но не обязательное поле. Если в ЭД есть перечень
   портов/направлений, оформлять это как рекомендацию с точными координатами («рук.
   администратора, табл. 2, с. 9–11 — стоит перенести»), а не как блокер. Блокерами остаются:
   незаполненные параметры/действия и пропущенные интерфейсы, меняющие поверхность атаки.
0.7. **П. 5 — механизм невозможности влияния.** Не блокер. В «Оценке» писать прямо
   «механизм не описан», вердикт — «соответствует»; рекомендации — отдельным блоком после
   вывода (см. 0.16). Формулировка приводится целиком, под конкретный продукт (порты, шина,
   хранилища, какие ФБ защищены), чтобы её можно было вставить в PREP.INFO без правки;
   в разделе замечаний механизм идёт с характером «рекомендация» — и в п. 5, и в п. 6.2.
0.8. **П. 6.1 — ссылка на ЭД только с координатами.** Любое утверждение «по ЭД модуль
   доступен/описан иначе» должно нести документ, раздел и страницу (например: «рук.
   администратора, разд. 3, с. 14»; «табл. 2, с. 9»). Без этого замечание не формулируется.
0.9. **Терминология: документ — PREP.INFO, не «анкета».** Слово «анкета» в отчётах и
   замечаниях не употреблять; координаты писать «PREP.INFO стр. N», «PREP.INFO, разд. 6.2».
0.10. **П. 2.1 без ЭД.** Служебные примечания в тексте и расхождение версий между пунктами
   (2.1 «3.3» / 2.3 «3.3.1450») — не минус и не «частично»: вердикт «соответствует»,
   это примечания к готовности. Если ЭД не приложен — добавить строку: рекомендовано
   сравнить PREP.INFO с ЭД после его представления, включая количество функций.
0.11. **П. 2.2 — «рекомендация меньше минимума» — не минус.** Наблюдение полезное, его
   стоит отметить (например, «4+1 ядро против минимума 8»), но на вердикт оно не влияет,
   если сами требования не противоречат ЭД. Остаются минусами только фактические ошибки
   (например, текст требований к процессору, продублированный в строке ОЗУ). Если ЭД
   не приложен — та же рекомендация сверить требования с ЭД.
0.12. **П. 2.3 — писать «меньше», а не «уже».** Формулировка: «состав в PREP.INFO меньше,
   чем в ЭД, — это ок, если разработка сверила перечень с дистрибутивом и это отражено
   в документе». Слово «уже» и оценка «это норма» вместо условия не годятся.
0.13. **П. 2.4 — шифры не обязательны.** Собственные имена ФБ («ФБ_суть_меры») без шифра
   меры — норма и право разработчика: это не минус и не примечание, замечание не пишется.
   Таблица «ФБ → подходящие меры ФСТЭК» допустима только как справочная, с прямой
   оговоркой «заполнение не требуется».
0.14. **П. 3 — номер и подпись рисунка не требуются.** Отсутствие нумерации, подписи и
   ссылки из текста на схему — не замечание: в шаблоне PREP.INFO этого нет.
0.15. **П. 4 — отсылки к документам не минус.** Если параметры и сообщения об ошибках даны
   отсылкой к руководству, это допустимо; писать требованием: «документы, на которые даны
   отсылки, должны быть приложены к PREP.INFO при передаче». Минусом остаются прочерки
   вместо параметров и пропущенные интерфейсы, меняющие поверхность атаки.
0.16. **П. 5 и 6.2 — механизма нет, и это не минус.** Писать прямо: «механизм невозможности
   влияния не описан» — без смягчений. Для вердикта это не основание для «не соответствует»
   и не повод для примечания: вердикт «соответствует», в таблицу замечаний — строка
   с характером «рекомендация». Рекомендации — отдельным блоком **после** вывода, жирным
   лидом, с готовой формулировкой для вставки в PREP.INFO.

## Сборка итогового отчёта

Когда пункты пройдены, отчёт собирается по образцу DIST.TST/DIST.FUZZ: `.md` + автономный
HTML тем же генератором (`dist-fuzz-report-check/scripts/md_report_to_html.py`, флаги
`--kicker`/`--footer`). Структура: шапка 6–7 строк `**Метка:** значение` (объект,
SHA-256, ЭД, объём, дата) → «Проверяемые требования» → «Итог»
(таблица «пункт / вердикт / основание») → «Проверка по пунктам» (Требование →
Что в документе → Оценка → Вывод) → «Сквозные проверки» → «Замечания»
(№ / пункт / замечание / характер / координаты в обоих документах) →
«Что требуется от разработчика» → приложения (карта портов, ФБ→подсистема→модуль,
средства проверки и «чего в материалах нет»).
Вердикты — из словаря генератора: «Не соответствует» (не принято),
«Соответствует частично» (принято с замечаниями), «Соответствует» (принято);
мелкие замечания входят в таблицу замечаний с пометкой «мелкое», но вердикт не меняют.
Имя файла — с префиксом продукта/модуля (`<продукт>-prep-info-review-report.*`),
класть рядом с материалами на шаре.

**Блок рекомендаций — отдельно от вывода.** Рекомендация внутри «Оценки» теряется
и спорит с вердиктом «соответствует». Правильно: «Вывод» → блок
`**Рекомендации (к заполнению, не блокируют приёмку):**` → нумерованные пункты,
каждый с жирным лидом и готовой формулировкой для вставки в PREP.INFO
(в т.ч. про механизм невозможности влияния — один и тот же текст в п. 5 и в 6.2,
а в таблице замечаний одна строка с характером «рекомендация»).

**Арифметику отчёта считать скриптом, а не печатать руками.** После каждой
правки пересчитывать: (а) строки таблицы замечаний по характеру — для строки
«Итого N замечаний: …»; (б) группы вердиктов — сумма «соответствует + частично +
не соответствует» обязана равняться числу проверенных пунктов. Ошибка в этих
двух строках — первое, что бросается в глаза, и она повторяется при каждой
перестановке характеров замечаний.

**Перенумерация после правки таблицы.** Удаление или замена строки в таблице
замечаний оставляет дыры (17 → 19), а вставка даёт дубли. После правки
перенумеровать строки подряд скриптом от заголовка раздела «Замечания» до
строки «Итого», потом пересчитать итог (см. выше).

**Массовая замена терминов.** Замена «анкета» → PREP.INFO по всему файлу
задевает заголовок, шапку «Объект проверки» и легенду сокращений: получается
«# Заключение по PREP.INFO PREP.INFO: …», «PREP.INFO «PREP.INFO — …»»,
«Сокращения: «PREP.INFO» — <имя файла>.pdf». После замены грепнуть `PREP.INFO PREP`
и «Сокращения» и починить эти три места руками.

## Ссылки в замечаниях

Каждое замечание — с координатами в обоих документах: пункт + страница (и номер
таблицы) в PREP.INFO и раздел + страница (и номер таблицы) в ЭД. Без этого
замечание невоспроизводимо. В журнале для портов ведётся сводная карта
«порт → PREP.INFO (пункт/стр.) → схема → ЭД (стр./табл.) → расхождение»:
один и тот же перечень портов встречается в 2.2, на схеме п. 3 и в ЭД, и
сводить их надо построчно, а не текстом.

## Чтение материалов

- `pdftotext -layout file.pdf out.txt` — текст; постранично (`-f N -l N`) — карта
  разделов для ссылок на страницы.
- `pdfimages -list file.pdf` — какие схемы есть на самом деле: раздел
  «Архитектура» и «Тестовые стенды» часто заполнены только картинкой, и пустой
  текст там не означает пустой раздел.
- Сравнение редакций: вырезать блок пункта из старой и новой версии и
  `diff -u` — видно, что именно изменили, и не приписывать новому документу
  унаследованные дефекты.
- Журнал проверки — таблица «пункт / кто заполняет / статус / замечания» в
  файле `review-log.md` рядом с извлечённым текстом (в рабочем каталоге проверки):
  сессия сжимается, статусы по 15 пунктам из истории не восстановить.

## Типовые дефекты шаблона

- Шапки всех блоков несут версию из предыдущей итерации («Информация актуальна
  для: X») — сверять с версией в заголовке документа.
- Плейсхолдеры «<указать ответственного>» и статусы «НЕ НАЧАТО» остаются во всех
  блоках: до сдачи ответственный и статус должны быть заполнены.
- Примечания продублированы: текст внутри раздела, а штатный подпункт «N.N.1
  Примечания» пуст.
- Подпункты 8.1/8.2 заполняет Cert, проверяет Dev — роли зеркальны относительно
  остальных пунктов (уточнить, так ли задумано).

## Критерии готовности проверки

- По каждому пункту: критерий, что фактически в документе (стр./строка),
  замечания, вердикт «принято / принято с замечаниями / не принято».
- Блокирующие замечания отделены от текстовых.
- `review-log.md` заполнен по всем пройденным пунктам.
