# Проверка материалов модульного тестирования (комплект DIST.TST)

Класс задач: разработчик передал каталог или архив с результатами модульного
тестирования компонентов продукта (сторонние библиотеки, собственный код,
встроенный рантайм), а испытательной лаборатории нужно проверить его на
соответствие «Методике выявления уязвимостей и недекларированных возможностей»
(Методика ВУ): ПОД.2 усиления 1–2, ДАО общие требования, ДАО.1 и усиления 1–5.

Скилл проверяет материалы, а не проводит тестирование. Главный принцип тот же,
что в `dist-fuzz-report-check`: **все числа считать из первичных
артефактов** (`junit.xml`, журналы прогонов, `coverage-summary.csv/json`,
`lcov.info`, `failures.csv`, `rerun/`, `causes/`), а не переписывать из
`readme.txt`. Readme — заявление стороны, его проверяют.

Скилл не привязан к конкретному продукту: состав компонентов определяется
автоматически по каталогам в комплекте, порог покрытия настраивается, объём
проверки задаётся в отчёте. Ничего про конкретные продукты, компоненты и
требования заказчика «на этот раз» в нём не зашито.

**Объём заключения задаёт пользователь, а не скилл.** Типовой запрос — пара
документов: заключение по полным требованиям Методики ВУ и отдельная проверка
**заявленного описания** (README/description разработчика) — таблица «заявление →
подтверждается / не подтверждается → артефакт», включая версии инструментов и
контрольные суммы. Второй документ не дублирует первый: в нём оцениваются только
утверждения описания.

Заказчик часто сужает объём до **одного** документа, например: «оставим общие
требования — порог покрытия для компонента в целом, „тестирование модулей со
съёмом кодового покрытия“, отметить инструменты». Тогда сдаётся один файл, а не
пара, со структурой: проверяемые требования (с формулировками) → итог → съём
покрытия → покрытие по компонентам → инструменты → замечания → что запросить.
Блоки, которых не просили (ПОД.2, ДАО.1 «а»–«г», усиления), в такой документ не
добавлять «для полноты» — лишний объём заказчик вычитывает как спор с его
постановкой.

Комплекты бывают двух видов, и проверяются они по-разному:
- интерпретируемый код (JS/TS, Python и подобное) — «спецсборка с датчиками» =
  запуск интерпретатора с дополнительными опциями, покрытие c8/Istanbul/coverage.py;
- компилируемый код (C/C++) — настоящая инструментированная сборка ASan/UBSan и
  покрытие gcovr; разбор такого комплекта — `references/sanitizer-build-evidence.md`.

Текст требований — `references/dist-tst-requirements.md` (встроен; при типовой
проверке запрашивать не нужно). Переиспользование чужих результатов тестирования
(«те же версии, взять из DIST.TST другого продукта») — `references/reuse-across-products.md`.

## When to Use

- Пришёл каталог с результатами модульного тестирования (обычно `DIST.TST`) —
  нужно заключение по блокам требований.
- Нужно пересчитать покрытие по компонентам и проверить порог (по умолчанию 25 %).
- Нужно разобрать не прошедшие тесты и оценить, годится ли триаж разработчика.
- Нужно понять, чего в материалах нет, и сформулировать запрос разработчику.
- Нужна повторная проходка («проверь ещё раз») с новыми сверками.
- Сторонние компоненты в комплекте не тестировались: README утверждает, что
  версии совпадают с другим продуктом и результаты можно переиспользовать.
- Не для: проведения самих тестов; фаззинга — это
  `dist-fuzz-report-check`.

## Prerequisites

- Материалы обычно лежат на общей папке VMware (`Work_bags`). Смонтировать:
  ```bash
  sudo mount -t fuse.vmhgfs-fuse .host:/Work_bags /mnt/hgfs -o allow_other
  ```
  Читать с шары медленно — скопировать комплект в рабочий каталог локально
  (типовой комплект десятки мегабайт, распаковка не нужна).
- `python3` (stdlib: `csv`, `json`, `xml.etree`, `argparse`), `markdown` для
  HTML-версии.
- Рабочий каталог — в `~/work/fuzzcheck/<продукт>-tst-<ГГГГ-ММ>/`.

## Quick Reference

```bash
S=~/.hermes/profiles/<профиль>/skills/certification/dist-tst-report-check/scripts

# 1) инвентаризация: dataset.json + сводная таблица (компоненты находятся сами)
python3 $S/tst_dataset.py <каталог материалов>

# 2) сверка заявлений readme с артефактами (тесты, сбои, пропуски, строки/ветви/функции)
python3 $S/recheck_claims.py <work> --threshold 25

# 3) независимые сверки пар источников: csv <-> json, baseline <-> sensors,
#    атрибуты tests в junit по каждому набору, даты и архитектура
python3 $S/crosscheck_artifacts.py <work>

# 4) целостность и полнота комплекта: манифест, битые ссылки index.html, профили покрытия
python3 $S/package_audit.py <каталог> --threshold 25

# 5) MD -> автономный HTML (общий генератор с DIST.FUZZ; путь считается от $S,
#    поэтому имя профиля и каталог установки значения не имеют)
python3 "$(dirname "$S")/../dist-fuzz-report-check/scripts/md_report_to_html.py" <отчёт>.md

# надзаголовок генератор берёт свой (фаззинг) и параметра для него нет — заменить в готовом HTML:
sed -i 's|<p class="kicker">[^<]*</p>|<p class="kicker">Проверка материалов модульного тестирования · Методика ВУ</p>|' <отчёт>.html
```

Объём проверки задаётся не правкой скриптов, а флагом:
`--exclude <компонент>` (можно повторять) — компонент остаётся в материалах, но не
входит в агрегаты и таблицы отчёта. Порог — `--threshold <проценты>`.

## Procedure

1. **Разложить требования на проверяемые утверждения** — по блокам:
   A) ПОД.2-У1 (сборочная среда, модификации кода, САСТ 4.2, ЭКО 4.4, 10 000
   инструкций); B) ПОД.2-У2 / ДАО.1 «б» (архитектуры); C) ДАО-общие (датчики,
   отсутствие обфускации, механизмы противодействия анализу); D) ДАО.1 «а»–«г»,
   п. 4.3.2 и контрольная выборка; E) усиления 1–5; F) структурное покрытие в
   приложении. Каждому — артефакт-доказательство и способ проверки.
   *Готово, когда* у каждого пункта есть «что искать / где / чем доказать».
2. **Инвентаризация.** Число компонентов, состав `results/`, наличие `junit.xml`,
   `coverage-summary.csv`, `environment.txt`, `source.txt`, `tarball-vs-tag.txt`,
   `git-status-*`, каталогов `_*attempt*`, `rerun/`, `causes/`. Зафиксировать
   SHA-256 манифеста (`find -type f | sort | xargs sha256sum | sha256sum`). Даты
   файлов на общей папке ничего не доказывают: при повторном копировании mtime
   обновляется у всего комплекта, поэтому «изменилось / не изменилось» решает
   только хеш манифеста. Если есть `MANIFEST.sha256` — проверить его
   (`shasum -a 256 -c MANIFEST.sha256 | grep -v ': OK$'`) и битые ссылки
   `index.html` (`scripts/package_audit.py`): файл из манифеста, которого нет в
   архиве, почти всегда означает изъятый документ (например, оценку находок).
   *Готово, когда* известно, по каким компонентам есть машинные результаты.
3. **Собрать `dataset.json`** скриптом `scripts/tst_dataset.py` (разбор JUnit по
   `<testcase>`, `coverage-summary.csv`, `coverage-summary.json`,
   `environment.txt`, `source.txt`, `tarball-vs-tag.txt`). Компоненты берутся из
   каталогов комплекта — список не хардкодить.
   *Готово, когда* получена таблица «компонент × тесты × сбои × пропуски ×
   покрытие × минимум по файлу × покрытие функций» из первичных данных.
4. **Сверить readme с артефактами** по каждому компоненту: число тестов, сбои,
   пропуски, покрытие строк/ветвей/функций, даты, коммиты/теги. Расхождения
   вынести в отдельный раздел отчёта, а не сглаживать.
   *Готово, когда* для каждого числа в отчёте есть источник или пометка
   «из readme, не подтверждено».
5. **Проверить тождество «тестируемый код = поставляемый»** по типу компонента:
   библиотека → `tarball-vs-tag.txt` / `built-vs-published.txt` (для собранных из
   TS); встроенный рантайм → `embedded-vs-source.txt`; собственный код →
   контрольные суммы до/после. Отдельно зафиксировать, что сверка **не** даёт:
   для TS-компонента тесты исполняют исходники, а не итоговый бандл.
6. **Разобрать прогоны и находки.** Для каждой библиотеки — профили `baseline` и
   `sensors` (коды возврата, срабатывания датчиков в журналах). Для крупного
   рантайма — `failures.csv`, `failures-analysis.txt`, `rerun/<режим>`, `causes/`:
   проверить, что каждый не прошедший тест классифицирован и перезапущен в
   штатных условиях. Сохранённые неудачные попытки (`_*attempt*`) и их разбор в
   readme — довод в пользу добросовестности.
7. **Пересчитать покрытие в двух срезах.** (1) **Агрегат по компоненту** —
   `Σ covered / Σ total` по всем его файлам: это основной критерий, если
   требование читается как «модуль = компонент целиком» (типовая трактовка
   заказчика, пофайловый порог прямо не заявлен). (2) Минимум по файлу и число
   файлов ниже порога — **справочно**, как запас прочности, а не как основание
   для «не соответствует». Плюс покрытие **функций** (`functions` в
   `coverage-summary.json`) и вид покрытия (строки/блоки). В таблицу выводить
   «покрыто/всего → процент → запас к порогу»: запас (`pct / 25`) сразу
   показывает дистанцию и снимает спор о трактовке.
8. **Оценить полноту набора.** Есть ли SBOM/перечень модулей продукта с
   атрибутами поверхности атаки и ФБ; какие модули охвачены, какие нет (например,
   C/C++-часть рантайма); заявлен ли перечень поддерживаемых архитектур и чем
   подтверждён.
9. **Проверить контрольную выборку.** Число тестов со сбоями и число модулей, к
   которым они относятся: если тестов со сбоями < 50 или модулей < 5, выборка по
   требованиям ДАО.1 не составляется — это отдельный вывод, а не «выполнено
   формально».
10. **Собрать отчёт** в объёме, который задал пользователь (пара документов или
    один), по структуре: итоговое заключение (таблица вердиктов) → состав
    материалов → проверка по блокам (требование / что в материалах / оценка /
    вывод) → сводка «что проверено — чем подтверждено» → **инструменты** (по
    компонентам: тестовый фреймворк, инструмент съёма покрытия и чем
    зафиксировано — `_scripts/libs/*.env`, `results/tools.txt`, `results/run.log`;
    отдельно перечень датчиков и чем проверяла лаборатория) → расхождения и
    замечания → что запросить → приложения (сводные таблицы, разбор сбоев, карта
    артефактов). HTML — общим генератором из DIST.FUZZ.
11. **Сверить текст с данными программно** (числа с разделителями тысяч,
    проценты с запятой) — объём отчёта глазами не проверяется.
12. **Сдать в ту же папку, откуда взяты материалы**, с префиксом модуля:
    `<модуль>-tst-report.md/.html`, `<модуль>-tst-dataset.json`. Общие имена
    `report.md`/`dataset.json` затирают прошлые заключения. Если сдаточный
    документ один — `<модуль>-tst-report.md/.html`; устаревшие и подробные версии
    не удалять, а переносить в `archive/` рядом с материалами: несколько файлов
    `*-report-*` в папке заказчика читаются как спорящие заключения.

## Повторная проверка («проверь ещё раз»)

Запрос повторной проверки — это новая проходка, а не пересказ прежнего
заключения. Порядок:

1. **Идентичность материалов** — хеш манифеста против прошлой проверки. Совпал:
   так и написать («материалы побайтно идентичны»), но проверку всё равно
   выполнить заново: заказчику нужен свежий разбор, а не ссылка на старый.
2. **Свежий рабочий каталог** — `<продукт>-tst-<ГГГГ-ММ>b`, копия материалов,
   `tst_dataset.py`, `recheck_claims.py`, `crosscheck_artifacts.py`.
3. **Сверки, которых в первом проходе обычно нет** — пары источников, чтобы
   исключить ошибку одного артефакта: readme ↔ `junit.xml`; readme ↔
   `coverage-summary.csv`; CSV ↔ `coverage-summary.json`; `baseline` ↔ `sensors`;
   атрибуты `tests` ↔ `<testcase>` по каждому набору; даты и архитектура из
   `environment.txt`; пофайловые минимумы и число файлов ниже порога.
4. **Отчёт:** добавить раздел «что дополнительно сверено при повторной проверке»
   (таблица «пара источников → результат») и явную строку «выводы не изменились /
   изменились, потому что …». Новые замечания нумеровать в общей
   последовательности отчёта, а не дописывать пометкой сверху.
5. **Файлы сдавать заново:** ранее сданные отчёты заказчик мог убрать из папки с
   материалами; проверить `ls` и скопировать актуальную версию, прежние — в
   `archive/`.

Признак добросовестной повторной проходки — новое замечание либо явное «к
прежним расхождениям ничего не добавилось» из перечня сверок; пересказ прежнего
текста читается как невыполненная работа.

## Переиспользование результатов другого продукта

Типовая ситуация: в комплекте продукта B сторонние компоненты не тестировались,
README утверждает «версии те же, что в продукте A, результаты можно взять из его
DIST.TST». Проверять три вещи по отдельности: **версии**, **тождество артефактов**,
**полноту перечня**. Первые две обычно сходятся, третья — нет. Подробный разбор с
готовыми командами — `references/reuse-across-products.md`.

1. **Версии** — не по таблице README, а по `results/installed-deps.json`
   (вложенное дерево `dependencies`), сверяя с каталогами `<pkg>-<semver>/` и
   строками «Библиотека: …» в ` readme.txt` комплекта-донора. Считать по всему
   дереву, включая транзитивные парсеры ввода (`qs`, `raw-body`, `path-to-regexp`,
   `send`, `iconv-lite`).
2. **Тождество** — для рантайма только хешем бинарника: `sha256` обычно
   зафиксирован в `environment.txt`/`run.log` донора, значит совпадение
   проверяется без самого бинарника. Совпадение имени версии без хеша — не довод:
   сборка под другую libc даёт другой код.
3. **Полнота** — собрать импорты из исходников (текст файлов есть внутри
   HTML-отчёта покрытия) и посмотреть, какие пакеты принимают данные от клиента:
   кука → разбор часового пояса/локали, название отчёта → шаблон, путь из URL →
   отдача статики. Такие пакеты — поверхность атаки независимо от того, что их
   считают «служебными». Внешние процессы (`spawn`/`exec`), замоканные в тестах,
   тоже не тестированы и в перечне README обычно отсутствуют.

В отчёт — три вывода: заявленные компоненты (правомерно), неназванные, но
совпадающие (результаты тоже применимы — нужно дополнить таблицу), не покрытые
ни одним продуктом (**не подтверждено материалами**: нужны тесты компонента либо
запись в SBOM/протоколе, что он не относится к поверхности атаки). Обязательная
оговорка: при переиспользовании в протокол переносятся и чужие сбои/пропуски
донора — их надо назвать числом, а не «взять итог».

## Комплект с компилируемой сборкой (C/C++, ASan/UBSan)

Если тестируется C/C++, доказательства другие: датчики настоящие, и центр
проверки смещается с «есть ли датчики» на «что они нашли и как оценено». Полный
набор команд, таблица вердиктов и ловушки — `references/sanitizer-build-evidence.md`.
Коротко: `-fsanitize` по всем командам компиляции → рантаймы в `DT_NEEDED` →
контрольные программы (чистая/asan/ubsan) → тождество исходников (`debian/patches`
пуст) → покрытие по профилям (`combined` для требования) → сходимость
`occurrences` = `sanitizer_diagnostic_events`.

## Вердикты

Тот же словарь, что в DIST.FUZZ: **Соответствует** / **Соответствует частично**
(«N из M») / **Не соответствует** / **Не подтверждено материалами** / **Вне
области проверки комплекта**.
Формулировать про материалы («материалы не содержат …»), а не про людей.
Практика: отсутствие описания сборочной среды, перечня архитектур или SBOM —
это «не подтверждено материалами» (запрос артефакта), а не «не соответствует»
(переделка работы). Если пользователь указал, что документ существует отдельно
(«описание сборочной среды, архитектуры и SBOM лежат в другом месте»), вердикт по
этим блокам — **«вне области проверки комплекта»**, а в отчёт идёт таблица
«артефакт → в каком документе находится → как учтён». Отсутствие чужого документа
в комплекте дефектом материалов не считается.

## Что обычно отсутствует (типовые пробелы)

- Описание сборочной среды и системы сборки ОО и реестр инструментов,
  модифицирующих код (ПОД.2-У1) — материалы описывают стенд тестирования, а не
  сборку продукта.
- Доказательство перечня поддерживаемых архитектур («поставляется только для
  одной архитектуры» без ссылки на документ).
- SBOM/перечень модулей продукта — метки `attack_surface`/`security_function`
  цитируются «по SBOM», но SBOM не приложен, полнота набора непроверяема.
- Сопоставление OSS-модулей с методиками пп. «м» п. 2.3 (усиление 2).
- Механизмы, препятствующие динамическому анализу: нет ни выявления, ни
  утверждения об отсутствии.
- Доказательство отсутствия обфускации/минификации для собственного компонента
  (для сторонних библиотек оно есть — побайтная сверка пакета).
- Триаж при большом числе сбоев и наоборот — мало сбоев для контрольной выборки.

## Pitfalls

- **`tests` в JUnit ≠ число `<testcase>`.** Вложенные `testsuite` дают двойной
  счёт при суммировании атрибутов (встречалось: 116 по атрибутам верхнего уровня,
  121 по всем наборам при 120 фактических тестах; родительский набор объявляет
  22 при 26). Бывает и обратное: родительский набор объявляет **число вложенных
  наборов** вместо числа тестов (12 при 72 фактических, 2 при 23), тогда сумма
  атрибутов завышает итог (1 791 против 1 760). Считать элементы `<testcase>`,
  `failure`, `skipped`; сравнивать атрибуты каждого набора с суммой своих и
  вложенных `<testcase>`, а не только суммарно — иначе дефект увидит лишь тот,
  кто посмотрит на дерево. Готовый разбор — `scripts/crosscheck_artifacts.py`.
- **Два разбора одного TAP дают разные итоги.** Встречается регистрозависимое
  регулярное выражение `#\s*(SKIP|TODO)`, тогда как TAP печатает `# skip`
  строчными: строки отбрасываются целиком, сводка занижает число тестов и
  показывает «пропущено: 0». Сверять `tap.txt` ↔ `junit.xml` ↔ `test-summary.txt`;
  истина — вариант с `/i` (обычно JUnit).
- **`c8 --check-coverage --lines 25` без `--per-file` — агрегат по компоненту.**
  При трактовке «порог для компонента в целом» такая настройка **соответствует**
  требованию, и замечанием её не делать: одной строкой зафиксировать «порог задан
  агрегатно, совпадает с трактовкой». Замечанием это становится только если
  требование прямо пофайловое. Независимо от настройки считать из
  `coverage-summary.csv` оба среза — агрегат по компоненту и минимум по файлу.
- **`branches` у c8/Istanbul ≠ базовые блоки.** Если требование про строки,
  закрывается строками; про базовые блоки писать «не собирались», а не «покрыты
  ветви».
- **Покрытие функций — не в CSV.** В `coverage-summary.csv` только строки;
  `functions` берутся из `coverage-summary.json` (`total.functions.pct`).
- **Для TS-компонента сверка идёт по исходникам.** Тесты исполняют `.ts` через
  трансформер, поставляется бандл; утверждение «минификации нет» без конфигурации
  сборки недоказуемо. Не путать с библиотеками, где сверка побайтная.
- **Пропуски тестов бывают законные и невидимые.** `it.skip` в коде тестов,
  платформенные и debug-only проверки, «неприменимо в этой среде» — каждому
  нужна причина в материалах; иначе это пробел «анализа журналов».
- **Метку SBOM читать вместе с «рекомендованной разметкой».** Строка меток в
  readme может содержать два слоя: `GOST по SBOM: attack_surface = no,
  security_function = no` и тут же «в рекомендованной разметке security_function =
  yes … тестируется как модуль ФБ». Брать только атрибут SBOM нельзя — получится
  неверный вывод «компонент не относится к ФБ/ПА». Правильно: вердикт по
  рекомендованной разметке, а расхождение с SBOM — отдельное замечание (SBOM
  требует исправления, иначе ломается трассировка ФБ → модуль).
- **Метку или цитату из материалов давать с путём и номером строки.** Вопрос «где
  это написано?» приходит на каждой спорной метке, поэтому ответ готовится
  заранее: `nl -ba <файл> | sed -n '1,10p'` и `grep -n` по ключу — для обеих копий
  (шара `/mnt/hgfs/...` и рабочая) плюс `sha256sum`, чтобы цитата относилась
  именно к проверенному файлу. Двухслойные строки разметки часто стоят подряд
  (строки 2 и 3), поэтому печатать блок строк, а не одну найденную.
- **Формулировки readme у компонентов разные, шаблон якорить на название
  метрики.** Встречается «пропущено: 4» рядом с «пропущенных: 0», «Покрытие
  строк: 335 из 335 = 100 %», отдельные строки «Покрытие ветвлений: 98,85 %» и
  «Покрытие функций». Общий шаблон `покрытие[^\n]*?([\d,.]+)\s*%` подхватывает
  ветвления раньше строк и даёт ложное расхождение (98,85 против 100 %). Брать
  `r'Покрытие строк\s*:\s*(\d+)\s*из\s*(\d+)'`, `r'Покрытие ветвлен\w*\s*:'`,
  `r'Покрытие функций\s*:'` и `r'пропущен\w*\s*:\s*(\d+)'`; шаблон не нашёлся —
  писать «заявление не распознано, проверить глазами», а не «расхождение».
- **Мало сбоев — не плюс, а проблема выборки.** Контрольная выборка требует
  ≥ 50 тестов со сбоями и ≥ 5 модулей: материалы с единичными сбоями в одном
  компоненте её не позволяют.
- **Порог «≥ 25 %» и «все модули» — разные проверки.** Первый — покрытие, второй —
  охват; модуль без тестов попадает в покрытие с 0 % только при `--all`.
- **Ограничение охвата рантайма фиксировать явно.** Для встроенного рантайма
  покрытие снимается только по его собственным модулям на основном языке;
  C/C++-часть и наборы `cctest`/`addons`/`node-api` могут не выполняться (нет
  компиляторов) — это граница охвата требования «а».
- **Датчики для интерпретируемого кода — рантаймовые флаги.** «Специальная
  сборка» = тот же образ с `NODE_OPTIONS`/`PYTHONWARNINGS`; так и формулировать в
  протоколе, не выдавая за инструментированную сборку.
- **Отказ от датчика должен быть доказан журналом.** Смена одного флага на
  другой (например, `--throw-deprecation` → `--trace-deprecation`) законна, если
  сохранены неудачные попытки и показано, что устаревший API — в коде тестов, а не
  библиотеки.
- **Вывод датчиков в `log_path` обесценивает проверку внутри тестов.** При
  `ASAN_OPTIONS=…:log_path=…` сообщения пишутся в отдельные файлы, а не в
  `error.log`, поэтому проверка вида «в error.log нет строк с Sanitizer» проходит
  всегда (встречалось: 419 `ok` при 548 фактических диагностиках). Следствие —
  теряется привязка «тест → диагностика», и контрольную выборку по материалам не
  составить. Проверять сходимость этих двух чисел.
- **Манифест — детектор изъятого документа.** `shasum -a 256 -c` с расхождениями
  вида «документ указан, файла нет» и «README правился после сборки манифеста».
  Отсутствие в манифесте оценки находок — прямое указание, что она не приложена (и
  на неё обычно ссылается `index.html` битой ссылкой). Проверять ссылки сводной
  страницы.
- **Два комплекта покрытия в одном пакете — сверять знаменатели.** Проценты
  почти совпадают, а `line_total` по файлам расходится (80 660 против 79 655
  строк, ветви 56 196 против 50 524) — это разные сборки или версии gcovr.
  Сравнивать по файлам, а не по итогу, и требовать указания, какой прогон считать
  результатом.
- **Версия gcovr из README не равна версии пакета.** Debian-версия вида
  `7.2+really-1.1` означает фактическую 1.1, хотя README пишет «7.2». Сверять с
  `dependencies.tsv` и не переписывать версию из описания.
- **`dpkg-source -x` не применяет Debian-патчи.** Утверждение «тестировался тот
  же исходный код» верно только при пустом `debian/patches`; иначе сначала
  применить патчи и сверять уже пропатченное дерево.
- **`objcopy --redefine-sym main=…` — вмешательство в объектный файл.** Так
  линкуют unit-стенд; на поставляемый бинарник это не влияет, но в отчёте
  фиксировать как модификацию сборки, а не умалчивать.
- **Не читать `summary.json` / `sanitizer-findings.json` через `cat`.** gcovr-сводка
  на сотни килобайт обрезается в выводе и забивает контекст; агрегировать из
  Python (число файлов, минимум, число файлов ниже порога).
- **Числа в отчёте сверять программно** и с теми же разделителями тысяч, что в
  тексте (`9 858`, `122 481`), иначе сверка даёт ложные пропуски.
- **Состав проверки задаётся флагом, а не правкой скрипта.** Если компонент не
  входит в объём — `--exclude <компонент>`; агрегаты при этом пересчитываются из
  `dataset.json` заново (тесты, файлы, `covered/total`, процент, минимум), потому
  что итог не равен «старый итог минус строка» при округлении. После правки —
  `grep` по старым итогам и по имени компонента: допустимы только явные записи об
  исключении в «Границах проверки» и в пункте «что записать в протокол».
- **«Нет данных о компоненте» ≠ «требование нарушено».** Наличие компонента
  доказывается адресом и номером строки (`results/tools.txt` — это вывод
  `npm ls --depth=0`; `results/run.log` — то же дерево в журнале прогона;
  `installed-deps.json` — `grep -n '"<pkg>"'`; импорты с номерами строк из HTML
  покрытия), а обязанность его тестировать — внешним документом (Методика: все
  модули, реализующие ФБ; либо SBOM с разметкой). Смешав эти два утверждения в
  одну фразу, получишь встречный вопрос «где написано, что они должны быть
  включены», и замечание выглядит надуманным. В отчёте — «неопределённость
  охвата», в запросе — «просим результаты либо разметку», плюс оговорка, что
  вопрос не блокирует приёмку собственного компонента. Готовые формулировки —
  `references/reuse-across-products.md`, §6.
