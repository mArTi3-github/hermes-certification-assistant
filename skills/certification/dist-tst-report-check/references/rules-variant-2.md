# Проверка по правилам «вариант 2»: результат на каждое требование

Так выглядит вторая редакция правил заказчика: заказчик пересылает свой текст
(пп. 1–5 — определение типа компонентов, модули собственной разработки,
заимствованные компоненты, формирование результатов, правила проведения проверки)
и просит отчёт «по ним». Отличается от прежнего формата тремя вещами: результат
ставится **на каждое требование отдельно**, статусов ровно четыре, и входным
документом объявлен **план проверки заимствованных модулей**.

## 1. Каркас отчёта

1. **Ограничение проверки — отдельным разделом сразу после шапки.** Не прятать в
   замечания: правила требуют сообщить об отсутствии плана прежде выводов.
2. **Итог** — таблица `пункт | требование | результат | компонентов`. Номер берётся
   не из правил, а по своей схеме: **«п. 1» и «п. 2»** — требования методики
   (покрытие > 25 %, метод сбора), затем **«1», «2», «3», «4»** — дополнительные
   требования А–Г. В колонке «компонентов» полезно писать счёт: «10 из 10»,
   «9 — не применимо, 1 — не подтверждено».
3. **Общие требования (пп. 1–2)** — по таблице на требование, строки = компоненты.
4. **Требований плана в перечне нет.** Заказчик просит их из требований убрать
   (встречалось: «убери из требования»): документ отсутствует, поэтому ни строки в
   итоге, ни отдельного раздела — только «Ограничение проверки» (п. 1) и замечание.
5. **Дополнительные требования (1–4): А** режимы, **Б** журналы, **В** покрытие,
   **Г** анализ ошибок. Внутри А таблица `компонент | сборка | санитайзеры |
   отладочные проверки | режим покрытия` — подписи А1/А3/А4/А5 не оставлять; наборы
   параметров и раздельное тестирование (бывшие А2/А6) — отдельными абзацами под
   таблицей: они либо одинаковы для всех, либо неприменимы сразу всем.
6. **Замечания** — нумерованные, каждое с файлом и фрагментом.
7. **Что запросить** — только артефакты.
8. **Приложение «Программные средства»** — обязательно и в этой редакции.

## 2. Поля результата

Правила требуют на каждое требование пять сведений: проверяемое требование,
результат, фактические сведения, доказательства (файл и фрагмент), замечание.

Реализация без раздувания: **текст требования — в заголовке подраздела (дословно),
таблица — `компонент | результат | фактические сведения | доказательства |
замечание`**. Требование в каждой строке не повторять — одиннадцать копий одной
фразы и есть «нагромождение».

Статусы — ровно четыре слова: **Соответствует / Не соответствует /
Не подтверждено / Не применимо**. «Соответствует частично» в этой редакции нет:

- выполнено в ослабленном объёме, и это доказано журналами → «Соответствует» +
  замечание (пример: строгий датчик заменён на трассирующий, попытки сохранены);
- выполнение не доказано → «Не подтверждено»;
- артефакты противоречат требованию → «Не соответствует»;
- условие требования не наступило, и это установлено по артефактам → «Не применимо».

Вердикт ставить **первым словом ячейки** — по нему генератор HTML красит ячейку;
метки `@@…@@` не использовать.

## 3. План проверки заимствованных модулей — гейт

Правила делают план основным источником состава компонентов. Если документа нет:

1. проверить отсутствие по именам файлов (`*план*`, `*plan*`, `*ППЗМ*`) и по
   ссылкам в `readme.txt` — поиск по содержимому тоже, не только по именам;
2. написать в отчёте: план не представлен, требования плана проверить и учесть
   нельзя, поэтому в перечень проверяемых требований они не включены;
3. зафиксировать, что **окончательный вывод о полноте не формируется**, а состав
   определён по фактически представленным комплектам;
4. внести план первым пунктом в «что запросить» и повторить в замечании со ссылкой
   на отсутствие файла; строку «Не подтверждено» по требованиям плана **не
   заводить** — иначе пункт возвращается в требования;
5. проверку общих требований (пп. 1–2) и дополнительных (1–4) выполнить — правила
   это прямо разрешают, но с пометкой ограничения.

## 4. Санитайзеры и отладочные проверки — по типу кода

| Что тестируется | Требование | Какой вердикт ставить |
|---|---|---|
| JS/TS-библиотека | `-asan/-msan/-race` | «Не применимо» с обоснованием по составу пакета |
| JS/TS-библиотека | отладочные проверки | «Соответствует», если в `_scripts/libs/*.env` есть `NODE_OPTIONS` и прогон `sensors` прошёл |
| Рантайм (Node.js) — **есть код на C/C++** | `-asan/-msan/-race` | «Не подтверждено», а не «не применимо»: инструментировался только JS-набор |
| Рантайм, отладочные флаги не включались | отладочные проверки | «Не подтверждено»: роль датчика (assert-проверки, контроль раннера) — объяснение, но не выполнение |
| Наборы параметров сборки | доп. 1 (А) | один `environment.txt` на всех → «Не подтверждено», пока нет документа о конфигурациях ОО |

Ошибка, которая стоит вердикта: пометить санитайзеры «не применимо» для рантайма,
потому что тесты на JS. Код на C/C++ в компоненте есть, требование к нему
применимо, а доказательств нет — это «Не подтверждено» и запрос прогонов C/C++
части либо документа об области проверки.

## 5. Анализ ошибок (доп. 4, Г)

Разбирать по подпунктам, по одному вердикту на каждый: оценка значимости → уровень
критичности → исправления и БДУ (для уровня выше «Влияние отсутствует») →
развёрнутое обоснование и его привязка к конкретной проблеме.

- случаи есть только у одного компонента → у остальных «Не применимо» (сбоев нет),
  а не пустая ячейка;
- «Не применимо» по исправлениям и БДУ обосновывать числом случаев выше уровня
  «Влияние отсутствует» (ноль) и файлом, где это видно;
- привязку обоснования к конкретной проблеме подтверждать поимённым разбором
  (таблица «тест → причина → связь с кодом ОО»), а не группировкой: группировка
  отвечает «почему», но не «к какой проблеме относится».

## 6. Чего не делать (п. 5 правил)

- не добавлять пороги и критерии, которых нет в правилах и плане (ZIP-архив, число
  архитектур, «полнота SBOM» — только если требование названо);
- readme — заявление, а не доказательство: все числа из первичных артефактов;
- отсутствие доказательства не превращать в «не соответствует»;
- неприменимость обосновывать составом кода, а не удобством;
- противоречия между материалами — отдельными замечаниями, а не сглаживанием.

## 7. Два отчёта вместо одного: собственные модули и заимствованные

Запрос «раздели на модули продукта и заимствованные» — это **два самостоятельных
заключения**, а не один документ с двумя разделами. Комплект делится по префиксу
собственного продукта: каталоги без префикса — заимствованные, с префиксом
(`<продукт>-bff`) — собственные.

- **Собственные модули — только раздел 2 правил:** покрытие > 25 % и метод сбора.
  Требования к режимам, журналам и анализу ошибок (доп. 1–4) в этот отчёт не переносить:
  для собственного кода таких требований в правилах нет, лишние вердикты читаются
  как претензии. Прогоны с датчиками, два профиля, отсутствие сбоев — отдельным
  абзацем «сверх требований раздела 2, к сведению», без статусов.
- **Заимствованные — пп. 1–2 (методика) и 1–4 (дополнительные);** требования плана
  отдельным пунктом не идут: план отсутствует → ограничение в разделе 1 и
  замечание, а когда появится — перечень требований дополняется его пунктами с их
  же нумерацией.
- В шапке каждого отчёта — взаимные ссылки («модули собственной разработки —
  `own-modules-…`», «заимствованные — `borrowed-components-…`») и оговорка, что
  прежние заключения не перезаписываются.
- **Перечень собственных модулей продукта тоже обычно не документирован**
  (в комплекте один каталог). Это тот же гейт, что ППЗМ: в отчёт — «вывод о
  полноте охвата собственных модулей не формируется», в «что запросить» — перечень
  модулей с областью проверки. Один представленный модуль не выдавать за все.
- Таблица покрытия собственного модуля — **по файлам** (`модуль | результат |
  строки покрыто/всего | %`) плюс строка «Итого по модулю»; колонку доказательств
  в неё не добавлять (пути в 35 символов разрывают ячейки), источник данных —
  строкой под таблицей (`coverage-summary.csv`, `lcov.info`, HTML-отчёт).
- Пофайловый порог прогона при этом идёт как запас прочности, а вердикт по 2.1 —
  по агрегату модуля.

## 8. Verification

- Каждое требование правил имеет вердикт из четырёх и доказательство с путём.
- Ограничение по плану стоит до выводов и повторено в «что запросить».
- Нумерация своя: колонка «Пункт» — только `п. 1`, `п. 2`, `1`–`4`; в тексте нет
  номеров вида 3.1/3.3 и подписей А1–А6 (`grep -n '3\.[123]\|А[1-6]'` пуст).
- В таблицах результатов строк столько же, сколько компонентов (или явно «все 10»).
- Числа процентов совпадают между разделами и приложением, округление одно и то же.
- Ячеек с вердиктом в HTML столько же, сколько строк таблиц результата; ни одна
  таблица не шире контейнера.
