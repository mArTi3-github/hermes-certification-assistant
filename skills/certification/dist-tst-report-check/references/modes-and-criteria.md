# Режимы выполнения, критерии окончания и упаковка результатов

Блок требований, который приходит отдельно от порога покрытия: заказчик
пересылает текст методики про **режимы** прогона, **критерии успешного окончания**
и **архив ZIP** с результатами, и просит «проверь материалы на эти требования и
сделай отчёт». Проверка идёт по тем же артефактам, что и обычная (шаг 6 основного
скилла), но вердиктов больше и они мельче: пять групп требований вместо трёх.

## 1. Разложить текст на проверяемые строки

Коды — из перечня дополнительных требований основных правил (1.А … 4.Г); у упаковки
своего пункта в этом перечне нет, она остаётся требованием к результатам испытаний.
Дробных кодов (`1.А-1`, `А1`) не вводить: в отчёте снова появятся ссылки, которые
Verification запрещает.

- **1.А Режимы выполнения.** Прогон в режиме сборки компонента с опциями,
  соответствующими его сборке как компонента ОО — **для каждого набора опций**, если
  ОО собирается разными способами; прогон с инструментацией датчиками (санитайзеры
  `-race`/`-msan`/`-asan` для C/C++/Go, для прочих языков — доступные отладочные
  проверки); прогон с инструментацией средствами сбора покрытия; совмещение режимов
  допускается, несовместимые датчики — раздельными прогонами.
- **2.Б Журналы.** Журнал выполнения тестов по каждой версии и конфигурации
  компонента и по каждому из режимов; сведения о crash/assert и failed.
- **3.В Покрытие.** Покрытие исходного кода, достигнутое в ходе тестов, по каждой
  версии и конфигурации компонента, в формате, соответствующем языку.
- **4.Г Анализ ошибок.** Оценка значимости для безопасности всех crash/assert и
  failed; для уровня ≠ «Влияние отсутствует» — исправления и сведения в БДУ ФСТЭК;
  для уровня «Влияние отсутствует» — развёрнутое обоснование решения.
- **Упаковка.** ZIP-архив: журналы, покрытие (lcov/llvm-cov или аналог), сбои с
  уровнем критичности, обоснования.

## 2. Чем доказывается каждый режим — по типу кода

| Подпункт 1.А | JS/TS | C/C++ | Go | Python | Что искать в комплекте |
|---|---|---|---|---|---|
| сборка как в ОО | `tarball-vs-tag.txt`, `built-vs-published.txt` (для собранных из TS), `embedded-vs-source.txt` для рантайма + sha256 бинарника в `environment.txt` | `debian/patches` пуст, флаги сборки, `objcopy`-вмешательства | `go version -m`, сверка модуля с тегом | версия интерпретатора + установленный пакет | каталоги профилей прогона, `_scripts/**/*.env`, `source.txt` |
| датчики | `NODE_OPTIONS` в env профиля: `--throw-deprecation`, `--trace-deprecation`, `--trace-warnings`, `--unhandled-rejections=strict`; срабатывания в журнале `sensors` | `-fsanitize=` по всем командам компиляции, рантаймы в `DT_NEEDED` | `-race` в `go test` | `PYTHONWARNINGS=error`, `-X dev` | каталог `sensors`/`asan`, неудачные попытки `_*attempt*` |
| инструментация покрытием | c8/Istanbul: `lcov.info`, `coverage-summary.*`, HTML | gcovr: `lcov`/XML/JSON | `go tool cover -func` / `cover.out` | coverage.py: `coverage.json`, `htmlcov` | профили покрытия по каждому режиму, не только итоговый |
| совмещение режимов | покрытие снято в **обоих** прогонах ⇒ режимы совмещены | отдельные профили `asan`/`ubsan`/`combined` | `-race` + `-cover` совместно | один прогон с обоими средствами | каталоги `rerun/<режим>` у рантайма |

Формулировка датчиков для интерпретируемого кода — «тот же образ, тот же прогон,
дополнительные рантаймовые флаги», а не «инструментированная сборка»: иначе
протокол обещает сборку, которой не было.

## 3. Таблицы отчёта

1. **Итог** — таблица требований: `пункт | требование | результат | компонентов`,
   результат первой фразой ячейки (только эта таблица цветная).
2. **Режимы по компонентам** — `компонент | 1.А сборка/тождество | 1.А датчики
   (конкретные флаги) | 1.А покрытие (инструмент и форматы)`. В ячейке — факт с
   именем файла, а не «есть».
3. **Сбои по группам причин** — `группа | случаев | что произошло | уровень |
   подтверждение`. Группы формировать по механизму (настройка ядра, влияние
   инструментации, влияние флага, тайм-ауты), а не по компонентам: так видно, что
   весь список объяснён одним-двумя механизмами и подтверждён контрольными
   экспериментами `E1…En` в `causes/`.
4. **Замечания** — триадами «что не так / чем подтверждено / что исправить»;
   **что запросить** — 5–6 проверяемых артефактов; **приложение «Программные
   средства»** обязательно (как в любом DIST.TST-отчёте).

Отдельный файл на этот срез: `<модуль>-tst-<срез>-report.md/.html` рядом с
прежними; уже сданные отчёты не переписывать.

## 4. Решения, которые приходится принимать

- **4.Г при отсутствии случаев выше «Влияние отсутствует» — «Не применимо»**
  (подсветка `v-mixed`): зелёный означал бы выполненную работу, которой не было,
  «не подтверждено» — претензию к комплекту, который условие не нарушал.
  В обосновании — число таких случаев (ноль) и файл, где это видно.
- **Упаковка без архива — «Не подтверждено материалами», не «не соответствует»:**
  материалы переданы каталогом и все четыре позиции в нём есть; упаковка — вопрос
  передачи, а не тестирования.
- **Одна версия и одна конфигурация на компонент.** Если все компоненты прогнаны
  в одной среде (`environment.txt` совпадает), один прогон закрывает требование
  «для каждой конфигурации»; заявление «продукт поставляется только для amd64»
  обычно живёт в `readme.txt` — тогда это замечание и запрос документа о
  поддерживаемых архитектурах, а не выполнение.
- **Несколько наборов опций сборки** доказываются несколькими профилями прогона
  или каталогами `rerun/<режим>`; один `baseline` — один набор.
- **Смена датчика на более слабый** (`--throw-deprecation` → `--trace-deprecation`
  у части компонентов, или отладочные флаги вообще не включены у рантайма) даёт по
  подпункту «датчики» требования 1.А «Соответствует частично» **по требованию в
  целом**: сохранённые неудачные попытки доказывают добросовестность, но не
  выполнение. Формулировать по компонентам с разбивкой «N из M», а не одним
  «частично» без счёта.
- **Роль датчика вместо датчика** (встроенные assert-проверки тестов и контроль
  раннера у Node.js) — обоснование, которое принимается как объяснение, но не как
  выполнение требования: нужен либо контрольный прогон с отладочными флагами,
  либо документ о неприменимости.
- **Код возврата 1 при ожидаемых сбоях** (`EXPECTED_FAILED=<N>`) не отменяет
  «журнал получен»: фиксировать число сбоев и то, что чистого прогона нет.

## 5. Пропуски — не сбои

Критерии 4.Г говорят о `crash`/`assert` и `failed`, а не о `skipped`.
Пропуски проверяются отдельно: на каждый — причина в материалах (`it.skip`,
платформенные, debug-only) либо замечание о пробеле анализа журналов. Число
пропусков сверять по источникам: директивы `# skip` в TAP, элементы `<skipped>` в
`junit.xml` и сводка readme дают разные значения (328 / 336 / 0) — расхождение
замечанием, а не фоном.

## 6. Verification

- Каждая группа требований (1.А, 2.Б, 3.В, 4.Г и упаковка) имеет вердикт из
  словаря и артефакт с путём.
- Матрица режимов покрывает все компоненты среза; ни один режим не оценён по readme.
- Сбои сгруппированы по механизму, у каждой группы — контрольный эксперимент.
- Число цветных ячеек равно числу строк таблицы требований.
- Есть замечания (как минимум про упаковку и про датчики), список запросов и
  приложение «Программные средства».
