# Режимы выполнения, критерии окончания и упаковка результатов

Блок требований, который приходит отдельно от порога покрытия: заказчик
пересылает текст методики про **режимы** прогона, **критерии успешного окончания**
и **архив ZIP** с результатами, и просит «проверь материалы на эти требования и
сделай отчёт». Проверка идёт по тем же артефактам, что и обычная (шаг 6 основного
скилла), но вердиктов больше и они мельче: 9–10 строк вместо трёх.

## 1. Разложить текст на проверяемые строки

Нумерация — своя (Р1.1 … Р4), в отчёте по ней же идти:

| Код | Требование |
|---|---|
| Р1.1 | Прогон в режиме сборки компонента с опциями, соответствующими его сборке как компонента ОО — **для каждого набора опций**, если ОО собирается разными способами |
| Р1.2 | Прогон с инструментацией датчиками: санитайзеры `-race`/`-msan`/`-asan` для C/C++/Go; для прочих языков — активация доступных отладочных проверок |
| Р1.3 | Прогон с инструментацией средствами сбора покрытия |
| Р2 | Совмещение режимов допускается; несовместимые датчики — раздельными прогонами |
| Р3.1 | Журнал тестов по каждой версии/конфигурации компонента и по каждому режиму |
| Р3.2 | Покрытие по каждой версии/конфигурации |
| Р3.3 | Оценка значимости для безопасности всех crash/assert и failed |
| Р3.4 | Для уровня ≠ «Влияние отсутствует» — исправления и сведения в БДУ ФСТЭК |
| Р3.5 | Для уровня «Влияние отсутствует» — развёрнутое обоснование |
| Р4 | ZIP-архив: журналы, покрытие (lcov/llvm-cov или аналог), сбои с уровнем критичности, обоснования |

## 2. Чем доказывается каждый режим — по типу кода

| Режим | JS/TS | C/C++ | Go | Python | Что искать в комплекте |
|---|---|---|---|---|---|
| Р1.1 | `tarball-vs-tag.txt`, `built-vs-published.txt` (для собранных из TS), `embedded-vs-source.txt` для рантайма + sha256 бинарника в `environment.txt` | `debian/patches` пуст, флаги сборки, `objcopy`-вмешательства | `go version -m`, сверка модуля с тегом | версия интерпретатора + установленный пакет | каталоги профилей прогона, `_scripts/**/*.env`, `source.txt` |
| Р1.2 | `NODE_OPTIONS` в env профиля: `--throw-deprecation`, `--trace-deprecation`, `--trace-warnings`, `--unhandled-rejections=strict`; срабатывания в журнале `sensors` | `-fsanitize=` по всем командам компиляции, рантаймы в `DT_NEEDED` | `-race` в `go test` | `PYTHONWARNINGS=error`, `-X dev` | каталог `sensors`/`asan`, неудачные попытки `_*attempt*` |
| Р1.3 | c8/Istanbul: `lcov.info`, `coverage-summary.*`, HTML | gcovr: `lcov`/XML/JSON | `go tool cover -func` / `cover.out` | coverage.py: `coverage.json`, `htmlcov` | профили покрытия по каждому режиму, не только итоговый |
| Р2 | покрытие снято в **обоих** прогонах ⇒ режимы совмещены | отдельные профили `asan`/`ubsan`/`combined` | `-race` + `-cover` совместно | один прогон с обоими средствами | каталоги `rerun/<режим>` у рантайма |

Формулировка режима 2 для интерпретируемого кода — «тот же образ, тот же прогон,
дополнительные рантаймовые флаги», а не «инструментированная сборка»: иначе
протокол обещает сборку, которой не было.

## 3. Таблицы отчёта

1. **Итог** — таблица требований: `требование | вердикт | обоснование`, вердикт
   первой фразой ячейки (только эта таблица цветная).
2. **Режимы по компонентам** — `компонент | Р1.1 сборка/тождество | Р1.2 датчики
   (конкретные флаги) | Р1.3 покрытие (инструмент и форматы)`. В ячейке — факт с
   именем файла, а не «есть».
3. **Сбои по группам причин** — `группа | случаев | что произошло | уровень |
   подтверждение`. Группы формировать по механизму (настройка ядра, влияние
   инструментации, влияние флага, тайм-ауты), а не по компонентам: так видно, что
   весь список объяснён одним-двумя механизмами и подтверждён контрольными
   экспериментами `E1…En` в `causes/`.
4. **Замечания** — триадами «что не так / чем подтверждено / что исправить»;
   **что запросить** — 5–6 проверяемых артефактов; **приложение «Программные
   средства»** обязательно (как в любом DIST.TST-отчёте).

Отдельный файл на этот срез: `<модуль>-tst-<срез>-report.md/.html` рядом с
прежними; уже сданные отчёты не переписывать.

## 4. Решения, которые приходится принимать

- **Р3.4 при отсутствии случаев выше «Влияние отсутствует» — «Не применимо»**
  (подсветка `v-mixed`): зелёный означал бы выполненную работу, которой не было,
  «не подтверждено» — претензию к комплекту, который условие не нарушал.
  В обосновании — число таких случаев (ноль) и файл, где это видно.
- **Р4 без архива — «Не подтверждено материалами», не «не соответствует»:**
  материалы переданы каталогом и все четыре позиции в нём есть; упаковка — вопрос
  передачи, а не тестирования.
- **Одна версия и одна конфигурация на компонент.** Если все компоненты прогнаны
  в одной среде (`environment.txt` совпадает), один прогон закрывает требование
  «для каждой конфигурации»; заявление «продукт поставляется только для amd64»
  обычно живёт в `readme.txt` — тогда это замечание и запрос документа о
  поддерживаемых архитектурах, а не выполнение.
- **Несколько наборов опций сборки** доказываются несколькими профилями прогона
  или каталогами `rerun/<режим>`; один `baseline` — один набор.
- **Смена датчика на более слабый** (`--throw-deprecation` → `--trace-deprecation`
  у части компонентов, или отладочные флаги вообще не включены у рантайма) даёт по
  Р1.2 «Соответствует частично» **по требованию в целом**: сохранённые неудачные
  попытки доказывают добросовестность, но не выполнение. Формулировать по
  компонентам с разбивкой «N из M», а не одним «частично» без счёта.
- **Роль датчика вместо датчика** (встроенные assert-проверки тестов и контроль
  раннера у Node.js) — обоснование, которое принимается как объяснение, но не как
  выполнение требования: нужен либо контрольный прогон с отладочными флагами,
  либо документ о неприменимости.
- **Код возврата 1 при ожидаемых сбоях** (`EXPECTED_FAILED=<N>`) не отменяет
  «журнал получен»: фиксировать число сбоев и то, что чистого прогона нет.

## 5. Пропуски — не сбои

Критерии Р3.3–Р3.5 говорят о `crash`/`assert` и `failed`, а не о `skipped`.
Пропуски проверяются отдельно: на каждый — причина в материалах (`it.skip`,
платформенные, debug-only) либо замечание о пробеле анализа журналов. Число
пропусков сверять по источникам: директивы `# skip` в TAP, элементы `<skipped>` в
`junit.xml` и сводка readme дают разные значения (328 / 336 / 0) — расхождение
замечанием, а не фоном.

## 6. Verification

- Каждая строка требований (Р1.1 … Р4) имеет вердикт из словаря и артефакт с путём.
- Матрица режимов покрывает все компоненты среза; ни один режим не оценён по readme.
- Сбои сгруппированы по механизму, у каждой группы — контрольный эксперимент.
- Число цветных ячеек равно числу строк таблицы требований.
- Есть замечания (как минимум про упаковку и про датчики), список запросов и
  приложение «Программные средства».
