# Переиспользование результатов тестирования другого продукта

Ситуация: для продукта B пришёл комплект модульного тестирования, в котором
сторонние компоненты не тестировались — README утверждает: «используются те же
версии, что в продукте A, результаты можно взять из его DIST.TST».

Проверять надо не фразу, а три вещи по отдельности: **версии**, **тождество
артефактов**, **полноту перечня**. Первые две обычно сходятся, третья — нет.

## 1. Перечень и версии: брать дерево, не таблицу README

Источник — `results/installed-deps.json` (вывод `npm ls --json` после `npm ci`),
а не таблица в README. Формат — вложенное дерево `dependencies`:

```python
import json
d = json.load(open('results/installed-deps.json', encoding='utf-8'))
out = {}
def walk(n):
    for name, v in (n.get('dependencies') or {}).items():
        out.setdefault(name, set()).add(v.get('version'))
        walk(v)
walk(d)
```

Сопоставить две стороны:

| Сторона | Откуда брать |
|---|---|
| версии в продукте B | `installed-deps.json` |
| версии, фактически протестированные в продукте A | имена каталогов компонентов в его комплекте (`<pkg>-<semver>/`) + строка «Библиотека: …» в каждом `readme.txt` |

Матрица по каждому runtime-пакету: `версия B / версия A / статус`, где статус —
«совпадает, результаты применимы», «версия иная — тестирование обязательно»,
«в A не тестировался». Считать надо по всему дереву, включая транзитивные
пакеты: парсеры запросов и тел (`qs`, `raw-body`, `type-is`, `content-type`),
маршрутизация (`path-to-regexp`, `router`), отдача файлов (`send`,
`serve-static`), кодировки (`iconv-lite`) — именно они принимают клиентский ввод.

## 2. Тождество артефактов: побайтная сверка бинарника проверяема

Утверждение «рантайм тот же» проверяется только по хешу. Хорошая практика
разработчика — фиксировать `sha256` бинарника в `environment.txt` и `run.log`
комплекта-донора; тогда достаточно `grep -rn '<хеш>' <каталог A>`, чтобы
подтвердить совпадение, не имея самого бинарника. Если хеша нет ни в одном из
комплектов — писать «не подтверждено материалами» и запрашивать хеш или сам
образ, а не соглашаться по названию версии.

Версия рантайма сама по себе слабее: сборка под другую libc/дистрибутив даёт
другой код. Совпадение имени версии — довод только вместе с хешем.

## 3. Полнота перечня: чего в README нет

Главный дефект таких комплектов — таблица README перечисляет 3–4 «главных»
компонента, а сервис импортирует больше. Находить импорты можно без исходников:
HTML-отчёт покрытия (istanbul/c8) содержит исходный текст файлов.

```python
import re, html
t = open('results/sensors/coverage/src/utils/x.ts.html', encoding='utf-8').read()
m = re.findall(r'<pre class="prettyprint lang-js">(.*?)</pre>', t, re.S)
code = html.unescape(re.sub(r'<[^>]+>', '', m[0]))
for ln in code.splitlines():
    if ln.strip().startswith(('import', 'const')) and 'from' in ln:
        print(ln.strip()[:120])
```

Дальше по каждому найденному пакету — вопрос «принимает ли он данные от
клиента». Признаки, которые уже видели в коде: значение куки идёт в разбор
часового пояса или локали, название отчёта идёт в шаблон, путь из URL идёт в
отдачу статики. Такие пакеты — поверхность атаки независимо от того, что
разработчик считает их «служебными».

Отдельно проверять внешние процессы и бинарники, которые сервис вызывает
(`spawn`/`exec`): если в тестах они замоканы, компонент фактически не
тестировался и в перечне его обычно нет.

## 4. Что писать в отчёте

Три отдельных вывода, не один:

1. **Заявленные компоненты** — «переиспользование правомерно»: версии совпадают
   (и хеш рантайма тоже), артефакты донора имеют вердикт «соответствует».
2. **Неназванные, но совпадающие** — «результаты также применимы, таблицу README
   дополнить». Это довод в пользу разработчика: перечень неполон в его пользу.
3. **Не покрытые ни одним продуктом** — «не подтверждено материалами»: нужны
   собственные тесты компонента либо запись в SBOM/протоколе, что компонент не
   относится к поверхности атаки, с обоснованием.

И обязательно оговорка: при переиспользовании в протокол переносятся и чужие
сбои/пропуски донора (`<failure>`, `<skipped>` в его `junit.xml`) — их надо
назвать числом, а не «взять итог».

## 5. Сопутствующие проверки комплекта

- `installed-deps.json`: поля `problems` и `error` — при `npm ci --ignore-scripts`
  встречается `ELSPROBLEMS` («invalid: <pkg>@<ver>»), дерево считается
  некорректным; требуется пояснение в README, иначе это незамеченный дефект.
- Наличие `package-lock.json` и SBOM в комплекте: без них совпадение версий
  проверяется только по дереву после установки, а полнота перечня зависимостей
  непроверяема.
- Манифест целостности комплекта: сверка `source-files.sha256` покрывает файлы
  репозитория, но не сами материалы — отдельная строка в замечаниях.
- Расхождение имени образа между `environment.txt` (короткое имя) и README
  (полное с registry) — косметика, но фиксируется, чтобы не всплыло в протоколе.

## 6. Замечание и запрос разработчику: формулировки

Главная ошибка — смешать два разных утверждения: «компонент есть в материалах» и
«компонент обязан быть протестирован». Первое доказывается путём и номером
строки, второе — внешним документом (Методика: автоматическое тестирование всех
модулей, реализующих ФБ; либо SBOM с разметкой `attack_surface`/
`security_function`). Если написать одной фразой «перечень неполон», заказчик
справедливо спросит «где сказано, что они должны быть включены», и весь пункт
выглядит выдуманным.

Для «компонент есть» давать три независимых адреса — они не дублируют друг друга:

| Где | Что видно |
|---|---|
| `results/tools.txt`, номера строк | прямые зависимости с версиями (вывод `npm ls --depth=0`) |
| `results/run.log`, строки с тем же деревом | что устанавливалось именно в этом прогоне |
| `results/installed-deps.json`, номера строк узлов | весь граф, включая транзитивные пакеты |
| HTML покрытия, номера строк импортов | что реально исполняется и куда приходит ввод |

Номера строк из HTML получаются делением текста из `<pre>` на строки: индекс+1 =
номер строки исходника (`import { IANAZone } from 'luxon'` → 7,
`IANAZone.isValidZone(...)` → 277). Так в отчёте появляется ссылка
`src/utils/reports-controller.ts, стр. 7, 271, 277`, которую нельзя оспорить.

Формулировки для отчёта: «неопределённость охвата», «в материалах отсутствуют
сведения о …», «требуется одно из двух: результаты тестов либо разметка SBOM».
Не писать «разработчик не протестировал» и «требование нарушено», пока не
показано, что компонент входит в объём.

Запрос разработчику — два варианта:

- **короткий** (письмо/чат): что видно в материалах с адресами → что
  подтверждаем (совпавшие версии, хеш рантайма) → чего не хватает → две
  приемлемые формы ответа (тесты либо SBOM) → отдельной строкой, что вопрос не
  блокирует приёмку собственного компонента;
- **формальный** (для протокола): нумерованные пункты «факт с адресами → что
  утверждает README → что просим (а: тесты / б: SBOM) → сопутствующие вопросы
  (`package-lock.json`, пояснение `ELSPROBLEMS`, подтверждение применимости
  неназванных, но совпавших компонентов) → формат ответа».

Тон: «в материалах отсутствуют сведения» вместо «вы не протестировали», и явно
оставить разработчику законный выход — SBOM, по которому компонент вне объёма.
Такой запрос закрывается быстрее, чем претензия.
