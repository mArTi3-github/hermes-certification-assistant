# Контракт отчёта и правила классификации

## `surface.json` (schema `attack-surface/1`)

```json
{
  "schema": "attack-surface/1",
  "tool_version": "0.1.0",
  "generated_at": "<UTC>",
  "product": {"name": "...", "root": "<abs path>", "commit": "<sha>"},
  "scope": {"languages": ["Python"], "framework": "FastAPI/Starlette", "build": "not used"},
  "stats": {
    "routes": 0, "no_auth": 0, "uploads": 0,
    "by_status": {}, "by_method": {}, "reachable_funcs": 0, "sinks": 0,
    "files": 0, "loc": 0, "code_loc": 0, "by_lang": [[".py", 0]], "by_ext": [[".py", 0]]
  },
  "interfaces": [{
    "id": "METHOD path", "method": "POST", "path": "/api/...",
    "kind": "http|static|docs", "note": "...",
    "handler": {"qual": "module.Class.method", "file": "rel/path.py", "line": 0},
    "params": [{"name": "", "annotation": "", "default": "", "kind": "body|body-model|file-upload|query|path|form|dependency|framework-object|body-scalar"}],
    "auth": {"class": "unauthenticated|unknown|admin-only", "label": "...", "reason": "..."},
    "validation": {"status": "...", "label": "...", "evidence": [{"kind": "", "weight": 0, "file": "", "line": 0, "text": "", "where": ""}]},
    "reachable": {"functions": [{"qual": "", "file": "", "line": 0, "depth": 0}], "unresolved": 0},
    "sinks": [{"kind": "", "file": "", "line": 0, "text": "", "where": ""}],
    "handler_source": "...", "admin_like": false
  }],
  "auth_signals": [], "parse_errors": [], "conclusions": [], "limitations": [], "command": "..."
}
```

Инварианты, которые нельзя нарушать при расширении:

- `handler.file:line` указывает на строку объявления функции (`def`/`async def`).
- `reachable.functions[0]` — сам обработчик с `depth = 0`; далее BFS-фронт, а не точные пути.
- `validation.evidence[*].file/line` — реальные строки исходника; текст строки обрезан, но не переписан.
- `sinks` не являются уязвимостями: это операции, требующие проверки происхождения данных.
- `stats` считается из `interfaces`, а не задаётся вручную.

## Веса и статусы

| Вес | Категория | Примеры правил |
|---|---|---|
| 2 | схемная проверка | модель pydantic в сигнатуре, `model_validate`, `Field(ge=/max_length=/pattern=)`, `jsonschema`, `_is_private_url`, `validate_url(` |
| 1 | явная проверка | `isinstance`, сравнение длины с лимитом, ответы 400/413/415/422, allowlist-константы, `re.fullmatch` |
| 0 | структурный разбор | `json.loads`, приведение `int()`, типизированные скаляры |

Правило статуса (первое сработавшее):

1. вес 2 в обработчике → `validated-boundary`;
2. иначе вес 2 в достижимом коде → `validated-in-depth`;
3. иначе вес 1 где угодно на пути → `partial`;
4. иначе вес 0 → `parse-only`;
5. иначе → `unvalidated`;
6. нет кода проекта (статика, `/docs`) → `n/a` (в статистике валидации показывается отдельно).

## Разделы HTML-отчёта

1. Методика и модель нарушителя — что считается интерфейсом, как трактуется валидация, границы применимости.
2. Сводка — объёмы, число интерфейсов, распределение по методам и статусам, состав исходных текстов.
3. Выводы по поверхности атаки — автоматические, проверяемые человеком утверждения (аутентификация,
   административные интерфейсы, загрузка файлов, документация API, интерфейсы без валидации, опасные операции).
4. Реестр интерфейсов — таблица для быстрой навигации.
5. Карточки интерфейсов — параметры, признаки валидации, опасные операции, достижимый код с глубиной,
   исходный текст обработчика.
6. Ограничения и что не покрыто.
7. Воспроизводимость — коммит, команда, ссылка на `surface.json`.

## Что писать в заключении сертификационного документа

- Сколько интерфейсов входит в поверхность и почему (класс нарушителя, отсутствие/наличие аутентификации).
- Какие интерфейсы исключены и на каком основании (например, требуют прав администратора — если это
  действительно проверяется в коде).
- Где валидация есть, где её нет, и что это означает для дальнейших проверок (не «уязвимо/не уязвимо»).
- Явная оговорка о методе: статический анализ без сборки, без taint, граф эвристический.
