# `false_positive` или `not_affected`

## Две корзины

| | `false_positive` | `not_affected` |
|---|---|---|
| Что утверждаем | находка неверна по идентификации или версии | компонент и версия верные, уязвимость не применима в продукте |
| Основание | другой продукт с тем же именем · версия вне затронутого диапазона · исправление пришло раньше поставленной версии | уязвимая функциональность не используется, код недостижим, сборка не та (архитектура, опции) |
| Формулировка | называет продукт/версию, к которой относится CVE | называет функциональность, которая не задействована |

Порядок решения: сначала проверить идентификацию и диапазон версий, только потом достижимость.
Если верны оба основания — ставится `false_positive`: «версия не подвержена» сильнее, чем
«код не используется», и не требует доказательств о рантайме.

## Проверка по идентификатору

Описание и затронутые версии по номеру уязвимости (ответ в файл, разбор отдельной командой):

```bash
curl -s -o /tmp/osv-vuln.json "https://api.osv.dev/v1/vulns/<CVE-или-GHSA>"
python3 -c "import json;d=json.load(open('/tmp/osv-vuln.json'));print(d.get('summary'));print([(a['package'], a.get('ranges')) for a in d.get('affected',[])][:3])"
```

Затронута ли именно поставленная версия — запрос по purl:

```bash
curl -s -X POST -d '{"package":{"purl":"pkg:pypi/<имя>@<версия>"}}' \
  -o /tmp/osv-purl.json https://api.osv.dev/v1/query
python3 -c "import json;print(sorted({v['id'] for v in json.load(open('/tmp/osv-purl.json')).get('vulns',[])}))"
```

Если в OSV нет ни по `id`, ни по purl — смотреть NVD (`nvd.nist.gov/vuln/detail/<id>`) и бюллетень
вендора: там видно, к какому продукту уязвимость относится на самом деле.

## Ловушки из реальных отчётов

- **Совпадение имени, а не продукта.** CVE-2020-1171 — RCE расширения Python для Visual Studio
  Code (Microsoft), а не интерпретатора CPython. CVE-2014-125074 — SQL-инъекция в Java-приложении
  «Nayshlok Voyager» (файл `Voyager/src/models/DatabaseAccess.java`), а не в пакете `voyager`
  для Python. Оба случая — `false_positive`, и обоснование должно назвать настоящий продукт.
- **«Исправлено в X» при поставленной версии ≥ X.** Уязвимого кода в поставке нет: это
  `false_positive`, а не `not_affected` (исправление в 1.26.12, поставлена 1.26.18).
- **Версия из будущего.** Версию исправления брать из источника, а не из текста разметки: там
  встречаются «Исправлено в 3.9.2» при фактическом исправлении 3.9.19 и поставленной 3.9.25.
- **«Актуально для 32-битных платформ» при поставке amd64.** Уязвимость настоящая, но сборка не
  та — `not_affected`; текст переписывается на «проявляется только в 32-битной сборке; поставлена
  64-битная», иначе он противоречит статусу.
- **Один CVE на разные компоненты.** Статус принадлежит паре (компонент, CVE): разные компоненты
  могут иметь разные статусы по одному номеру. Одна и та же пара с двумя разными статусами —
  всегда дефект отчёта.

## Диапазон версий: главный решающий признак

Вопрос "затронута ли поставленная версия" решается по диапазону из источника, а не по тексту
разметки. Запрашивать нужно оба источника — они покрывают разные экосистемы:

- OSV по `id` и по purl — для PyPI, npm, Go, Maven.
- NVD `configurations[].nodes[].cpeMatch[]` — для системных пакетов (alpine, debian) и для того,
  чего нет в OSV. Поля `versionStartIncluding`/`versionEndExcluding`/`versionEndIncluding`
  дают границы; отсутствие границы с какой-то стороны значит "без ограничения".

**OSV по purl для apk/deb возвращает 0 уязвимостей всегда** — это не доказательство отсутствия
уязвимости, а отсутствие индекса. Для `pkg:apk/alpine/...` и `pkg:deb/debian/...` истина
только в NVD/cpe и в бюллетене дистрибутива.

Сравнение версий — числовыми компонентами, с учётом дистрибутивных суффиксов: `1.3.1-r2` — это
`1.3.1.2` для apk, `17.9-0+deb13u1` — `17.9`; `%2B` в purl — это `+`.

### Доступ к NVD и кэш диапазонов

NVD без ключа пускает **5 запросов за 30 секунд**: без пауз часть запросов получает отказ, и тогда
часть строк молча остаётся без диапазона — предложения по статусу просто не появляются
(20 CVE = 6 предложений вместо 32). Поэтому запросы идут по одному с паузой ~6,5 с и явным
`User-Agent`, ответ каждого CVE кэшируется в `~/.cache/src-dep-report-check/<CVE>.json`.
На отчёт с 70+ CVE — несколько минут: запускать в фоне с уведомлением, а не в foreground.

Офлайн-страховка — `references/version-ranges.json`, который заполняет `scripts/refresh_ranges.py <отчёт>`
(структура: `{CVE: {"ranges": [{"from", "to", "to_incl"}], "source", "checked"}}`).
Если диапазона нет ни в кэше, ни в файле — это **не** «уязвимость не подтверждена»: это
отсутствие данных, и в ответе такая строка должна звучать как «диапазон не получен», а не молчать.

Реальные последствия пропуска этого шага (отчёт по заимствованным компонентам, 463 строки):
116 строк стояли как `not_affected` с обоснованием "не используется", хотя поставленная версия
вне затронутого диапазона (zlib 1.3.1 при "≤ 1.2.12", musl 1.2.5 при "≤ 1.1.15", busybox 1.37 при
"≤ 1.27.2") — это `false_positive`, а не `na`. Разметка была адекватна по форме и неверна по
основанию.

## Соответствие текста и статуса

| Текст обоснования | Статус, который он подтверждает |
|---|---|
| уязвимость в другом продукте / версия до исправления | `false_positive` |
| библиотека или модуль не используется, код недостижим | `not_affected` |
| нужна 32-битная сборка, отключённая опция, отсутствующий компонент | `not_affected` |
| «уязвимость актуальна», «эксплуатация возможна» | `affected` — строку нельзя закрывать ни fp, ни na |

Последняя строка — не статус для отчёта, а сигнал: строку не закрывать, нужно уточнение у
человека и, вероятно, план устранения.

## Проверка уже написанного

Разметку проверяют до сборки и после: скриптом по всему отчёту, а не выборочно.
`check_markup.py <исходный> <…_filtered>` показывает четыре среза, каждый — вопрос человеку или
повод к правке:

| Срез | Что значит |
|---|---|
| утверждение о применимости («актуальна», «эксплуатация возможна», «подтверждена») | строку нельзя закрывать `fp`/`na`: показать человеку явно, в ответе отдельным списком |
| статус против смысла обоснования | `fp` с текстом про недостижимость и наоборот — признак копипаста или спешки |
| версия в тексте ≠ версия компонента | текст скопирован с другой строки (libpq5@17.7 в тексте при компоненте 18.1) |
| короткий текст без основания | «Уязвимость для VSCode», «Исправлено 3.9.2-1»: проверять нечего |

Пары (компонент, `id`) с разными статусами — всегда дефект; с разными текстами при одном
статусе — расхождение формулировок, кандидат на унификацию.

Утверждения о применимости не правятся автоматически и не остаются в молчании: они идут в ответ
человеку отдельным блоком с номером строки и полным текстом, даже если вся остальная работа по
отчёту уже закончена.
