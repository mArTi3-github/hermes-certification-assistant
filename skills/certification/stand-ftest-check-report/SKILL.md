# Проверка материалов stand-ftest (тестовая документация, приказ № 76)

Класс задач: пришли чужие материалы «Тестовой документации» — отчёт `.docx` и,
возможно, папка приложения — нужно сказать, что соответствует требованиям, что нет
и чего не хватает, со ссылками на места в документе. Исполнение проверок, дописывание
тестов и сборка отчёта — парный скилл `stand-ftest`.

## When to Use

- Нужно проверить комплект перед сдачей заказчику или органу по сертификации.
- Пришли замечания проверяющего — надо пройти отчёт по пунктам и ответить по факту.
- Надо оценить чужой отчёт: полнота тестов, прослеживаемость, свидетельства.
- Не для: разбора «что написано в отчёте» и правки `.docx` — это `stand-ftest`;
  не для проверки кода продукта — это `attack-surface-analysis` и отчёты по уязвимостям.

## Границы проверки

| Проверяется | Не проверяется |
|---|---|
| комплектность (отчёт, приложение, сводка) | соответствие изделия требованиям — это предмет испытаний |
| структура по карте разделов приказа № 76 | корректность самих тестовых сценариев продукта |
| прослеживаемость: тест → требования → покрытие/глубина | арифметика глубины за пределами заявленных таблиц |
| наличие и качество свидетельств каждого шага | истинность скриншотов (только воспроизводимость по документу) |
| отсутствие заглушек и битых ссылок | оформление, не влияющее на приёмку (выносится в «косметические») |
| OOXML-гигиена файла | — |

## Вход

1. `.docx` отчёта (обязательно).
2. Папка приложения со свидетельствами (если отчёт на неё ссылается; отсутствие —
   уже замечание: ссылки мертвы).
3. Сводка прогона `.md`, если её прикладывали — сверять с отчётом, а не верить ей.

Если чего-то нет, проверка всё равно выполняется, а отсутствие фиксируется в
заключении как блокирующее замечание.

**Инструменты.** Нужны `python3` с `python-docx` (чтение документа скриптами штатного скилла
`microsoft-office` и `docx_read_ordered.py` из скилла `stand-ftest`) и
`soffice` из LibreOffice (PDF-рендер страниц со свидетельствами); для разбора пакета — `unzip`.
Проверяются до начала, и отсутствие называется сразу с предложением установки
(`sudo apt-get install -y libreoffice-writer`, `python3 -m pip install python-docx` в venv) —
с разрешением, потому что установка меняет чужую машину. Если инструмента нет и поставить
нельзя, в заключении пишется, что именно не проверено: визуальный контроль вёрстки без
`soffice` не выполняется, и это ограничение проверки, а не «замечаний нет».

## Процедура

1. **Разбор документа — инструментами `microsoft-office` и `docx_read_ordered.py` из скилла
   `stand-ftest`.** `docx_read.py file.docx --structure`, затем дамп текста (`S` — каталог
   этого скилла):
   `python3 "$(dirname "$S")/../stand-ftest/scripts/docx_read_ordered.py" file.docx > dump.txt`
   (абзацы и таблицы в порядке документа), при необходимости `--start/--end` по разделу. Скриншоты —
   `docx_read.py file.docx --images DIR/` и просмотр зрения на предмет «что реально
   на экране». Дамп сохраняется в файл: заключение ссылается на раздел/абзац/рисунок,
   а не на пересказ.
2. **Карта разделов.** `references/report-structure.md` скилла `stand-ftest`:
   `skill_view(name='stand-ftest', file_path='references/report-structure.md')`.
   Номера таблиц и рисунков брать из документа, а не из шаблона.
3. **Каждый тест 4.1.N** — проверить наличие и содержание блоков: заголовок с ID
   требований, таблица «Проверяемые требования», «Предварительные настройки»,
   шаги по каждому ID отдельной подсерией, ожидаемые результаты, вывод, свидетельства
   у каждого шага, негативные кейсы перечислены явно.
4. **Таблицы 5–6 (покрытие и глубина).** Каждый интерфейс функции безопасности и
   каждый модуль, реализующий проверяемые требования, сопоставлен хотя бы одному
   существующему тесту; обратная ссылка из теста существует.
5. **Свидетельства.** У каждого шага есть ссылка на рисунок, листинг или файл
   приложения; подписи уникальны и осмысленны; дата/адрес/команда в текстовом
   свидетельстве есть; секреты замаскированы, а не удалены.
6. **Ссылки и заглушки.** Файлы из приложения существуют и совпадают по именам;
   в тексте нет `<IP>`, `<раздел>`, `TODO`, «заполнить позже».
7. **Файл.** `python3 <stand-ftest>/scripts/docx_word_hygiene_check.py file.docx` —
   порядок `pPr`, дубли `bookmarkStart`/`docPr`, битые `r:embed`, нулевые `wp:extent`;
   код возврата 1 — дефекты, которые Word не откроет. Дополнительно PDF-рендер
   (`soffice --headless --convert-to pdf`) — читать глазами те страницы, где
   свидетельства.
8. **Вердикт и заключение** по словарю ниже.

## Словарь вердиктов

| Вердикт | Когда ставится |
|---|---|
| Соответствует | все обязательные блоки есть, свидетельства на месте, блокирующих и существенных замечаний нет |
| Соответствует с замечаниями | структура полная, но есть дефекты, не мешающие приёмке (подписи, оформление, нумерация) |
| Не соответствует | отсутствует обязательный блок, свидетельство или прослеживаемость хотя бы одного требования |
| Не применимо | пункт не требуется для этой поставки — с обоснованием, а не молча |

## Формат заключения

1. Шапка: что проверено (файл, дата, версия, состав комплекта), чем проверено
   (инструменты и команды).
2. Таблица: `Пункт проверки | Что смотрели | Результат | Доказательство` —
   в «Доказательстве» раздел/абзац/номер рисунка или «отсутствует».
3. «Замечания»: ID, приоритет (блокирующее / существенное / косметическое), где
   именно, что не так, почему это важно для приёмки.
4. «Что запросить у разработчика» — краткий список, без пересказа замечаний.
5. Итог — один абзац: можно ли принимать и что мешает.

## Правила

- **Замечание без ссылки на место в документе — не замечание.** «Не хватает
  свидетельств» заменяется на «шаг 2 раздела 4.1.3 не имеет ссылки на рисунок».
- **Требований не выдумывать.** Формулировки — из документа и приказа; если
  раздела или пункта в документе нет — писать «в документе не найден», а не
  «должен быть такой-то» без основания.
- **Проверять по файлу, а не по сопроводительному письму и не по сводке.**
  Сводка и README — заявление стороны, а не доказательство.
- **Считать командами, а не на глаз:** число тестов в плане и в разделе 4,
  число подписей и медиафайлов, число битых ссылок — иначе заключение
  рассыпается на первом же вопросе.
- **Не править документ в рамках проверки.** Правки — отдельная задача в `stand-ftest`.
- **Чужой формат — по их методике.** Если отчёт не по приказу № 76 (внутренний
  стандарт, требования заказчика), карта разделов берётся из их документа
  требований, и это явно пишется в шапке заключения.

## Verification

- [ ] Дамп текста сохранён; числа абзацев/таблиц/медиа сверены с `--structure`.
- [ ] Каждый тест из плана найден в разделе 4 (или отмечено отсутствие).
- [ ] Каждое замечание имеет ссылку на раздел/абзац/рисунок.
- [ ] Таблицы покрытия и глубины сверены с фактическим списком тестов.
- [ ] Все ссылки на приложение разрешаются в существующие файлы.
- [ ] `docx_word_hygiene_check.py` прогнан, результат в заключении.
- [ ] Итоговый вердикт выбран из словаря, а не сформулирован свободно.
