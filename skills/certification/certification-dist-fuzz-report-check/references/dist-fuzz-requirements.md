# Требования к материалам фаззинг-тестирования (Методика ВУ)

Значимые для фаззинга пункты «Методики выявления уязвимостей и недекларированных
возможностей» (Методика ВУ), изложенные по структуре «что именно требуется по
каждому пункту». Текст встроен в скилл: при типовой проверке файл требований
запрашивать не нужно.

Если заказчик передал свою редакцию требований, сверить нумерацию и состав
пунктов: при расхождении ссылаться на пункты его редакции, а этот файл
использовать как каркас заключения.

## 1. Сборка с датчиками срабатывания ошибок

- Фаззинг-тестирование выполняется в отношении специальных сборок компонентов
  Продукта со встроенными датчиками срабатывания ошибок (санитайзерами) — при
  условии, что они применимы для используемого языка программирования.
- Если для языка исходных кодов и среды функционирования датчики неприменимы или
  отсутствуют, их использование не требуется.
- **Перечень используемых датчиков фиксируется в материалах** по итогам
  фаззинг-тестирования.

## 2. Коллекции входных данных — или правила порождения

Если применяются фаззеры, поддерживающие работу с коллекциями входных данных:

- для каждого подлежащего фаззинг-тестированию интерфейса формируются **и
  применяются** коллекции примеров входных данных;
- коллекции вызывают использование различных функциональных возможностей
  тестируемого интерфейса;
- формирование выполняется на основе публично доступных коллекций, генераторов
  коллекций, инструментов автоматического определения и формирования коллекций
  данных либо экспертным способом.

Если применяются фаззеры, коллекции не поддерживающие:

- для каждого интерфейса формируются и применяются **правила порождения** входных
  данных;
- правила вызывают использование различных функциональных возможностей интерфейса.

## 3. Анализ журналов: зависания, сбои, воспроизведение

Для каждой тестируемой цели (интерфейс, участок кода):

- выполняется анализ журналов фаззера на предмет фактов зависаний и сбоев работы
  Продукта, в том числе порождаемых датчиками срабатывания ошибок;
- выполняется проверка **подтверждения воспроизведения** этих фактов в штатном
  режиме функционирования Продукта.

## 4. Генетические алгоритмы за счёт инструментирования

- Фаззер обеспечивает применение генетических алгоритмов фаззинг-тестирования за
  счёт инструментирования кода — если доступны инструменты, позволяющие вести
  такое тестирование с учётом языков программирования, компиляторов и среды
  функционирования Продукта.
- Допустимое инструментирование:
  - по исходным текстам и по бинарному (в том числе промежуточному) представлению;
  - по бинарному представлению — если модуль на интерпретируемом языке
    компилировался в промежуточное представление или проходил принудительную
    компиляцию в исполняемый код («Ahead of Time»).

## 5. Условия завершения фаззинг-тестирования

Проверяется выполнение **как минимум одного** из условий:

- **а)** для фаззеров, подсчитывающих уникальные пути: число найденных уникальных
  путей не менее чем в два раза превышает число образцов входных данных, поданных
  на вход фаззеру;
- **б)** для фаззеров, подсчитывающих покрытие: достигнутый процент покрытия не
  менее чем в два раза превышает процент покрытия, достигаемый при подаче на вход
  стартовых образцов входных данных.

Дополнительно: при покрытии по строкам исходного кода не менее 90 % (по базовым
блокам — не менее 80 %) испытательная лаборатория может не учитывать дальнейший
прирост покрытия при принятии решения о завершении фаззинг-тестирования.

## 6. Продолжительность тестирования каждой цели

- Тестирование каждой фаззинг-цели продолжается до состояния, когда в течение не
  менее двух часов фаззер не находит нового пути либо отсутствует прирост
  покрытия — при условии, что на вход подаются уникальные мутированные данные.

## 7. Что требуется зафиксировать в материалах

В материалах исследований, в формате электронных приложений:

- структурное покрытие для каждого тестируемого модуля;
- параметры сборки каждой фаззинг-цели;
- принципы формирования коллекции, правил, словарей;
- достигнутое структурное покрытие для каждой фаззинг-цели.

## Три места, которые читают неправильно

- **Пункт 1 условный.** Требование действует, только если санитайзеры применимы к
  языку. Для C/C++/Rust/Go они применимы, значит пункт действует. Для
  интерпретируемого языка без AOT-компиляции применение может не требоваться — но
  это должно быть **зафиксировано** в материалах, а не подразумеваться.
- **Пункт 2 — две ветви.** «Коллекции» — если фаззер их поддерживает (AFL++,
  libFuzzer); «правила порождения» — если нет. Проверять надо ту ветвь, которая
  соответствует применённому фаззеру, и не требовать коллекций от фаззера, который
  с ними не работает.
- **Пункт 5 — «как минимум одного».** Для заключения достаточно одного подпункта,
  но указывать надо тот, по которому реально принято решение. «а» при одном
  стартовом образце выполняется вырожденно (любое число путей ≥ 2), и это надо
  писать явно, а не предъявлять как доказательство достаточности.
