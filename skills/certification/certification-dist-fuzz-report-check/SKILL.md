# Проверка материалов фаззинг-тестирования (DIST.FUZZ)

Класс задач: разработчик передал архив с результатами фаззинг-тестирования
компонента продукта, а испытательной лаборатории нужно проверить его на
соответствие формальным требованиям «Методики выявления уязвимостей и
недекларированных возможностей» (Методика ВУ) и выдать заключение по каждому
пункту требований.

Скилл не делает фаззинг, а только проверяет переданные материалы: что реально
лежит в отчете, чего в нём нет, и какие пункты требований из-за этого не
выполнены.

Главный принцип: **все числа считать из первичных артефактов** (`fuzzer_stats`,
`plot_data`, журналы фаззеров, HTML-отчёты покрытия, файлы `crashes/`/`hangs/`),
а не переписывать из сопроводительного файла `Readme`. **Readme разработчика — заявление стороны, а не доказательство.**

Текст требований встроен в скилл — `references/dist-fuzz-requirements.md`
(7 пунктов + дополнительные требования п. 7). При типовой проверке файл
требований запрашивать не нужно; если заказчик передал свою редакцию — сверить
нумерацию и цитировать по ней.

## When to Use

- Пришёл архив (или каталог) с результатами фаззинг-тестирования компонента —
  нужно заключение «соответствует / не соответствует» по пунктам Методики ВУ.
- Надо понять, чего в материалах не хватает, и сформулировать запрос разработчику.
- Надо пересчитать критерии завершения фаззинга (пп. 5, 6) по `fuzzer_stats`
  или восстановить их по журналам, если статистики нет.
- Надо разобрать `crashes/`/`hangs/` и понять, есть ли необъяснённые находки.
- Не для: собственно проведения фаззинг-тестирования, написания отчёта по
  приказу № 76.

## Prerequisites

- Текст требований отдельно не нужен: он встроен в скилл
  (`references/dist-fuzz-requirements.md`).
- `python3` (stdlib достаточно; для HTML-версии отчёта нужен модуль `markdown`).
- `unzip`/`zipinfo` для точечной распаковки; `sha256sum` для фиксации хеша материалов.
- Свободное место: материалы легко занимают 20+ ГиБ в распакованном виде —
  **распаковывать выборочно** (см. шаг 3), не «unzip всего».
- Рабочие материалы (распаковка, выборки, промежуточные файлы) — **только в рабочем
  каталоге под `$TMPDIR`**, созданном `scripts/fuzz_workspace.py create`; не рядом с
  архивом (сетевая шара) и не в `output/`. В `output/` попадают только отчёт и
  приложения.
- Архив часто лежит на сетевой шаре (vmhgfs/NFS): чтение медленнее, `unzip -t`
  на 2,6 ГБ идёт минуты — запускать в фоне.

## Quick Reference

```bash
# рабочий каталог проверки: проверка свободного места + маркер для безопасной уборки
scripts/fuzz_workspace.py create --need-gib 23 --label sflow-28.1 --archive sflow-28.1-cert.zip
scripts/fuzz_workspace.py list --older-than 1
scripts/fuzz_workspace.py purge --older-than 1 --dry-run

# инвентаризация архива без распаковки (central directory)
scripts/fuzz_artifact_inventory.py <archive.zip> --top 12

# метрики одной цели + расчёт пп. 5, 6 (seeds — из журнала или вручную)
scripts/afl_stats_report.py <misc_dir> --engine-log <engine.log> --json stats.json
scripts/afl_stats_report.py <misc_dir> --seeds 1

# восстановление динамики покрытия по журналу, когда fuzzer_stats нет
scripts/afl_log_timeline.py <engine.log> --min-plateau 2

# профиль корпуса: версии формата, num_samples, распределение размеров
scripts/corpus_profile.py <corpus_dir> --sflow

# Markdown-отчёт -> автономный HTML (оглавление, подсветка вердиктов, печать)
scripts/md_report_to_html.py report.md
```

## Procedure

1. **Взять требования и разложить на проверяемые утверждения.**
   Текст уже в скилле — `references/dist-fuzz-requirements.md`; запрашивать файл
   у пользователя не нужно. Каждый пункт превратить в вопрос, на который можно
   ответить «да/нет» по артефактам; подробный разбор —
   `references/vy-metodika-checklist.md`. Если пользователь передал свою редакцию
   требований — сверить нумерацию, при расхождении цитировать по ней.
   *Готово, когда* у каждого пункта есть: что искать, где искать, чем доказать.

2. **Инвентаризация архива без распаковки.**
   `scripts/fuzz_artifact_inventory.py <zip>` даёт объём, группы, крупнейшие
   файлы, наличие описательных документов, `fuzzer_stats`/`corpus`/`crashes`/
   `hangs`/`coverage` по каждой цели, вложенные архивы.
   *Готово, когда* известно: сколько целей, есть ли вообще описательная часть,
   у какой цели нет `fuzzer_stats`, и где лежат журналы.

3. **Создать рабочий каталог и распаковать только нужное.**
   ```bash
   WORK=$(scripts/fuzz_workspace.py create --need-gib <объём из шага 2> \
            --label <компонент>-<версия> --archive <имя.zip> --quiet)
   unzip -o -q <zip> "results/Readme" "results/input/*" \
     "results/*/results/misc/*/*" -d "$WORK/ext"
   ```
   Объём для `--need-gib` брать из инвентаризации (шаг 2). Если он с запасом 15 %
   не влезает в свободное место, распаковывать **по группам**: сначала метаданные
   и `misc/`, затем по одной цели, удаляя группу сразу после разбора
   (`rm -rf "$WORK/ext/<группа>"`). Журналы на гигабайты — по одному и удалять
   после разбора; вложенные `results-*.zip` вскрывать по мере необходимости
   (в них `corpus/`, `crashes/`, `hangs/`, иногда дубли журналов).
   *Готово, когда* в рабочем каталоге лежат только метаданные (`fuzzer_stats`,
   `plot_data`, `fuzzer_setup`, `cmdline`), отчёты покрытия и выборки образцов, а
   `fuzz_workspace.py list` показывает один каталог — этой проверки.

4. **Определить фаззер, цели и число стартовых образцов.**
   `fuzzer_stats` → `afl_version`, `command_line`, `target_mode`; `fuzzer_setup`
   → все `AFL_*` переменные и роли `-M`/`-S`; журнал → `Loaded a total of N seeds`.
   Число стартовых образцов — ключевая величина: от неё зависят оценки по пп. 2 и 5.
   *Готово, когда* для каждой цели выписано: фаззер и версия, число инстансов,
   power schedules, число seeds, таймаут `-t`, лимит памяти `-m`.

5. **Собрать метрики и пересчитать критерии (пп. 5, 6).**
   `scripts/afl_stats_report.py` печатает таблицу по инстансам и сам считает:
   `5«а»` (пути против seeds), `5«б»` (финальное покрытие против первой точки
   `plot_data`), `6` (`time_wo_finds`). Если `fuzzer_stats` нет —
   `scripts/afl_log_timeline.py` восстанавливает плато по журналу.
   *Готово, когда* по каждой цели есть числа и явно указано, выполняется критерий
   или нет, и **по какому подпункту** принято решение.

6. **Разобрать находки: `crashes/` и `hangs/`.**
   Подсчитать файлы, распределение размеров, при известном формате — разобрать
   заголовки (`scripts/corpus_profile.py --sflow`) и поискать заведомо
   «дорогие» поля (например, `num_samples` в миллиардах). Сравнить таймаут `-t`
   с медианным `exec_us` из журнала: если `-t` в сотни раз больше, превышение
   таймаута — не артефакт строгой настройки.
   *Готово, когда* по каждой находке сказано: сколько, какие, есть ли в материалах
   анализ и подтверждение воспроизведения (обычно — нет).

7. **Проверить структурное покрытие (п. 7).**
   Разобрать HTML gcovr по каждой цели и суммарный: строки/функции/ветви,
   список файлов, дата генерации. Отдельно отметить файлы с нулевым покрытием и
   расхождение «карта AFL 5–8 %» против «строки 80–90 %».
   *Готово, когда* есть таблица «файл × цель × суммарно» и вывод о применимости
   льготы «90 % строк / 80 % базовых блоков» **по каждой цели**, а не по сумме.

8. **Проверить датчики (п. 1) и параметры сборки.**
   Искать в материалах явную фиксацию: перечень санитайзеров, флаги, компилятор,
   скрипт сборки, хеш бинаря. Переменные `ASAN_OPTIONS`/`MSAN_OPTIONS` в
   окружении фаззера — только косвенный признак, доказательством не являются.
   *Готово, когда* вывод сформулирован как «зафиксировано / не зафиксировано»,
   без догадок о том, что «наверное, собирали с ASan».

9. **Собрать отчёт.** Структура — `templates/review-report.md`: сводная таблица
   вердиктов, состав материалов, разбор по пунктам (требование → что в материалах →
   оценка → вывод), дополнительные замечания, чек-лист «что запросить»,
   приложения с расчётными таблицами. HTML-версия — `scripts/md_report_to_html.py`.
   *Готово, когда* каждый пункт требований имеет вердикт из фиксированного словаря
   и ссылку на конкретный артефакт в архиве.

10. **Проверить отчёт на согласованность.** Все числа в тексте должны совпадать
    с приложениями и с выводом скриптов; доли и кратности — пересчитаны, а не
    прикинуты; утверждения о дублировании/объёмах — подтверждены сравнением
    размеров файлов, а не именами.
    *Готово, когда* ни одно число в отчёте не взято из `Readme` без сверки.

11. **Убрать рабочий каталог.** `scripts/fuzz_workspace.py clean "$WORK"` —
    печатает освобождённый объём; отчёт и приложения к этому моменту уже в
    `output/`. На автоочистку `$TMPDIR` не рассчитывать: Hermes убирает записи
    только при простое > 24 ч, а 20 ГиБ успевают занять диск за часы.
    *Готово, когда* `fuzz_workspace.py list` не показывает каталогов проверки, а в
    отчёте есть строка «временные материалы удалены, освобождено N».

## Партия модулей (несколько архивов за один заход)

Комплект по нескольким компонентам (`<модуль>-<версия>-cert.zip` × N) проверяется
той же методикой, но с общей структурой работы:

1. Инвентаризовать все архивы сразу, без распаковки: `fuzz_artifact_inventory.py`
   плюс `unzip -Z1 <zip> | cut -d/ -f2 | sort -u` — состав корня сразу показывает,
   какие архивы плоские, а какие с вложенными `results-*.zip`.
2. Каждый архив — в свой workspace (`--label <модуль>-<версия>`): имена целей и
   инстансов (`LA000`) в материалах разных модулей совпадают, общий каталог их
   смешает и подменит статистику.
3. Свести первичные данные в один `dataset.json`: размер и SHA-256 архива, текст
   Readme, по каждой цели — инстансы с `fuzzer_stats` целиком, seeds, состав
   `corpus/`/`crashes/`/`hangs/`, покрытие из gcovr.
4. Отчёты генерировать скриптом из `dataset.json`, а не писать по одному руками:
   одинаковый словарь вердиктов, одна правка чинит все модули, числа в тексте
   берутся только из данных. Шаблон отчёта при этом остаётся один и тот же.
5. После генерации сверять текст с данными программно (число файлов находок,
   покрытие, `time_wo_finds` должны встречаться в MD в отформатированном виде) —
   такой объём глазами не проверяется, а расхождения копятся именно в числах.
6. HTML собирать по каждому модулю отдельно; сводную таблицу по партии предлагать
   пользователю отдельным документом, а не вклеивать в модульные отчёты.

## Критерии по пунктам (что считается доказательством)

| Пункт | Доказательство «выполнено» | Типовой пробел в материалах |
|---|---|---|
| 1. Санитайзеры | Явный перечень датчиков и параметров сборки в материалах; сборка C/C++/Rust/Go с ASan/UBSan/MSan | Перечень не зафиксирован; есть только переменные окружения; нет бинаря и флагов |
| 2. Коллекции / правила | Коллекция на каждый интерфейс, сформированная разработчиком, с описанием принципов; либо правила порождения | Стартовый корпус = 1 файл; итоговый корпус — продукт самого фаззера; словарей нет |
| 3. Анализ журналов | Таблица триажа находок + подтверждение воспроизведения в штатном режиме | Есть только сырые журналы; `hangs/` не разобраны; воспроизведение не описано |
| 4. Генетические алгоритмы | Инструментирование подтверждено обратной связью по покрытию, есть прирост путей | Не указан тип инструментирования (исходники/LTO/бинарь) |
| 5. Критерий завершения | Пути ≥ 2× seeds **или** покрытие ≥ 2× стартового; либо льгота 90 % строк / 80 % блоков | Покрытие от стартовых образцов не измерено; льгота считается по сумме целей, а не по цели |
| 6. ≥ 2 ч без новых путей | `time_wo_finds` ≥ 2 ч у каждого инстанса (или плато по журналу) | По части целей нет `fuzzer_stats`; прогон прерван без финальной статистики AFL |
| 7. Покрытие + параметры | HTML/XML покрытие по каждой цели, параметры сборки, принципы коллекций и словарей | Параметры сборки и принципы коллекций отсутствуют |

## Словарь вердиктов

Держать формулировки одинаковыми во всём отчёте — по ним сверяются между собой
пункты и приложения.

- **Соответствует** — артефакты прямо подтверждают требование.
- **Соответствует частично** — подтверждена часть составляющих пункта
  (в п. 7 их четыре: покрытие по цели, покрытие суммарно, параметры сборки,
  принципы коллекций) — указывать «N из M».
- **Не соответствует** — артефакты прямо противоречат требованию.
- **Не подтверждено материалами** — проверить нельзя, потому что нужного
  артефакта в материалах нет. Это **не** то же самое, что «не соответствует»:
  разработчику запрашивается артефакт, а не переделка работы.

Формулировать про материалы, а не про людей: «материалы не содержат …» вместо
«проверка не выполнялась». Второе — упрёк, который по архиву не проверяется, и
разработчик справедливо возразит, что анализ у него есть, просто не приложен.

## Pitfalls

- **Не распаковывать архив целиком.** 2,6 ГБ сжатого превращаются в 21–23 ГиБ;
  на типовой VM это половина диска. Сначала `unzip -l`/инвентаризация, потом
  точечная распаковка по шаблонам.
- **Рабочие каталоги не должны накапливаться.** `$TMPDIR` (scratch Hermes) чистится
  только при простое > 24 ч, а распакованные 20 ГиБ успевают забить диск ВМ за
  часы (здесь 17 ГБ свободно из 40). Правило: `purge --older-than 1` в начале
  новой проверки, `clean` — в конце.
- **`/tmp` — не место для материалов.** На этой ВМ `/tmp` — tmpfs на 3,7 ГиБ, то
  есть RAM: распаковка туда съест память и всё равно не влезет. `/var/tmp` — на
  диске, но при перезагрузке **не** чистится (в `tmpfiles.d` правило `q`, а не `D`),
  так что «очистится после ребута» — неверная посылка; очистку обеспечивает только
  явный `clean`/`purge`.
- **Не распаковывать рядом с архивом.** Архив обычно лежит на vmhgfs/NFS: запись
  туда засоряет шару заказчика и идёт медленнее локального диска.
- **Дубли ищутся по паре «имя + размер», а не по имени.** Одноимённые
  `plot_data`/`fuzzer_stats` у 20 инстансов — это разные файлы. Настоящий дубль —
  совпадение имени и размера (например, журналы и распакованные, и внутри
  вложенного `results-*.zip`).
- **`fuzzer_stats` может отсутствовать у части целей.** Это не повод писать
  «метрики недоступны»: покрытие и плато восстанавливаются по журналу фаззера
  (`afl_log_timeline.py`), а в отчёте указывается, что это реконструкция.
- **Нет строки `Statistics: ...` в журнале — прогон прерван.** Штатное завершение
  AFL печатает финальную статистику; её отсутствие означает kill контейнера, и
  причину остановки по материалам установить нельзя. Это отдельное замечание.
- **`ASAN_OPTIONS`/`MSAN_OPTIONS` в окружении ≠ сборка с санитайзерами.**
  Переменные ставит оркестратор; в одном бинаре ASan и MSan несовместимы, так что
  по ним нельзя определить, что реально включено. Пункт 1 требует явной фиксации.
- **Один стартовый образец делает п. 5«а» вырожденным.** 3400 путей против 1 seeds
  формально даёт кратность 3400×; это надо назвать прямо, а не предъявлять как
  доказательство достаточности фаззинга. Достаточность проверяется по «б» и по
  абсолютному покрытию.
- **Покрытие карты AFL и покрытие gcovr — разные величины.** 5 % по карте при
  90 % по строкам — нормально (карта шире, чем файлы модуля, попавшие в gcovr).
  Сравнивать их нельзя, а расхождение надо объяснять в отчёте.
- **«Ветви» gcovr ≠ «базовые блоки» Методики.** gcovr не даёт покрытие по базовым
  блокам, поэтому вторую половину льготы (80 % блоков) по таким отчётам оценить
  невозможно — так и писать.
- **Льгота 90 %/80 % применяется к цели, а не к сумме целей.** Объединённое
  покрытие двух целей всегда выше каждой по отдельности и маскирует слабую цель.
- **Таймаут сравнивать с реальным временем исполнения.** При `-t 1000` мс и
  медианном `exec_us` 500–1500 мкс превышение в 1000 раз — это не «строгий
  таймаут», а вероятное зависание; при `exec_us` ~1000 мс те же таймауты, наоборот,
  артефакт настройки. Медиану брать из строк `exec_us=` журнала.
- **Корпус фаззера ≠ сформированная коллекция.** Итоговый `corpus/` из тысяч
  мутированных файлов выглядит разнообразно, но он продукт фаззера, а не
  коллекция разработчика; п. 2 проверяет именно стартовый корпус и принципы.
- **Числа из `Readme` перепроверять.** Сопроводительный файл обычно содержит
  только сводку покрытия и умалчивает о зависаниях, отсутствии статистики и
  нулевом покрытии отдельных файлов; таблицу gcovr в нём стоит сверить с HTML
  (обычно совпадает), а вот выводы Readme — не источник.
- **Заголовки таблиц и единицы.** В отчётах фигурируют и ГиБ, и ГБ: 21,8 ГиБ и
  23,4 ГБ — один и тот же объём. Указывать обе величины, чтобы не спорить с
  разработчиком о цифрах.
- **Плоская раскладка ломает `afl_stats_report.py`.** В части архивов статистика
  лежит как `misc/engine.LA000.fuzzer_stats` без каталога-инстанса, а скрипт ждёт
  `<misc>/LA0NN/fuzzer_stats` и показывает «нет инстансов». Собрать
  `statview/LA000/` копиями `misc/engine.LA0NN.fuzzer_stats` и подать `statview`.
- **`validator-log.txt` — не протокол триажа.** Это журнал оркестратора (кто
  поднялся, когда сохранялись образцы); ссылаться на него как на «анализ находок»
  нельзя. Триаж — таблица с классификацией и воспроизведением.
- **Заявление Readme «находки ложные, при триаже не подтвердились» — не триаж.**
  Если файлы в `hangs/` лежат, а таблицы и протокола воспроизведения нет, вердикт
  по п. 3 остаётся «не соответствует», как бы уверенно ни был написан Readme.
- **Вердикты в MD должны быть жирными.** `md_report_to_html.py` красит ячейку по
  `<td><strong>…`; обычный текст остаётся серым и таблица теряет смысл. Составной
  вердикт п. 5 писать как `**Соответствует по подпункту «а»** (по подпункту «б»
  не подтверждено)` — тогда сработает правило `v-mixed`; если заарить всю фразу,
  ячейка станет зелёной и скроет оговорку.
- **Широкие таблицы транспонировать.** 12 колонок «инстанс × метрика» не влезают
  в страницу и рвутся при печати; вид «Показатель | `LA000` | `LA001`» (12 строк)
  читается без горизонтальной прокрутки.
- **Объём рабочего каталога замерять до генерации финальных HTML.** `clean` только
  печатает освобождённый объём, а строка «временные материалы удалены,
  освобождено N» — часть Verification; иначе отчёты придётся перегенерировать
  ради одной строки.
- **`stability` < 100 % завышает `edges_found`.** Нестабильная карта даёт ложные
  «новые пути»: при 40–80 % п. 5«а» выполняется формально, и это надо оговорить.
  Вывод по п. 4 при этом сохраняется — форк-сервер, CmpLog и прирост путей видны
  и без детерминизма.
- **Таймаут в сотни секунд отключает обнаружение зависаний.** `-t 200000` мс при
  медиане исполнения 120–170 мс означает, что зависанием считается только
  двадцатиминутный цикл: пустой `hangs/` не доказывает устойчивость цели. Это
  замечание к пп. 3 и 6, а не признак качества.
- **Формулировка «не подтверждено» экономит цикл.** Требование «перечень датчиков
  фиксируется в материалах» нарушено отсутствием записи, а не отсутствием
  санитайзеров; в запросе должно быть «приложите перечень и параметры сборки», а
  не «переделайте фаззинг».
