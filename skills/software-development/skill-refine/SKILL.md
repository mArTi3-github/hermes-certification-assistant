# Улучшение скилла

Вычитывает один скилл как инструкцию для агента: находит места, где правило
сформулировано частным случаем, двусмысленно, избыточно или непроверяемо,
разбирает находки с человеком по одной и переписывает скилл так, чтобы он описывал
решение класса задач. Противоречия между материалами профиля не ищет и ничего не
публикует — это `profile-audit` и `profile-contribution`.

## When to Use

- «улучши скилл <имя>», «почисти от частностей», «сделай универсальным»,
  «проверь формулировки».
- Скилл писали под один продукт, стенд или заказчика, а применять будут к другим.
- После неудачного прогона: агент сделал не то, потому что правило читалось двояко.
- Перед публикацией скилла, которым будет пользоваться команда.
- Не для: поиска противоречий между файлами (`profile-audit`), публикации правки
  (`profile-contribution`), ревью кода внутри `scripts/` (обычное код-ревью).

## Граница с profile-audit

| | `profile-audit` | `skill-refine` |
|---|---|---|
| Единица работы | материалы профиля целиком | один скилл |
| Вопрос | «одно место противоречит другому?» | «так ли это сформулировано, чтобы работать в общем случае?» |
| Метод | сканер улик и опровержение | чтение и чек-лист антипаттернов |
| Итог | точечные правки по согласию | переписанные разделы скилла |

Оба спрашивают по одному вопросу за раз. Аудит сравнивает две редакции текста,
улучшатель судит одну.

## Что считается находкой

Классы — в `references/antipatterns.md` (признаки, типовой вопрос, образец
правки): `over-specific` частное вместо правила · `misplaced` частное в общем
теле, место которого — `references/` · `underdetermined` правило без условия
применения · `ambiguous` читается двояко · `redundant` уточнение, не меняющее
поведения · `unverifiable` утверждение без способа проверки · `duplicated` одно
правило в двух местах · `dead-weight` текст ни о чём (история, мета-объяснения,
обещания).

Находка — гипотеза с цитатой и номером строки, а не приговор. Прежде чем
спрашивать, проверь, не отвечает ли на вопрос сам скилл, соседний файл, история
коммитов.

## Порядок работы

1. **Прочитать скилл целиком.** `SKILL.md` и весь каталог
   (`search_files target='files'`): `references/`, `scripts/`, `templates/`.
   Специфика, вынесенная в `references/`, — нормальная архитектура, а не находка:
   тело ссылается на файл, а не пересказывает его. Готово, когда назначение
   каждого файла сводится к одной строке.

2. **Собрать находки по классам.** Каждая: класс, цитата, `файл:строка`, гипотеза
   правки («было → станет»). Готово, когда список записан в
   `$TMPDIR/skill-refine/<скилл>.md` и число находок названо.

   Порог: находка обязана менять поведение агента или его понимание задачи. «Мне
   не нравится стиль» — не находка. Находок больше двадцати — сначала свести
   однотипные в одну (одно решение на класс: «все адреса стендов становятся
   плейсхолдерами?»), иначе сессия вопросов превращается в допрос.

3. **Коротко представиться.** Две-три строки: что скилл делает, для какого класса
   задач, что в нём уже держится хорошо. Затем повестка — одна строка на находку:
   человек видит объём и может ответить сразу на несколько.

4. **Интервью по одной находке.** Формат вопроса:

   ```
   Находка 3 из 8 — over-specific — SKILL.md:78
   цитата: «...»
   Вопрос: адрес стенда здесь — правило или пример текущего прогона?
   1) Рекомендуется: заменить на `<стенд>` и сослаться на файл прогона
   2) Оставить как пример с пометкой «значения меняются»
   3) Удалить абзац
   Свой вариант тоже подходит — напиши его словами.
   ```

   Правила ведения сессии — скилл `interview`: загрузи его до первого вопроса.
   Своё здесь: повестка строится по находкам, цитата и номер строки обязательны
   (человек не должен искать место сам), «оставь как есть» и «не знаю» — законные
   ответы, находка уходит в `open`, а на следующую без ответа не переходить.

5. **Записать решение.** На каждую находку — строка в
   `<профиль>/.audit/skill-refine/<скилл>.jsonl`: `ts`, `class`, `where`, `quote`,
   `question`, `answer`, `status`, `change`. `status`: `resolved` (правка
   применена или решение «оставить»), `open` (ответа нет), `deferred` (отложено
   осознанно). Каталога нет — создать. Это память между прогонами: повторный
   прогон не спрашивает снятое.

6. **Переписать.** Правка — `skill_manage(action='patch')` по одному месту, а не
   перезапись файла, если меняется меньше половины текста: так сохраняется
   остальной текст и не теряются правки фоновой ревизии. Итоговый текст
   показывается до применения, когда меняется формулировка правила, и не
   показывается, когда правка механическая (опечатка, вынос абзаца в
   `references/`) и ответ уже дан. `version` скилла поднимается: patch — текст без
   нового правила, minor — новое правило или раздел.

   Порядок правок — от общего к частному: сначала структура и правила, потом
   примеры и формулировки. Переписанный раздел обнуляет часть находок, а правка
   «в лоб» по старой нумерации строк промахнётся.

7. **Проверить.** Перечитать изменённые разделы целиком и убедиться: ссылки на
   `references/` резолвятся, плейсхолдеры названы и объяснены, второй экземпляр
   переписанного правила не остался, `description` ≤ 60 символов и по-прежнему
   описывает задачу. Прогнать `python3 <клон>/tools/skill_lint.py`, если скилл
   публикуется, и тесты его `scripts/`, если они правились. Если скилл входит в
   материалы профиля — инкрементальный прогон `profile-audit`
   (`audit_scan.py --mode incremental` из скилла `profile-audit`): переписанный текст мог создать
   новое расхождение с README или соседним скиллом. Сканер читает клон, а не профиль: скилла,
   которого в клоне ещё нет (новый скилл), прогон не видит — скопируй каталог **этого** скилла в клон до прогона —
   только его, не всё дерево профиля: штатные скиллы линт встречает ошибкой
   «политика публикации его не включает», и настоящие ошибки тонут в этом шуме; после
   прогона вернуть клон в исходное состояние (`git checkout -- skills && git clean -fdq skills`,
   источник правки — профиль), иначе «находок нет» относится к прежнему составу, а не к твоему тексту.

8. **Напомнить про публикацию, но не публиковать.** Скилл в профиле — рабочая
   копия: правка исчезнет при следующей синхронизации, если не попадёт в
   репозиторий. Напомнить три факта: категория решает, публикуется ли скилл
   (`certification/` — по умолчанию, остальное — по строке в `[publish]`;
   проверка — `tools/publish_policy.py --status`); публикация —
   `tools/contribute.sh -m "<скилл>: <что изменилось>"` из клона; порядок правок,
   PR и релиз — в `profile-contribution`. Публикацию запускать только по отдельной
   просьбе: правка и публикация — разные последствия.

## Когда раздел уезжает в `references/`

`misplaced` — не только «частное в общем теле». Тот же класс: тело скилла переросло рабочий
размер (больше ~300–350 строк или ~40 КБ) и загружается целиком в каждой сессии, где он нужен
хотя бы краем.

- Переносится **дословно** (`write_file` нового `references/<тема>.md` + замена раздела в теле),
  а не пересказывается: пересказ теряет механику («почему так»), которую в следующий раз будут
  восстанавливать заново.
- В теле остаётся **короткий указатель**: 10–12 самых дорогих пунктов одной строкой каждый
  плюс ссылка на файл. Полный список без выборки — это тот же объём, только в двух местах.
- Имя файла — по теме (`pitfalls.md`, `campaign-status.md`), не по дате и не по инциденту.
- После переноса проверка **в обе стороны**: каждый `references/…`/`scripts/…`, упомянутый в
  тексте, существует, и каждый файл на диске упомянут в тексте — иначе получается либо битая
  ссылка, либо осиротевший файл, который не найдёт ни читатель, ни линт.

```python
import os, re
t = open(D + "/SKILL.md", encoding="utf-8").read()
refs = set(re.findall(r"(?:references|scripts)/[A-Za-z0-9._-]+", t))
print("нет на диске:", [r for r in refs if not os.path.exists(os.path.join(D, r))])
print("не упомянуты:", [p for p in ondisk if p not in refs])
```

## Парный скилл: проверка или исполнение

Прежде чем создавать `<проверка>-check-report`, проверьте, есть ли в скилле **режим
рецензирования**, а не слово «проверка» в описании. Признаки режима: вход — чужой отчёт, а не
изделие; словарь вердиктов (соответствует / не соответствует / не применимо); заключение с
замечаниями и ссылками на места в документе. Если всего этого нет, «проверка» в описании
означает исполнение тестов функций безопасности — парный скилл не создаётся, а `description`
исполняющего переписывается так, чтобы слова не читались как рецензирование («чтение,
написание, обновление» вместо «чтение, написание, проверка»).

Создавая проверочный скилл, критерии берите из уже существующего артефакта парного скилла
(карта разделов, шаблон блока теста) и ссылайтесь на него через `skill_view(name='<парный>',
file_path='references/…')`, а не копируйте себе: копия расходится с оригиналом после первой
правки. Чего в артефакте нет — не додумывайте: в заключение идёт «в документе не найден», а
новые критерии согласуются с человеком отдельным вопросом.

## Два вопроса, которые решают почти всё

1. **Правило или экземпляр?** «Если завтра другой продукт, другой стенд, другой
   набор функций — предложение останется верным?» Нет — это экземпляр: он либо
   становится примером с оговоркой, либо уезжает в `references/<продукт>.md`, а в
   теле остаётся процедура и плейсхолдер.
2. **Что изменится, если убрать?** Ничего — `redundant` или `dead-weight`:
   удалять. Что-то меняется, но непонятно что — `ambiguous` или
   `underdetermined`: спрашивать.

Вспомогательный вопрос: **как это проверить?** Командой, файлом, ответом
интерфейса — правило остаётся. Никак — это обещание, а не правило.

## Частые ошибки

- **Ставить настоящее значение в колонку «было».** Пример находки целиком становится текстом
  скилла: адрес стенда, имя узла, логин из «было» уезжают в публичный репозиторий и остаются
  в истории git. Плейсхолдеры нужны в обеих колонках — правдоподобность даёт форма
  (`https://<адрес>:<порт>`), а не реальное значение.
- **Вычищать специфику вместо её изоляции.** Адрес стенда, набор проверяемых
  функций, имя заказчика — не мусор, а данные прогона: они нужны, но не в тексте
  правила. Правильный ход — плейсхолдер плюс файл-источник, а не удаление факта.
- **Ссылаться на скрипт соседнего скилла путём из его каталога.** `scripts/<файл>.py` в тексте
  читается как файл рядом с твоим скиллом: линт аудита даёт находку `paths`, а исполнитель ищет
  файл не там. Правильно — «`<файл>.py` из скилла `<имя>`» без слэш-пути.
- **Путать с аудитом профиля.** Расхождение правила с README — находка
  `profile-audit`: здесь судится один скилл изнутри, а не его отношения с соседями.
- **Считать общую фразу универсальностью.** «Действовать по ситуации» без условия
  применения — `underdetermined`, а не переносимое правило.
- **Спрашивать по каждой строке.** Пять однотипных адресов — один вопрос о
  политике, а не пять.
- **Переписывать файл целиком ради одной находки.** Полная замена теряет чужие
  правки и делает дифф нечитаемым для ревью.
- **Спрашивать то, что есть в скилле.** Ответ часто стоит тремя абзацами ниже:
  дочитать раздел дешевле, чем задать вопрос.
- **Менять смысл правила вопреки ответу.** «Оставь как есть» — тоже решение, и оно
  закрывает находку без правки.
- **Заканчивать без напоминания о публикации.** Правка в профиле не уехала —
  после одной синхронизации её нет.

## Verification

- [ ] Каждая находка закрыта ответом либо записана `open`/`deferred` в журнал.
- [ ] Реальных адресов, имён узлов и логинов нет ни в правилах, ни в примерах
      «было → станет» — вместо них плейсхолдер и ссылка на файл-источник.
- [ ] Ссылки на `references/` резолвятся, плейсхолдеры объяснены.
- [ ] `description` ≤ 60 символов, `version` поднят.
- [ ] Линт (и тесты `scripts/`, если правились) прошли.
- [ ] Способ публикации назван, сама публикация не запущена.
