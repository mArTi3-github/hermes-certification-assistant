# Штатные скиллы Hermes и их обновления

Глубина к правилу 7: почему правка штатного скилла дороже, чем кажется, и куда девать
собственные дополнения.

## Две витрины, которые путают

| Каталог | Что это | Кто владеет |
|---|---|---|
| `~/.hermes/hermes-agent/skills/` | бандл установленного Hermes — эталон апстрима | пакет Hermes |
| `~/.hermes/skills/` и `~/.hermes/profiles/<имя>/skills/` | рабочие деревья, откуда агент грузит скиллы | пользователь |

Штатный скилл, которого нет в бандле, апстрима не имеет вообще — в этой сборке так с `docx`:
его править и публиковать можно, обновлять будет нечего. Но «нет в бандле сейчас» ≠ «не был
штатным»: апстрим регулярно сворачивает родственные скиллы в один (`docx`, `powerpoint`, `xlsx`
→ `microsoft-office`), и у скилла просто кончилась история. Это выясняется историей пакета, а не
памятью: `git -C ~/.hermes/hermes-agent log --oneline -- skills/<категория>/<скилл>` — коммит
вида «fold … into one … skill» и есть точка, после которой апстрима нет.

## Что именно изменилось относительно штатной версии

Когда спрашивают «в профиле своя версия штатного скилла — что в ней поменялось», отвечают
диффом **от блоба апстрима**, а не от соседней копии в `~/.hermes/skills`: это такое же рабочее
дерево, его тоже правят, и как эталон оно даёт ложную картину (в нём может стоять своя
формулировка того же раздела).

1. **Эталон** — git-история пакета `~/.hermes/hermes-agent`. Последняя штатная редакция:

   ```bash
   U="$TMPDIR/up-skill"; rm -rf "$U"; mkdir -p "$U"
   git -C ~/.hermes/hermes-agent archive '<коммит слияния>^' skills/<категория>/<скилл> | tar -x -C "$U"
   diff -rq "$U/skills/<категория>/<скилл>" "$HERMES_HOME/skills/<категория>/<скилл>" --exclude=__pycache__
   ```

   `diff -rq` по каталогу, а не по `SKILL.md`: так видно **добавленные файлы** (новые скрипты) и
   то, что остальное — `LICENSE`, `references/`, прочие скрипты — осталось стоковым.
2. **По SKILL.md читают обе стороны.** `diff -u` показывает не только добавленное: раздел,
   который в профиле **выброшен** относительно апстрима (например длинный блок сборки общего
   окружения, заменённый коротким `pip install`), — это потеря, и о ней говорят первой, а не как
   о «сокращении»: у коллеги рецепт из текста уже не прочитать.
3. **Тесты — тоже факт для ответа.** Если `tests/` идентичен стоковому, добавленные скрипты в
   этой копии не покрыты ничем; это называют, а не умалчивают.
4. **Статус в Hermes проверяют до диффа**, иначе легко подписаться под неверной посылкой
   «скилл перестал получать обновления»: `hermes skills list | grep <имя>` (колонка источника —
   `builtin`/`local`), `hermes skills list-modified`, отсутствие записи в
   `skills/.bundled_manifest`. `local` + нет в манифесте — апдейтов у копии нет вовсе, и об этом
   говорят прямо, прежде чем разбирать изменения.
5. **Форма ответа**: таблица «файл/сущность → в штатной → в профиле», затем изменения SKILL.md по
   разделам (одним пунктом на механизм, а не пересказом диффа), отдельно «что потеряно» и «что не
   покрыто тестами». Источник сравнения называют явно (коммит апстрима), чтобы цифры строк можно
   было перепроверить; `version:` в копии обычно уже поднят — это первая строка таблицы, но не
   ответ.

## Почему «поменять только описание» не работает

`skills/.bundled_manifest` хранит пары `имя: хеш каталога`. Синхронизация сравнивает хеш
**всего каталога**, а не отдельных файлов, поэтому одна переформулированная строка в
`description` даёт тот же эффект, что переписанный SKILL.md: скилл печатается как
`~ <имя> (user-modified, skipping)` и перестаёт получать апдейты. Дешёвого компромисса нет —
либо сток, либо форк.

## Команды

```bash
hermes skills list                 # колонка источника: builtin/builtin, local/local
hermes skills list-modified        # где локальная копия разошлась с бандлом
hermes skills diff <имя>           # построчно, что именно разошлось
hermes skills reset <имя> --restore --yes   # вернуть стоковую версию из бандла
```

`reset` без `--restore` сохраняет локальную копию рядом, а не выбрасывает её — но при чистом
рабочем дереве проще сначала сохранить нужное в отдельный скилл.

## Перенос штатного скилла не приживается

Синхронизация знает канонический путь штатного скилла и возвращает его туда; изменённую копию
в чужой категории она оставляет с предупреждением и не перезаписывает. Итог — два скилла с
одинаковым именем в индексе агента, из которых обновляется только один. Поэтому штатные скиллы
не переносим и не переименовываем — даже если категория кажется неподходящей.

## Что делать вместо форка

1. Создать **отдельный скилл-дополнение** рядом, в той же категории, с именем
   `<штатный>-notes` и описанием, объясняющим, что это дополнения.
2. Сослаться на него из `related_skills` профильных скиллов, которые им пользуются, — иначе
   агент о нём не вспомнит.
3. Содержимое писать только о том, чего нет в апстриме: локальные ограничения, проверенные
   обходы, особенности этого окружения. Пересказ штатного скилла — мусор, который устареет
   вместе с апстримом.
4. Если дополнение нужно команде — оно проходит обычный цикл: категория → политика → PR.

## Ритуал после обновления Hermes

```bash
hermes skills list-modified   # показать расхождения
hermes skills diff <имя>      # решить: сток или свои дополнения
```

Расхождение у штатного скилла — сигнал, что кто-то (возможно, прошлая сессия) правил бандл на
месте. Нужное переносится в скилл-дополнение, после чего `reset --restore` возвращает сток и
апдейты снова приходят.
