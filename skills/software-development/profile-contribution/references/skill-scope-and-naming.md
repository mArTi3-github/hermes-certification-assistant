# Что публикуется и под каким именем

Глубина к правилу 9 и к разделу о политике публикации: какой скилл попадает в репозиторий,
как его назвать, как размечать и почему переименование дороже, чем кажется.

## Три механизма, которые легко перепутать

| Механизм | Что решает | Чего не решает |
|---|---|---|
| `skills/.bundled_manifest` в профиле | происхождение: штатный скилл Hermes или авторский | ничего о публикации |
| `distribution_owned` в `distribution.yaml` | какие пути `hermes profile update` перезаписывает у получателя | состав: запись `skills/` означает «что положишь, то и приедет» |
| `publish.list` в корне репозитория | **состав**: что вообще попадает в GitHub | обновление и порядок загрузки |

Состав публикации определяется **категорией** (`[defaults] publish_categories`), а `publish.list`
нужен для исключений в обе стороны. Проверка картины:
`python3 tools/publish_policy.py --status --profile <каталог профиля>` — печатает публикуемое,
локальное и неклассифицированное.

## Почему нельзя опираться на «что лежит в git»

Отслеживаемые файлы — следствие, а не правило: они молчаливы, и скрипт, копирующий всё авторское
из профиля, опубликует приватное вместе с публичным. Поэтому:

Приоритет правил в `publish.list` (сверху вниз, первое совпадение побеждает):

| Место | Смысл |
|---|---|
| `[private]` | не публикуется никогда, даже если категория публикуемая |
| `[publish]` | публикуется, даже если категория не в списке по умолчанию |
| `[defaults] publish_categories` | все скиллы категории публикуются сами |
| вне списков | локально: в GitHub не попадает и коллегам не приезжает |

Поэтому:

- скилл публикуемой категории не требует ни строки в `[publish]`, ни `contribute.sh -i`:
  категория и есть решение о публикации;
- скилл вне `[private]`, `[publish]` и публикуемых категорий — неклассифицированный: линт
  падает, если он уже в репозитории, а `contribute.sh` спрашивает по каждому (`[c]` перенести
  в `certification/`, `[l]` записать в `[private]`, `[Enter]` пропустить) или без терминала
  печатает подсказку с `publish_policy.py --classify`;
- перенос в приватные = строка в `[private]` + `git rm -r skills/<путь>`; у получателей хвост
  снимает `sync.sh --prune`.

## Как размечать

Индекс скиллов, который агент видит при выборе, содержит только **категорию, имя и описание**
(группами по категории). `metadata.hermes.tags` в индекс не попадают — теги не влияют на выбор
скилла и служат людям и поиску по файлам.

| Ось | Правило |
|---|---|
| Категория (каталог в `skills/`) | единственная ось группировки в индексе: процедуры — `certification/`, их инструменты — `certification/tools/` (отдельная группа `certification/tools`) |
| Имя | свободное: `name` во фронтматтере равно имени каталога. Префикс `certification-` — историческая привычка, правилом не является и линтом не проверяется |
| Описание | первая фраза — триггер («Сертификация: …», «Фаззинг по Методике ВУ: …»); линт требует ≤ 60 символов |
| Теги | 1–3 facet-тега (`fstek`, `fuzzing`, `docx`); не дублировать имя и не считать их правилом |

Куда класть новый скилл:

| Что описывает | Куда |
|---|---|
| Процедуру сертификации по приказу/методике | `skills/certification/` |
| Служебный инструмент, на который опираются сертификационные скиллы | `skills/certification/tools/` |
| Инструмент AppSec, используемый и вне сертификации | `skills/security/` |
| Работу с документом или офисным форматом | `skills/productivity/` |
| Процесс команды или репозитория | `skills/software-development/` |

## Цена переименования и переноса

- `sync.sh` копирует аддитивно: после переноса в профиле остаются оба каталога, и в индексе
  появляется дубль. Хвост снимает `sync.sh --prune`, но только для путей, записанных в
  `skills/.distribution_managed`: при первом запуске после смены политики запишите туда
  прежний состав публикации, иначе удалять ему будет нечего. Копия удалённого — в
  `.backup/pre-sync-*/removed/`.
- Перенос в `certification/` или `certification/tools/` не переименовывает скилл: при ответе
  `[c]`/`[t]` скрипт переносит каталог как есть и копирует его в репозиторий по новому пути.
- Переименование = новый каталог + `name` во фронтматтере + обновление всех ссылок (README,
  другие скиллы, память агента). Делать одним коммитом; линт сверяет `name` с каталогом.

## Проверка после правки разметки

```bash
python3 tools/publish_policy.py --status --profile "$HERMES_PROFILE"   # состав и классификация
python3 tools/skill_lint.py --history                                  # фронтматтер, секреты, расхождения
```

Изменения самой политики проверяйте на одноразовых копиях, а не сразу в `main` и не на живом
профиле: скопируйте репозиторий в `$TMPDIR`, положите туда фиктивный скилл вне политики
(`skills/security/fake/SKILL.md`) — линт должен дать ошибку, и фиктивный
`skills/certification/tools/fake/SKILL.md` — он публикуется по категории и ошибки не даёт;
затем профиль-пустышку с `--published`, `--unclassified`, `--classify private` и
`sync.sh --prune` (старый путь исчезает в `removed/`, новый появляется).
