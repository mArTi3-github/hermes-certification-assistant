# Фоновая ревизия скиллов и публикация

Скиллы профиля меняют два независимых писателя с разным жизненным циклом. Пока их путают, каждая
публикация выглядит как расхождение, а каждая сверка — как чужая правка.

## Кто пишет

| Писатель | Как узнать | Что делает |
|---|---|---|
| Фоновая ревизия сессии (в журнале — актор `curator`) | `skills/.curator_ledger.jsonl`: `actor: curator`, `evidence.session_id` твоей сессии | дописывает и переписывает скиллы во время работы, пачками, по нескольку десятков правок за сессию |
| Недельный проход `hermes curator` | `hermes curator status`: интервал, последний прогон, число управляемых скиллов | архивирует и консолидирует скиллы; консолидация по умолчанию выключена, неуправляемые скиллы он не трогает |

Актор ставится функцией `derive_actor()` из файла `skill_ledger.py` (каталог `tools/` установки
Hermes): `curator`, если сработал `is_background_review()`, иначе `agent`. Отсюда два вывода, на
которых ломаются догадки:

- «`hermes curator status` говорит, что последний прогон был давно» **не** опровергает авторство
  правок: недельный проход и фоновая ревизия — разные механизмы;
- mtime файла ничего не доказывает: синхронизация и `cp -a` его не сохраняют, а ревизия пишет
  поверх того же файла. Единственный источник атрибуции — журнал и sha256 манифестов в нём.

Запись журнала: `{id, ts, actor, action, skill, evidence: {session_id, file_path}, before: [{path,
sha256}], after: [...]}`. Сравнение `before[].sha256` с текущим хешем файла отвечает на вопрос
«правил ли его кто-то после меня» без всякой хронологии.

## Атрибуция перед публикацией

```bash
PROFILE=~/.hermes/profiles/hermes-certification-assistant
# записи за сегодня: какие скиллы и в какой сессии менялись
jq -r 'select(.ts|startswith("2026-01-01")) | [.ts,.actor,.skill,.action,(.evidence.session_id // "-")] | @tsv' \
  "$PROFILE/skills/.curator_ledger.jsonl" | sort
# то же штатной командой, по одному скиллу
hermes curator ledger --skill profile-contribution --limit 20
# что из этого уже опубликовано, а что нет
python3 ~/work/hermes-certification-assistant/tools/publish_check.py --json
```

Порядок работы — один цикл, без очередей:

1. `python3 ~/work/hermes-certification-assistant/tools/attribution.py` — что не опубликовано и
   чьё: списки «агент» и «curator» плюс готовая строка коммита. Одна команда вместо `jq` и
   сравнения mtime.
2. `~/work/hermes-certification-assistant/tools/contribute.sh -m "…"` — публикует **весь**
   накопленный дельта в одной ветке.
3. `--split-head` вызывается из `contribute.sh` сам: коммит до push раскладывается на два — свои
   файлы и «заметки куратора … (background review, сессия <id>)». Если автор один, коммит
   остаётся один.
4. мерж → `tools/sync.sh` → `publish_check.py` (код 0), затем `attribution.py` (публиковать
   нечего).
5. `--force` не используется, ревизию не догоняют вторым PR: пока ветка не смержена, её правки
   забирает тот же PR вторым коммитом; после мержа — следующий цикл (новый PR).

`--force` по кураторским дельтам не применяется: содержимое обычно верное (оно описывает грабли
той же сессии), а гейт `sync.sh` с этого момента блокирует любые другие обновления профиля.
Откатывать молча тоже нельзя — только через вопрос человеку с диффом.

## Разложение коммитов: два правила

- **Чужие заметки ложатся ниже своей правки.** Верхний коммит ветки должен совпадать по смыслу с
  заголовком PR: иначе ревьюер открывает PR и видит сверху коммит про чужие правки. Если сплит
  положил «заметки куратора» сверху, ветку пересобирают (`git reset --mixed origin/main`, один
  общий коммит по `skills` и `CHANGELOG.md`, снова `--split-head`) и пушат `--force-with-lease`:
  ветка ещё не смержена, переписывать её безопасно.
- **Разложение проверяют по файлам, а не по факту успеха.** `git show --stat` на каждый коммит
  должен дать тот же набор путей, что печатал `attribution.py` до публикации; расхождение значит,
  что файл попал в чужую группу — обычно потому, что его правили после снятой атрибуции.

## Рычаги, когда шум мешает

| Рычаг | Что делает | Цена |
|---|---|---|
| `hermes config set agent.auxiliary.background_review.enabled false` | выключает фоновую ревизию (по умолчанию включена) | теряется источник уроков сессии |
| `hermes curator pin <скилл>` / `unpin` | исключает скилл из авто-переходов и из LLM-прохода куратора, правки содержимого не трогает | не заменяет публикацию: пины лежат в локальном `skills/.usage.json`; неуправляемому скиллу не нужен и вреден — втягивает его в список кандидатов |
| `hermes curator lock <скилл>` / `unlock` | контент-замок: `skill_manage`, `write_file`, `patch`, `terminal` отказывают, чтение и авто-загрузка работают | блокирует и свои правки — нужен цикл unlock → правка → lock, годится на окно публикации |
| `hermes config set skills.write_approval true` | правки скиллов не ложатся, а ждут подтверждения | гейт по подсистеме, а не по файлу: подтверждать придётся всё |
| `hermes curator pause` / `resume` | пауза недельного прохода | к правкам сессии не относится — их не останавливает |

## Защита скиллов от архивации: отсутствие маркера, а не пин

Категорий и масок «не трогать» у куратора нет. Всё, что он вообще рассматривает, приходит из одной
функции — `tools/skill_usage.py::curated_report()`, а она собирает agent-created скиллы **плюс
запиненные**. Отсюда главное: скилл без маркера `created_by: agent` и без пина в список не входит
вовсе, поэтому сроки `stale_after_days` (14) и `archive_after_days` (30), `hermes curator prune`
и LLM-консолидация к нему не применяются — не «пропускают его», а не видят. Именно так живут все
скиллы, приехавшие из репозитория: копирование маркер не создаёт.

Исключения внутри самого свипа (`agent/curator.py::apply_automatic_transitions`) — три: флаг
`pinned`, скиллы, на которые ссылается cron-задача, и `locked`. Первые два касаются только тех, кто
в `curated_report()` уже попал.

- `hermes curator pin <имя>` — рычаг для **управляемого** скилла (его завела фоновая ревизия или он
  передан `adopt`). Пин исключает его из авто-переходов, `prune` и LLM-прохода; правки содержимого
  остаются разрешены. Фоновую ревизию сессии пин **не** останавливает: её промпт прямо разрешает
  улучшать «hand-written, installed, bundled, and pinned» скиллы, исключение — только `locked`.
  Ответ «pinned '<имя>' (recorded; this skill is unmanaged — auto-transitions never consider it)» —
  это предупреждение по существу: пин записан, но защищать было нечего.
- **Неуправляемый скилл пинить не надо.** Побочный эффект пинования в том, что скилл появляется в
  отчёте `curator status` и попадает в список кандидатов LLM-прохода, где защита держится на
  инструкции модели «pinned=yes — не трогать». Без пина его там нет вовсе. Отсюда правило профиля:
  не пинить, а не адоптировать.
- `hermes curator lock <имя>` — контент-замок: агент не может править скилл вообще
  (`skill_manage`, `write_file`, `patch`, `terminal` отказывают), куратор его тоже не архивирует.
  Для живых рабочих скиллов не годится — годится на окно публикации.
- `skills/.usage.json` локальный (в репозиторий не попадает), поэтому пины и замки у каждого
  профиля свои; скилл, приехавший из репозитория, в них не нуждается вовсе.

Проверка «скилл не состарится» — свип с датой в будущем и подменённым отчётом, так что трогаются
только проверяемые записи. Для неуправляемого скилла она избыточна (его в списке нет вовсе), для
управляемого показывает, держит ли пин:

```bash
cd <каталог установки Hermes>   # там, где лежат agent/ и tools/
python3 - <<'PY'
from datetime import UTC, datetime, timedelta
from tools import skill_usage as su
from agent import curator
names = ["<скилл>", "<скилл>"]
data = su.load_usage()
rows = [{**su._report_row(n, data.get(n, {}), _persisted=True, provenance=su.provenance(n))} for n in names]
su.curated_report = lambda: rows
print(curator.apply_automatic_transitions(now=datetime.now(UTC) + timedelta(days=400)))
PY
```

`checked: N, archived: 0, marked_stale: 0` — пины держат. Любое ненулевое значение значит, что
запись `pinned` не та (`skill_view` и `curator status` этого не показывают: они смотрят текущее
состояние, а не будущий срок). Живой `hermes curator run` для такой проверки не нужен и опасен —
он пройдёт по всем управляемым скиллам.

## Что защищает от чего

| Угроза | Кто исполняет | Что защищает |
|---|---|---|
| Состаривание и архив по неактивности (`stale_after_days` 14 / `archive_after_days` 30) | `apply_automatic_transitions` | отсутствие маркера `created_by: agent` — в `curated_report()` скилл не входит вовсе; для управляемого — `pinned` |
| Массовый архив по простою | `hermes curator prune` — тот же `curated_report()` | то же |
| Слияние в умбреллу | LLM-проход куратора, кандидаты из `curated_report()` | то же |
| Переписывание содержимого | фоновая ревизия сессии | только `lock`; пин и отсутствие маркера не защищают |
| Физическое удаление | только `hermes curator purge` | автоматически не наступает: «explicit only — never automatic», по умолчанию выключен (`curator.archive_ttl_days` = 0), требует подтверждения, перед удалением пишет блобы и запись `purge` в журнал; скилл из репозитория возвращается `sync.sh`, из `.archive/` — `hermes curator restore` |

Практический вывод для авторских скиллов профиля: скилл, созданный по явному запросу и
опубликованный, защищён от архивации **по умолчанию** — копирование из репозитория не создаёт
маркер, и куратор его не видит. Пинать его не нужно (пин только втягивает скилл в список
кандидатов), адоптировать нельзя. Единственный класс, которому пин нужен, — скиллы, которые завела
фоновая ревизия: они управляемые, стареют по общим срокам и обратно в неуправляемые не переводятся.
Признак «лежит в репозитории» — косвенный: механизм его не читает, он работает лишь потому, что
копирование не ставит маркер.

## Почему пин не кладут в репозиторий (и почему он там не нужен)

Вопрос «положим пины в репозиторий, чтобы знание было общим?» упирается в механику ядра, а не
в политику профиля:

- `tools/skill_usage.py` каталога установки Hermes хранит состояние по **имени** скилла в
  `skills/.usage.json`; в шапке модуля прямо сказано, что телеметрия и пины не пишутся во
  фронтматтер. Авто-переходы и LLM-проход читают только эту запись.
- Список «неприкосновенных встроенных» скиллов (`is_protected_builtin`) захардкожен в ядре;
  ключа конфигурации вида `curator.protected_skills` нет.
- `curated_report()` = agent-created скиллы **плюс** запиненные. Отсюда две несвязанные защиты:
  скилл без маркера `created_by: agent` авто-переходы не видят вовсе — его не состарят и не
  заархивируют по `archive_after_days`; но фоновая ревизия правит его текст как обычный (её
  промпт не различает запиненные и незапиненные скиллы, исключение — только `locked`), хотя
  консолидировать и архивировать не имеет права. Состав смотреть
  `hermes curator list-unmanaged`.
- `created_by: agent` ставится ровно в двух местах ядра: `record_created(...,
  agent_created=is_background_review())` при создании скилла фоновая ревизия и `hermes curator
  adopt`. Передний `skill_manage(create)` пишет `created_by: learn`, установка из хаба —
  `installed`, копирование из репозитория не создаёт маркер вовсе. Обратной команды нет: `unadopt`
  в CLI отсутствует, управляемость снимается только удалением записи вручную.
- `hermes curator adopt --all-unmanaged` (и подсказка в конце вывода `list-unmanaged`) переводит
  все скиллы профиля в управляемые одной командой — после этого единственная защита `pinned`, а
  `curator status` показывает такие скиллы как обычные. Публикация этого не отменяет:
  `sync.sh` кладёт только каталоги скиллов и `.usage.json` не трогает, поэтому у автора скилл,
  созданный ревизией, остаётся управляемым и после публикации, а у коллег та же публикация
  приезжает неуправляемой.
- `lock` живёт в том же `.usage.json`, то есть тоже локален.

Следствие: сам `.usage.json` в публикацию не годится (личная телеметрия плюс замки), а «общий
список пинов» — это отдельный файл в репозитории **и** шаг, который его применяет; у
`hermes profile update` такого шага нет, так что у коллеги список остаётся не применённым до
ручного `hermes curator pin`. Профилю это не нужно: защита держится отсутствием маркера, а не
списком. Нужен один запрет — не запускать `adopt` — и он живёт в `SOUL.md`, потому что исполняет
его агент сессии, а не Hermes, и пережить правку скиллов правилу помогает только identity-слот.

## Гонка за один файл

Ревизия читает ту же сессию, поэтому целится в те же файлы. Признаки, что она переписала текст
после тебя: в файле две редакции одного правила, появилась склеенная строка или лишние пробелы в
слове, `before[].sha256` последней записи не совпадает с хешем, который ты запомнил.

Порядок: перечитать файл → перенести свой фрагмент в новую редакцию через `patch` по уникальному
тексту (не по номеру строки) → проверить, что обе редакции не остались рядом → только потом
публиковать. Правка «по позиции» после чужой перезаписи попадает в другое место и уносит с собой
соседний абзац.

## Ревизия переписала файл после публикации

Обратный случай: правку уже смержили, а ревизия в профиле переписала тот же файл независимо — иногда
целую функцию своей реализацией. Гейт на следующем `sync.sh` видит `≠`, хотя в `main` решение той
же задачи уже есть, и первый порыв — опубликовать всё заново вторым PR.

Порядок:

1. `diff -ru` профиль ↔ `main` по скиллу и разложить остаток на три класса: альтернативная
   реализация уже исправленного, переформулировки уже опубликованного, номер версии скилла.
2. Оставить в силе ту реализацию, которая в `main` и прогнана на копиях; из чужой редакции
   перенести только то, чего в `main` нет: новые факты, строки таблиц, предупреждения о граблях.
   Две реализации одной функции в репозитории — не «обе пригодятся», а расхождение при первой же
   правке, поэтому вторую не публикуют.
3. В теле PR перечислить, что **не** перенесено и почему (дубль уже описанного, альтернативная
   реализация) — иначе ревьюер ищет в диффе знакомый текст и не находит его.
4. Убедиться, что ревизия не дописала ещё: `ts` последней записи журнала по скиллу должен быть
   старше начала публикации. Тогда в профиле остались только непринятые куски.
5. Синхронизация — `sync.sh --force` после `publish_check.py --save` и подтверждения из шага 1;
   бэкап `.backup/pre-update-*` сохраняет и непринятую редакцию.
