# Публикация дистрибутива в GitHub

Глубина к разделу «Публикация дистрибутива в GitHub» в SKILL.md: чем доказывать право писать,
какие права нужны PAT, как включить защиту ветки и как доказать, что всё действительно работает.

## PAT или SSH-ключ

| | fine-grained PAT | SSH-ключ |
|---|---|---|
| Что лежит на машине | строка в файле окружения (600) | приватный ключ в `~/.ssh` |
| Область поражения при утечке | один репозиторий | весь аккаунт (если ключ без пассфразы) |
| Срок | истекает (≤ 90 дней) | бессрочно |
| Авто-создание PR | да | нет: GitHub не создаёт PR по ключу |
| Когда выбирать | агент публикует сам, нужен узкий доступ | ручная работа человека, ключ с пассфразой + ssh-agent |

Ключ без пассфразы нужен, чтобы агент пушил без участия человека, — и он даёт доступ ко всему
аккаунту. Для агентской публикации поэтому предпочтителен PAT с доступом к одному репозиторию.

## Права fine-grained PAT

- Contents: Read and write — коммиты и ветки.
- Pull requests: Read and write — создание PR.
- Workflows: Read and write — **обязательно**, если в коммите есть `.github/workflows/`.
- Administration: Read and write — только владельцу, для защиты ветки и режима мержа.
- Metadata: Read — ставится автоматически.

## Первый push и защита ветки

```bash
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
git push origin --tags
```

Защита ветки и режим мержа (владелец, PAT с Administration):

```http
PATCH /repos/<owner>/<repo>
{"allow_squash_merge": true, "allow_merge_commit": false, "allow_rebase_merge": false,
 "delete_branch_on_merge": true}

PUT /repos/<owner>/<repo>/branches/main/protection
{"required_status_checks": null, "enforce_admins": false,
 "required_pull_request_reviews": {"dismiss_stale_reviews": true,
   "require_code_owner_reviews": true, "required_approving_review_count": 1},
 "restrictions": null, "allow_force_pushes": false, "allow_deletions": false,
 "required_conversation_resolution": true}
```

`enforce_admins: false` оставляет владельцу обход защиты — иначе его собственные PR некому
одобрять. Если обход не нужен, включайте `true` и держите второго ревьюера.

Проверка после PUT — повторный GET `/branches/main/protection`: в ответе должны быть
`require_code_owner_reviews: true` и `required_approving_review_count: 1`.

## Push по HTTPS без токена в `.git/config`

Готовый вариант — `scripts/push_and_wait_ci.py <каталог> <owner/repo> [ветка]`: берёт токен из
окружения или `.env`, подставляет его в URL push, маскирует в выводе и поллит CI по SHA головы.
Ручной эквивалент ниже — когда нужен нестандартный шаг.

Токен подставляется через `GIT_ASKPASS`, поэтому не попадает ни в argv, ни в конфиг:

```bash
ASK="$(mktemp)"
cat > "$ASK" <<'EOF'
#!/bin/sh
case "$1" in
  *[Uu]sername*) printf '%s\n' "${GITHUB_USER}" ;;
  *)             printf '%s\n' "${GITHUB_TOKEN}" ;;
esac
EOF
chmod 700 "$ASK"
GIT_ASKPASS="$ASK" GIT_TERMINAL_PROMPT=0 git push -u origin <ветка>
rm -f "$ASK"
```

Логин для username берётся из `GET /user`. Порядок поиска токена: файл окружения `$HOME/.hermes`,
затем `$HERMES_HOME/.env`, затем `.env` профиля — у коллег токен часто лежит именно в профильном
файле.

`GIT_TERMINAL_PROMPT=0` обязателен: без него push в неинтерактивной сессии висит на приглашении
пароля вместо понятной ошибки.

## Проверка на живом PR

1. Опубликовать ветку и убедиться, что PR действительно создан:
   `GET /repos/<owner>/<repo>/pulls?state=open`.
2. Дождаться CI по SHA головы PR: `GET /repos/<owner>/<repo>/commits/<sha>/check-runs`,
   поллить до `status == completed`; успех — `conclusion == success` у нужного job. Имя job
   читается из ответа, а не берётся из памяти: в этой сборке он называется `skills`, и «ждём
   `validate`» превращается в ожидание job, которого нет.
3. Убрать за собой: `PATCH .../pulls/<n> {"state": "closed"}` и
   `DELETE .../git/refs/heads/<ветка>`, затем сверить, что в репозитории остался только `main`.
   При `delete_branch_on_merge: true` ветка исчезает сама при мерже, и тот же `DELETE` отвечает
   `422 Reference does not exist` — это признак, что убирать уже нечего. `git push origin --delete`
   в клоне, где remote без токена, падает на приглашении логина, поэтому уборка — только через API.

Опрос CI держите короткими отдельными вызовами (`GET /commits/<sha>/check-runs` в цикле по 15–20 с):
одно долгое ожидание внутри запускавшего push вызова упирается в таймаут инструмента, и дальше
непонятно, упал push или ждал CI. Таймаут после push — не отказ: `git ls-remote --heads origin <ветка>`
показывает, что ветка на месте, и ожидание продолжается опросом.

Тестовый PR закрывается, а не мержится: `main` не должен содержать проверочных коммитов.

## Отладка детектора секретов

- Вывод инструментов редактирует секретоподобные строки, поэтому напечатанная строка может не
  совпадать с содержимым файла. Сравнивайте длину совпадения, набор символов и позицию
  (`len`, `set(token)`, `span`), а не сам токен.
- Плейсхолдеры документации (`ghp_` + `xxxx…`, `AKIA…EXAMPLE`, `sk-...`) секретом не являются:
  отбрасывайте совпадения с повторяющимся символом или словом `example`, иначе CI краснеет на
  reference-файлах штатных скиллов.
- Требуйте реалистичную длину (classic PAT — 36 символов после префикса, fine-grained — десятки),
  иначе короткие заглушки дают ложные срабатывания.
- Проверяйте детектор на синтетических токенах, сгенерированных в скрипте: положительные и
  отрицательные случаи в одном прогоне дешевле разбора ложного срабатывания в CI.

## Предполётная проверка публикации

Три проверки до `contribute.sh`; каждая дешевле, чем разбор после уехавшей ветки.

- **Личность в клоне** — `git -C <клон> config user.name`. Из него берётся слаг ветки
  (`contrib/<автор>/…`) и автор коммита: чужое имя в local-конфиге даёт ветку-однофамильца и
  коммит от не того человека. Оно должно совпадать с аккаунтом, под которым идёт push.
- **Токен** — строка `GITHUB_TOKEN=` в `~/.hermes/.env`, `$HERMES_HOME/.env` или `.env` профиля.
  Проверять наличием и длиной значения, значение не печатать.
- **Клон синхронен** — `git status -sb` чист, `rev-list --left-right --count main...origin/main`
  даёт `0 0`. Иначе ветка ляжет поверх чужого `main` и PR покажет лишние файлы.

## Push упал после коммита

`contribute.sh` коммитит ветку до push, поэтому падение push (нет токена, нет сети, отказ прав)
оставляет готовый коммит — `git log --oneline -2` и `git status -sb` покажут ветку. Повторять
скрипт не нужно: он создаст вторую ветку с новым штампом времени и вторую строку в `CHANGELOG.md`.
Дальше — добавить токен, `git push -u origin <ветка>` тем же `GIT_ASKPASS`-способом и продолжить
с PR и CI.

## Мерж владельцем, тег и асинхронные правки профиля

Второй ревьюер для мержа владельцу не нужен: при `enforce_admins: false` достаточно
`PUT /repos/<owner>/<repo>/pulls/<n>/merge` с `{"merge_method": "squash"}`. Признак успеха —
`merged: true` и `merge_commit_sha` в ответе; затем `state: closed, merged: true`, а
`mergeable_state` переходит в `unknown` — это нормальное состояние смерженного PR, не ошибка.
Проверять ветку защиты (`GET /branches/main/protection`) не обязательно и часто нельзя: без
права Administration эндпоинт отвечает `403 Resource not accessible by personal access token`,
а мерж при этом работает. Судить по результату операции, а не по доступности проверки.

Перепроверка релиза после `release.py`: `git ls-remote --tags origin` и `GET /releases/latest`
(`draft: false`). Push тега под ruleset печатает
`Bypassed rule violations for refs/tags/v<версия>: - Cannot create ref due to creations being restricted`
— это сообщение об обходе админом, а не отказ; код возврата при этом нулевой.

**Куратор скиллов пишет в профиль асинхронно.** `contribute.sh` копирует каталог скилла в клон
в один момент, куратор Hermes может дописать профиль позже — в том числе в паузе между
копированием и мержем. Тогда PR увозит устаревшую версию: публикация «прошла», а
`diff -rq` профиль ↔ `origin/main` снова не пуст. Следы: `.curator_ledger.jsonl` со свежими
записями `"action": "patch"`, бэкапы в `.curator_backups/blobs/`, mtime файлов скилла позже
времени коммита в ветке. Лечение — не amend и не перетегирование: дельта идёт вторым PR, версия
выпускается следующей (та же или меньшая не пройдёт — `release.py` откажется, а теги
неизменяемы). Чтобы не плодить релизы, сверяйте `diff` профиль ↔ ветка PR **перед** мержем,
а не после.

## Правка только вне `skills/`

README, `tools/`, `publish.list`, `.github/` не входят в то, что публикует `contribute.sh`, а у
правки без единого изменённого скилла он вообще не создаст ветку («нечего публиковать»). Такой PR
собирается руками, но по тем же правилам: ветка `contrib/<автор>/<штамп>-<слаг>`, один смысловой
коммит, строка в `CHANGELOG.md` сразу после `## Unreleased` в формате
`- <ГГГГ-ММ-ДД> — <суть> (<git user.name>)` — тот же формат, что вставляет `contribute.sh`.

Порядок: `git switch main && git pull --ff-only` → ветка → правка → коммит (`README.md` и
`CHANGELOG.md` в одном коммите) → push через `scripts/push_and_wait_ci.py` или `GIT_ASKPASS` → PR
через API → squash-мерж → удалить ветку через API → `git switch main && git pull --ff-only`, чтобы
клон остался чистым на `main`.

Проверки перед PR (README — тоже код, ошибки в нём видны только на GitHub):

- `tools/skill_lint.py` — скиллы не тронуты, значит 0 ошибок; не 0 — в ветку попал лишний файл;
- относительные ссылки таблицы резолвятся в существующие файлы (`pathlib.Path(link).exists()`);
- во всех строках markdown-таблицы одинаковое число колонок после `split('|')`;
- раздел не дублирует существующий: при добавлении обзора старую таблицу с теми же данными
  заменяют ссылкой на новый раздел, а не оставляют рядом.

После мержа содержимое читается с `raw.githubusercontent.com/<owner>/<repo>/main/<файл>`: локальный
файл доказывает только, что правка была сделана.

## Правки самих скиллов дистрибутива

Правится клон репозитория, а не живой профиль: `sync.sh` перезаписывает скиллы дистрибутива и
молча снимет правку, сделанную только в профиле. Правка в профиле допустима лишь как исходник
для `contribute.sh` в том же сеансе.

Порядок шагов внутри `contribute.sh` важен, иначе скрипт врёт о своём результате:

- проверка «есть ли изменения» (`git add -A skills` + `git diff --cached --quiet`) идёт **до**
  присвоения имени ветке и до вставки строки в `CHANGELOG.md`: иначе пустой запуск всегда
  создаёт коммит из одной строки журнала и выглядит как успешная публикация;
- вставку в журнал якорить на строку, равную `## Unreleased`, а не на подстроку: упоминание
  `## Unreleased` в тексте шапки файла ловит первый же `partition`;
- при провале линта откатывать рабочее дерево клона (`git reset` + `git checkout -- skills
  CHANGELOG.md`): иначе клон остаётся с незакоммиченным секретом, который потом легко утащить
  в следующий коммит;
- ветку создавать после проверки изменений, иначе после отказа в удалённом репозитории остаётся
  пустая ветка;
- коммитятся только пути `skills` и `CHANGELOG.md`: изменения в `tools/`, `README.md`,
  `.github/`, `publish.list` остаются в рабочем дереве клона и в PR не уезжают, хотя скрипт
  отчитается об успехе. Их добавляют в ту же ветку вторым коммитом — squash-мерж свернёт историю
  в один коммит. Правку `.github/workflows/*` GitHub отклонит, если у PAT нет права Workflows
  (`refusing to allow a Personal Access Token to create or update workflow … without 'workflow'
  scope`): такой файл либо пушат после выдачи права, либо выносят в отдельный PR, чтобы не
  держать готовую публикацию из-за одной проверки CI;
- интерактивные вопросы внутри цикла по списку (`while read -r x; do … done <<< "$LIST"`) читают
  ответ из `/dev/tty`, а не из stdin: stdin уже занят herestring-ом, и `read` молча съест
  следующую строку списка вместо ответа. Без терминала (`[ -t 0 ]`) — печатать подсказку,
  а не висеть на вводе.

Проверка после push владельцем в защищённый `main`: GitHub печатает
`Changes must be made through a pull request`, но при `enforce_admins: false` коммит принимается.
Судить по `git ls-remote origin main`, а не по тексту предупреждения; код возврата в конвейере
(`git push | tail`) к тому же относится к `tail`, а не к push.

## Обновление профиля при неопубликованных правках

Два пути обновления по-разному относятся к локальным правкам:

| Обновление | Что делает со скиллами дистрибутива | Бэкап профиля |
|---|---|---|
| `hermes profile update <имя>` | каталог скилла заменяется целиком: новая копия собирается рядом в `.dist_swap`, старая версия каталога удаляется (`_replace_entry` в `hermes_cli/profile_distribution.py`) | нет |
| `tools/sync.sh` | `rsync -a` копирует скиллы репозитория поверх профиля, лишние файлы не удаляются | `.backup/pre-sync-<дата>/` |

Отсюда поведение по умолчанию:

- правка, сделанная только в профиле, после любого из двух путей исчезнет, если её не
  опубликовали — содержимое каталога просто замещается версией из репозитория;
- `sync.sh` управляет этим сам: вызывает `publish_check.py` до копирования и при состояниях
  `≠` (расходится) или `+` (не опубликован) останавливается с кодом 3; `--check` — только отчёт,
  `--force` — перезаписать с бэкапом;
- у `hermes profile update` гейта нет — это штатная команда Hermes, и знать про локальные правки
  она не может. Preflight делает агент: `publish_check.py --save .backup/pre-update-<дата>`
  перед вызовом, затем публикация или явное решение перезаписать;
- авторский скилл, которого нет в дистрибутиве, обновление не трогает: и нативный апдейт
  («skills you added yourself stay in place»), и `sync.sh` без `--prune` его не удаляют.

Порядок, который даёт «синхронное» состояние без потерь: `publish_check.py` → при расхождениях
опубликовать (`contribute.sh`) или сохранить копию (`--save`) → обновить профиль → повторить
`publish_check.py`: код 0 означает, что профиль и `main` совпадают, и ничего не потеряно.

## Инструмент сверки: `tools/publish_check.py`

Один прогон отвечает на вопрос «что ещё не опубликовано и что разошлось», не публикуя ничего:

```bash
python3 tools/publish_check.py                     # активный профиль
python3 tools/publish_check.py --profile <каталог>  # профиль коллеги или установленный из дистрибутива
python3 tools/publish_check.py --json              # машинный вывод: diverged, missing_in_profile, unclassified
```

Что попадает в вывод: состояние клона (ветка, чистота, `↑/↓` к `origin/main`), по каждому
публикуемому скиллу — совпадает ли профиль с деревом клона и какие файлы отличаются, скиллы
репозитория, которых нет в профиле (профиль отстал, нужен `sync.sh`), авторские скиллы вне
политики публикации, версия `distribution.yaml` с двух сторон.

Коды возврата: `0` — синхронно; `1` — есть расхождения; `2` — нет профиля или клон не
git-репозиторий. Поэтому проверка годится как гейт в конвейере (`publish_check.py && merge`)
и как источник фактов для ответа в чат вместо ручного `diff -rq` по каждому скиллу.

Когда запускать:

- **перед `contribute.sh`** — чтобы в PR не поехало лишнее и чтобы отставание профиля от
  репозитория не выглядело как «правка»;
- **перед мержем PR** — на ветке PR (`git -C <клон> switch <ветка>`), код 0 означает, что
  профиль не ушёл вперёд ветки; собирать `diff -rq` по шести скиллам вручную уже не нужно;
- **после мержа** — если код 1 и расхождения ровно в тех файлах, которые PR только что менял,
  значит профиль дописали между копированием и мержем: это не ошибка публикации, а следующая
  порция, её публикует второй PR и следующая версия.

Инструмент обходит `skills/` через `rglob("SKILL.md")` (как `publish_policy.py`), поэтому
вложенные категории `certification/tools/` он видит; мусор вроде `__pycache__` и `.DS_Store`
в сравнение не попадает, иначе код возврата скакал бы от запуска к запуску.
