# Публикация дистрибутива в GitHub

Глубина к разделу «Публикация дистрибутива в GitHub» в SKILL.md: чем доказывать право писать,
какие права нужны PAT, как включить защиту ветки и как доказать, что всё действительно работает.

## PAT или SSH-ключ

| | fine-grained PAT | SSH-ключ |
|---|---|---|
| Что лежит на машине | строка в файле окружения (600) | приватный ключ в `~/.ssh` |
| Область поражения при утечке | один репозиторий | весь аккаунт (если ключ без пассфразы) |
| Срок | истекает (≤ 90 дней) | бессрочно |
| Авто-создание PR | да | нет: GitHub не создаёт PR по ключу |
| Когда выбирать | агент публикует сам, нужен узкий доступ | ручная работа человека, ключ с пассфразой + ssh-agent |

Ключ без пассфразы нужен, чтобы агент пушил без участия человека, — и он даёт доступ ко всему
аккаунту. Для агентской публикации поэтому предпочтителен PAT с доступом к одному репозиторию.

## Права fine-grained PAT

- Contents: Read and write — коммиты и ветки.
- Pull requests: Read and write — создание PR.
- Workflows: Read and write — **обязательно**, если в коммите есть `.github/workflows/`.
- Administration: Read and write — только владельцу, для защиты ветки и режима мержа.
- Metadata: Read — ставится автоматически.

## Первый push и защита ветки

```bash
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
git push origin --tags
```

Защита ветки и режим мержа (владелец, PAT с Administration):

```http
PATCH /repos/<owner>/<repo>
{"allow_squash_merge": true, "allow_merge_commit": false, "allow_rebase_merge": false,
 "delete_branch_on_merge": true}

PUT /repos/<owner>/<repo>/branches/main/protection
{"required_status_checks": null, "enforce_admins": false,
 "required_pull_request_reviews": {"dismiss_stale_reviews": true,
   "require_code_owner_reviews": true, "required_approving_review_count": 1},
 "restrictions": null, "allow_force_pushes": false, "allow_deletions": false,
 "required_conversation_resolution": true}
```

`enforce_admins: false` оставляет владельцу обход защиты — иначе его собственные PR некому
одобрять. Если обход не нужен, включайте `true` и держите второго ревьюера.

Проверка после PUT — повторный GET `/branches/main/protection`: в ответе должны быть
`require_code_owner_reviews: true` и `required_approving_review_count: 1`.

## Push по HTTPS без токена в `.git/config`

Готовый вариант — `scripts/push_and_wait_ci.py <каталог> <owner/repo> [ветка]`: берёт токен из
окружения или `.env`, подставляет его в URL push, маскирует в выводе и поллит CI по SHA головы.
Ручной эквивалент ниже — когда нужен нестандартный шаг.

Токен подставляется через `GIT_ASKPASS`, поэтому не попадает ни в argv, ни в конфиг:

```bash
ASK="$(mktemp)"
cat > "$ASK" <<'EOF'
#!/bin/sh
case "$1" in
  *[Uu]sername*) printf '%s\n' "${GITHUB_USER}" ;;
  *)             printf '%s\n' "${GITHUB_TOKEN}" ;;
esac
EOF
chmod 700 "$ASK"
GIT_ASKPASS="$ASK" GIT_TERMINAL_PROMPT=0 git push -u origin <ветка>
rm -f "$ASK"
```

Логин для username берётся из `GET /user`. Порядок поиска токена: файл окружения `$HOME/.hermes`,
затем `$HERMES_HOME/.env`, затем `.env` профиля — у коллег токен часто лежит именно в профильном
файле.

`GIT_TERMINAL_PROMPT=0` обязателен: без него push в неинтерактивной сессии висит на приглашении
пароля вместо понятной ошибки.

## Проверка на живом PR

1. Опубликовать ветку и убедиться, что PR действительно создан:
   `GET /repos/<owner>/<repo>/pulls?state=open`.
2. Дождаться CI по SHA головы PR: `GET /repos/<owner>/<repo>/commits/<sha>/check-runs`,
   поллить до `status == completed`; успех — `conclusion == success` у job `validate`.
3. Убрать за собой: `PATCH .../pulls/<n> {"state": "closed"}` и
   `DELETE .../git/refs/heads/<ветка>`, затем сверить, что в репозитории остался только `main`.

Тестовый PR закрывается, а не мержится: `main` не должен содержать проверочных коммитов.

## Отладка детектора секретов

- Вывод инструментов редактирует секретоподобные строки, поэтому напечатанная строка может не
  совпадать с содержимым файла. Сравнивайте длину совпадения, набор символов и позицию
  (`len`, `set(token)`, `span`), а не сам токен.
- Плейсхолдеры документации (`ghp_` + `xxxx…`, `AKIA…EXAMPLE`, `sk-...`) секретом не являются:
  отбрасывайте совпадения с повторяющимся символом или словом `example`, иначе CI краснеет на
  reference-файлах штатных скиллов.
- Требуйте реалистичную длину (classic PAT — 36 символов после префикса, fine-grained — десятки),
  иначе короткие заглушки дают ложные срабатывания.
- Проверяйте детектор на синтетических токенах, сгенерированных в скрипте: положительные и
  отрицательные случаи в одном прогоне дешевле разбора ложного срабатывания в CI.

## Правки самих скиллов дистрибутива

Правится клон репозитория, а не живой профиль: `sync.sh` перезаписывает скиллы дистрибутива и
молча снимет правку, сделанную только в профиле. Правка в профиле допустима лишь как исходник
для `contribute.sh` в том же сеансе.

Порядок шагов внутри `contribute.sh` важен, иначе скрипт врёт о своём результате:

- проверка «есть ли изменения» (`git add -A skills` + `git diff --cached --quiet`) идёт **до**
  присвоения имени ветке и до вставки строки в `CHANGELOG.md`: иначе пустой запуск всегда
  создаёт коммит из одной строки журнала и выглядит как успешная публикация;
- вставку в журнал якорить на строку, равную `## Unreleased`, а не на подстроку: упоминание
  `## Unreleased` в тексте шапки файла ловит первый же `partition`;
- при провале линта откатывать рабочее дерево клона (`git reset` + `git checkout -- skills
  CHANGELOG.md`): иначе клон остаётся с незакоммиченным секретом, который потом легко утащить
  в следующий коммит;
- ветку создавать после проверки изменений, иначе после отказа в удалённом репозитории остаётся
  пустая ветка;
- интерактивные вопросы внутри цикла по списку (`while read -r x; do … done <<< "$LIST"`) читают
  ответ из `/dev/tty`, а не из stdin: stdin уже занят herestring-ом, и `read` молча съест
  следующую строку списка вместо ответа. Без терминала (`[ -t 0 ]`) — печатать подсказку,
  а не висеть на вводе.

Проверка после push владельцем в защищённый `main`: GitHub печатает
`Changes must be made through a pull request`, но при `enforce_admins: false` коммит принимается.
Судить по `git ls-remote origin main`, а не по тексту предупреждения; код возврата в конвейере
(`git push | tail`) к тому же относится к `tail`, а не к push.
