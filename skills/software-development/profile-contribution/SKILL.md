# Совместная модернизация профиля

Профиль `hermes-certification-assistant` живёт в двух местах: **репозиторий — источник
истины**, **каталог профиля — рабочая копия**, в которой агент правит скиллы во время
работы. Этот скилл описывает, как изменения попадают из рабочей копии в репозиторий,
не ломая работу остальных девяти человек.

## Когда применять

- Нужно опубликовать правку скилла, которую агент сделал в профиле.
- Нужно принять чужие изменения из репозитория.
- Владелец репозитория ревьюит и мержит PR.
- Возникла ошибка публикации/синхронизации («линт не прошёл», «нечего публиковать»).

## Работа только через чат

**Пользователь не запускает скриптов.** Он говорит намерение — агент выполняет шаги и
возвращает результат. Что именно делает агент:

| Пользователь говорит | Агент делает | Что возвращает в чат |
|---|---|---|
| «опубликуй правки», «отправь изменения», «сделай PR» | проверяет клон и токен; при отсутствии клона клонирует репозиторий в `~/work/hermes-certification-assistant`; запускает `contribute.sh -m "<сводка>"` | ссылку на PR, список изменённых скиллов, строку, добавленную в CHANGELOG |
| «что нового», «получи обновления», «обнови профиль» | `hermes profile update <имя>` (профиль установлен дистрибутивом) либо `sync.sh` в клоне; при переносах путей — с `--prune` | версию дистрибутива и список обновлённых скиллов |
| «проверь мой PR», «он прошёл?» | статус PR и CI через API | зелёный/красный CI, нужен ли review, ссылку |
| «выпусти версию 1.8.0» (только владелец) | `release.py <версия>` | версию, тег, ссылку на релиз |
| «почему скилл не уехал?» | `publish_policy.py --status --profile <профиль>` | категорию скилла, публикуется ли он, что мешает |

Роль меняет не способ общения, а набор прав:

| | Владелец | Коллега |
|---|---|---|
| Публикация правок | да | да (ветка + PR) |
| Мерж в `main` | да | нет — просит владельца |
| Релиз и теги | да | нет |
| Получение обновлений | да | да |

Одно разовое условие: для автоматического PR нужен `GITHUB_TOKEN` в `~/.hermes/.env`
(fine-grained, только этот репозиторий, файл `600`). Без него публикация тоже работает, но
агент вернёт ссылку `compare`, и один клик в браузере останется за человеком — это
единственный ручной шаг, и убрать его лучше сразу. Поэтому первое действие агента по просьбе
«опубликуй»: проверить клон и токен, сказать, чего не хватает, и попросить только недостающее.

У коллеги, установившего профиль дистрибутивом, клона нет — это нормально: агент делает его
сам и дальше работает с `REPO_DIR`, не трогая остальной профиль.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Владелец | один человек (`@mArTi3-github`) | ревью, мерж в `main`, версия в `distribution.yaml`, теги |
| Контрибьютор | остальные | правит скиллы в своём профиле, публикует ветку + PR |

`main` защищён: прямой push запрещён, нужно ревью владельца. Мержит только владелец.

## Железные правила

1. **Никогда не пушить в `main`.** Ветка + PR. Исключений нет, даже для опечатки.
2. **Один PR — одно смысловое изменение.** «Поправил проверку блокировок» и «переписал
   структуру отчёта» — два PR, а не один.
3. **Секреты не попадают в репозиторий никогда:** `.env`, `auth.json`, пароли, токены,
   ключи, результаты прогонов с учётными данными. Проверяется линтом и CI.
4. **Адреса стендов не фиксируются.** IP и имена узлов меняются от прогона к прогону: в
   скиллах и шаблонах только плейсхолдеры (`<узел>`, `<стенд>`). Реальные адреса — в
   свидетельствах, не в тексте скилла.
5. **Правки не «на живую навсегда».** Незакоммиченная правка исчезнет при следующей
   синхронизации: `sync.sh` перезаписывает скиллы дистрибутива. Правишь — публикуй.
6. **Версию поднимает только владелец**, одной командой `tools/release.py <версия>`:
   она переносит `## Unreleased` в раздел с версией, поднимает `distribution.yaml`, ставит тег
   и создаёт GitHub Release. Вручную версию не править — иначе в истории появляются версии без
   меток. Контрибьютор только добавляет строку в `## Unreleased` (это делает `contribute.sh`).
7. **Bundled-скиллы не вендорятся.** Штатные скиллы Hermes приезжают сами; в репозиторий
   кладём только авторские и осознанно изменённые.
8. **Не редактировать чужие PR-ветки без договорённости.** Замечания — комментарием в PR.
9. **Публикация определяется категорией скилла.** Всё, что лежит в `skills/certification/`,
   публикуется по умолчанию (`[defaults] publish_categories` в `publish.list`); всё остальное
   остаётся локальным и коллегам не уезжает. Общие инструменты, которые команде всё же нужны,
   перечислены явно в `[publish]`; `[private]` перекрывает любую категорию.
10. **Новый скилл создаётся только после выбора категории.** Перед вызовом
   `skill_manage(action='create', ...)` спросите пользователя, что это:
   - сертификационная процедура → `certification/`;
   - служебный инструмент, на который опираются сертификационные скиллы → `certification/tools/`;
   - личный или общий инструмент вне сертификации → любая другая категория.

   Первые две публикуются автоматически, третья остаётся локальной. Категория и есть решение
   о публикации — не угадывайте её молча.
11. **Пользователь не запускает скрипты.** Всё, что описано в этом скилле, выполняет агент:
    клонирует репозиторий, если клона нет, проверяет токен, запускает `contribute.sh`,
    `sync.sh`, `release.py` и возвращает результат — ссылку на PR, версию, список изменений.
    Отвечать «введите такую команду» нельзя, пока пользователь сам об этом не попросил.

## Как предложить изменение (контрибьютор)

```bash
# 1. Агент уже поправил скилл в профиле — проверьте, что правка видна:
python3 ~/work/hermes-certification-assistant/tools/skill_lint.py

# 2. Публикация: копирование профиль → репозиторий, линт, ветка, коммит, push, PR
~/work/hermes-certification-assistant/tools/contribute.sh \
  -m "stand-ftest: уточнил порядок проверки блокировок"

# 3. Если PR не создался автоматически — откройте напечатанную ссылку compare в браузере
```

Если скилл не сертификационный, но команде он всё же нужен, добавьте его в политику явно:

```bash
~/work/hermes-certification-assistant/tools/contribute.sh \
  -i software-development/my-new-skill -m "новый скилл: проверка чего-то"
```

Скиллы вне политики `contribute.sh` показывает отдельно: в терминале он спрашивает по каждому
`[c]` — перенести в `certification/` и опубликовать, `[l]` — оставить локально, `[Enter]` —
пропустить; в неинтерактивном режиме печатает подсказку с командой. Зафиксировать решение
вручную: `tools/publish_policy.py --classify <категория/имя> publish|private`.

Посмотреть, что публикуется, что осталось локальным и что не классифицировано:

```bash
python3 ~/work/hermes-certification-assistant/tools/publish_policy.py --status --profile "$HERMES_HOME"
```

Что делает `contribute.sh`:

- складывает бэкап скиллов профиля в `.backup/<дата>/` (каталог в `.gitignore`);
- копирует в клон все скиллы дистрибутива, которые есть в профиле, плюс новые авторские
  скиллы (штатные скиллы Hermes пропускаются по `.bundled_manifest`);
- прогоняет линт и **останавливается**, если он не прошёл (правки в клоне откатываются,
  исходник остаётся в профиле, бэкап — в `.backup/<дата>/`);
- создаёт ветку `contrib/<автор>/<дата>-<слаг>`, добавляет строку в `CHANGELOG.md`,
  коммитит и пушит;
- открывает PR через API, если в `~/.hermes/.env` есть `GITHUB_TOKEN` (тогда же push идёт
  по HTTPS без ввода пароля), иначе печатает ссылку для открытия PR в браузере.

## Как принять обновления

Способ зависит от того, как профиль установлен, — агент определяет это сам, пользователю
отвечать не нужно:

| Как установлен профиль | Что запускает агент | Вручную нужно? |
|---|---|---|
| дистрибутивом (`hermes profile install`) — обычный случай у коллеги | `hermes profile update <имя>` | нет |
| из клона репозитория (обычно у владельца) | `tools/sync.sh`, при переносах путей — `tools/sync.sh --prune` | нет |

Как отличить: у установленного дистрибутивом профиля есть `distribution.yaml` в каталоге профиля
и нет `.git`. У клона есть `.git` и каталог `tools/`.

```bash
# клон: скиллы и SOUL.md (личные данные не трогаются)
tools/sync.sh

# клон: заодно снять скиллы, которые политика перестала публиковать
tools/sync.sh --prune

# клон: перезаписать config.yaml (локальный конфиг уйдёт в .backup/)
tools/sync.sh --config
```

Новые и изменённые скиллы подхватываются в следующей сессии, перезапускать ничего не нужно.
Перед синхронизацией скрипт делает бэкап в `.backup/pre-sync-<дата>/`.

## Ревью владельцем

```bash
# что пришло и что именно меняется
git -C ~/work/hermes-certification-assistant fetch --all --prune
git -C ~/work/hermes-certification-assistant diff --stat main...origin/<ветка>
git -C ~/work/hermes-certification-assistant diff main...origin/<ветка> -- skills/
```

Чек-лист перед мержем:

- [ ] `validate` в CI зелёный (линт скиллов + скан истории на секреты).
- [ ] В диффе нет `.env`, `auth.json`, паролей, токенов, внутренних IP и имён заказчиков.
- [ ] Правка соответствует методике (приказ № 76), а не личным предпочтениям автора.
- [ ] `name` во фронтматтере совпадает с каталогом, `description` ≤ 60 символов.
- [ ] Строка в `CHANGELOG.md` описывает изменение по существу, а не «правки».
- [ ] Изменение не дублирует существующий скилл (иначе — правка имеющегося).

Мерж — squash, чтобы история `main` оставалась линейной и читаемой.

Релиз после мержа:

```bash
python3 ~/work/hermes-certification-assistant/tools/release.py 1.7.0 --dry-run
python3 ~/work/hermes-certification-assistant/tools/release.py 1.7.0
```

## Креды и секреты

| Что | Где хранится | Кто заводит |
|---|---|---|
| SSH-ключ для push | `~/.ssh/`, публичная часть — в GitHub-профиле коллеги | каждый сам |
| PAT для HTTPS-push и авто-PR (опция) | `~/.hermes/.env` → `GITHUB_TOKEN` (файл `600`, в репозиторий не попадает) | каждый сам, fine-grained, только этот репозиторий, срок ≤ 90 дней |

При утечке токена: отозвать в GitHub → выпустить новый → заменить в `.env`. Если токен попал
в коммит — сообщить владельцу немедленно: репозиторий публичный, история переписывается и
токен всё равно придётся отозвать.

## Частые ошибки

| Симптом | Причина и что делать |
|---|---|
| `нечего публиковать` | правка не сохранена в профиле или профиль указан неверно (`-p`) |
| `линт не прошёл` | смотреть `ERROR:` в выводе; клон откатан, исходник цел в профиле — исправьте скилл и повторите |
| `remote origin не настроен` | `git -C <клон> remote add origin git@github.com:mArTi3-github/hermes-certification-assistant.git` |
| PR не создался, напечатана ссылка | нет `GITHUB_TOKEN` — это штатный режим, открыть PR в браузере |
| Скилл не появился у коллег | они не сделали `sync.sh`; правка есть в `main`, но не в их профиле |
| Скилл не попал в репозиторий | его категория не публикуется: перенесите в `skills/certification/` (или `certification/tools/`) либо добавьте строку в `[publish]` через `contribute.sh -i <путь>` |
| Скилл пропал после синхронизации | он не был опубликован в `main`; восстановить из `.backup/pre-sync-*` и провести через PR |
