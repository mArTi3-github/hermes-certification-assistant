# hermes-certification-assistant

Дистрибутив профиля Hermes Agent для подготовки сертификационной тестовой
документации ФСТЭК России (приказ № 76) на веб-СЗИ: прогон проверок функций
безопасности, сбор свидетельств, отчёт `.docx` со скриншотами и сводка `.md`.

Репозиторий — **источник истины** и канал доставки: скиллы, персона и конфиг
приезжают к каждому участнику команды через `hermes profile install/update`, а
изменения принимаются через pull request. Личные данные (память, сессии, ключи)
остаются у каждого свои и в репозиторий не попадают.

## Установка (новый участник)

```bash
# 1. Поставить профиль из репозитория (публичный — креды не нужны)
hermes profile install github.com/mArTi3-github/hermes-certification-assistant --alias

# 2. Заполнить ключ модели
cp ~/.hermes/profiles/hermes-certification-assistant/.env.EXAMPLE \
   ~/.hermes/profiles/hermes-certification-assistant/.env
# вписать в .env: DEEPSEEK_API_KEY=...

# 3. Запуск
hermes -p hermes-certification-assistant chat
# или, если создан alias:
hermes-certification-assistant chat
```

Требуется `git` и Hermes `>=0.12.0`.

## Как участвовать в модернизации

Короткая версия: правишь скилл в своём профиле → публикуешь ветку → владелец
мержит PR → остальные подтягивают обновление.

```bash
# 1. Агент поправил скилл в профиле. Проверить, что всё валидно:
python3 <клон>/tools/skill_lint.py

# 2. Опубликовать: копирует правки в клон, коммитит в ветку, пушит и открывает PR
<клон>/tools/contribute.sh -m "stand-ftest: уточнил проверку блокировок"

# 3. Принять обновления из main к себе в профиль
<клон>/tools/sync.sh
```

Полный регламент — в скилле
[`skills/software-development/profile-contribution`](skills/software-development/profile-contribution/SKILL.md):
роли, железные правила, чек-лист ревью, разбор частых ошибок.

### Правила коротко

- `main` защищён: прямой push запрещён, нужен PR и approve владельца; мержит владелец.
- Один PR — одно смысловое изменение; строка в `CHANGELOG.md` добавляется автоматически.
- Секреты (`.env`, `auth.json`, токены, пароли) в репозиторий не попадают — проверяет CI.
- Адреса стендов в скиллах не фиксируются: только плейсхолдеры (`<узел>`, `<стенд>`).
- Незакоммиченная правка исчезнет при следующей синхронизации — правки публикуются, а не копятся.

### Какие скиллы публикуются

Правило по умолчанию — **категория скилла**, исключения — явным списком (`publish.list`):

```text
[defaults]
publish_categories: certification   # вся категория уезжает в репозиторий сама

[publish]                           # публикуется, хотя категория не в списке по умолчанию
software-development/profile-contribution
productivity/docx
...

[private]                           # не публикуется никогда (сейчас пусто)
```

Приоритет правил:

1. `[private]` — скилл не публикуется ни при каких условиях.
2. `[publish]` — публикуется, даже если его категория не в списке по умолчанию (общие
   инструменты: CodeQL, SAST, `docx`, регламент).
3. `[defaults] publish_categories` — все скиллы категории публикуются по умолчанию:
   новый `skills/certification/*` уходит в репозиторий без единой команды.
4. Всё остальное — **локально**: в GitHub не попадает и коллегам не приезжает.

Раскладка каталогов и есть основное правило:

```text
skills/certification/                 процедуры сертификации — публикуются
skills/certification/tools/           служебные скиллы команды — тоже публикуются
skills/<любая другая категория>/      локально, если не указано явно в [publish]
```

Имена внутри `certification/` свободные: префикс `certification-` сложился исторически, но правилом
не является и линтом не проверяется. Единственное требование — `name` во фронтматтере совпадает
с именем каталога.

Что делает механизм в нужный момент:

- **при создании скилла** агент спрашивает категорию (правило №10 в скилле
  `profile-contribution`) — выбор категории и есть выбор «публикуется / локально»;
- **`contribute.sh`** находит скиллы вне политики и, если запущен в терминале, спрашивает по
  каждому: `[c]` — перенести в `certification/` и опубликовать, `[l]` — оставить локально,
  `[Enter]` — пропустить; в неинтерактивном режиме печатает подсказку с командой;
- **`publish_policy.py --status --profile <каталог>`** показывает текущую картину, включая
  неклассифицированные скиллы;
- **`sync.sh --prune`** убирает из профиля скиллы, которые политика перестала публиковать
  (иначе после переноса категории в профиле остались бы дубли по старым путям).

Технические подробности:

- штатные скиллы Hermes не перечисляются — они приезжают сами;
- CI падает, если в репозитории лежит скилл вне политики или нарушено правило имён;
- убрать скилл из публикации: строку из `[publish]` → в `[private]`, каталог из репозитория
  (`git rm -r skills/<путь>`), затем `sync.sh --prune` у себя.

### Версии и релизы

Версия живёт в `distribution.yaml`, описание — в `CHANGELOG.md`, метка — в теге `v<версия>`
и в GitHub Release. Все три шага делает одна команда:

```bash
python3 tools/release.py 1.7.0 --dry-run   # план: что попадёт в релиз
python3 tools/release.py 1.7.0             # Unreleased → раздел с версией, коммит, тег, Release
```

Правило: версию поднимает только владелец, и только этой командой — иначе получается история,
в которой версии есть, а меток нет. Теги неизменяемы: ошибочный релиз исправляется следующей
версией, а не переносом тега.

### Учётные данные

| Что | Зачем | Где живёт |
|---|---|---|
| SSH-ключ | push ветки (и clone/update, если репозиторий станет приватным) | `~/.ssh/`, публичная часть — в GitHub-профиле |
| PAT (`GITHUB_TOKEN`) | необязательно: чтобы `contribute.sh` сам открывал PR | `~/.hermes/.env`, файл `600`, fine-grained, только этот репозиторий, срок ≤ 90 дней |

Без PAT публикация тоже работает: скрипт печатает ссылку `compare` — PR открывается
одной кнопкой в браузере.

## Что внутри

| Путь | Назначение |
|---|---|
| `SOUL.md` | персона агента: прямой ответ, отчёт о сделанном, без пересказа процесса |
| `config.yaml` | полный конфиг профиля: `deepseek-flash` по умолчанию, лимиты контекста, тулсеты, делегирование |
| `skills/` | авторские скиллы, которые несут специфику работы (см. ниже) |
| `distribution.yaml` | манифест дистрибутива: версия, требования к окружению, distribution-owned пути |
| `publish.list` | **политика публикации**: какие скиллы уходят в репозиторий, а какие остаются локальными |
| `tools/` | `contribute.sh`, `sync.sh`, `skill_lint.py`, `publish_policy.py`, `release.py` — публикация, приём обновлений, линт, политика |
| `.github/` | `CODEOWNERS` (ревью у владельца) и CI `validate` |
| `CHANGELOG.md` | журнал изменений: строка на PR, раздел на релиз |

### Скиллы в репозитории

| Скилл | Зачем |
|---|---|
| `certification/stand-ftest` | методика тестовой документации по приказу № 76: разделы, функции безопасности, структура отчёта, сбор свидетельств |
| `certification/dist-fuzz-report-check` | проверка материалов фаззинг-тестирования по Методике ВУ: отчёт и разбор артефактов AFL |
| `certification/attack-surface-analysis` | анализ поверхности атаки из исходников: модель нарушителя, классификация находок, требования к доказательности |
| `software-development/profile-contribution` | регламент совместной модернизации профиля: PR, ревью, синхронизация |
| `autonomous-ai-agents/hermes-agent-notes` | дополнение к штатному `hermes-agent`: гигиена длинных сессий (сжатие контекста, замер размера, артефакты на диске), подключение Desktop к удалённому бэкенду, раздача профиля команде |
| `productivity/docx` | работа с `.docx`; **отличается от стокового** — добавлен `scripts/docx_read_ordered.py` (чтение в порядке документа) |

Остальные штатные скиллы Hermes в репозиторий намеренно не вложены: они приезжают в
профиль сами при первом запуске (`sync_skills` вызывается на старте CLI/TUI/гейтвея) и
остаются в актуальной для версии Hermes редакции.

### Про изменённый штатный скилл `docx`

`docx` отличается от той редакции, что лежит в общем каталоге скиллов хоста. В текущей сборке
Hermes его в bundled-наборе уже нет, поэтому обновлений, которые можно потерять, не существует:
скилл живёт как локальный и публикуется вместе с профилем.

С остальными штатными скиллами правило другое: **их не правим**. Любая правка каталога отвязывает
скилл от апстрима (`~ <имя> (user-modified, skipping)`), и обновления Hermes перестают приезжать.
Собственные дополнения живут в отдельном скилле `hermes-agent-notes`, который дополняет штатный
`hermes-agent` (он публикуется: гигиена длинных сессий и раздача профиля нужны всей команде). Проверить расхождения:

```bash
hermes skills list-modified
hermes skills diff <имя>
hermes skills reset <имя> --restore    # вернуть стоковую редакцию
```

## Модель и секреты

- Модель по умолчанию: `deepseek-flash`, провайдер `deepseek`.
- Ключ живёт только в `.env` профиля; в репозитории его нет и быть не должно.
- Секция `dashboard.basic_auth` из `config.yaml` удалена при публикации: хеш пароля
  веб-панели и ключ подписи сессий каждому свои, задаются локально.

## Что не попадает в репозиторий

`memories/`, `sessions/`, `state.db*`, `logs/`, `.env`, `auth.json`, `vault/`, `cron/`,
кеши, `.backup/` — см. `.gitignore`. Это пользовательские данные, состояние и локальные
резервные копии, а не часть дистрибутива.

## Обновление у получателя

```bash
# нативный путь для профилей, установленных из репозитория
hermes profile update hermes-certification-assistant

# либо скриптом из клона: скиллы + SOUL.md, с бэкапом в .backup/
<клон>/tools/sync.sh
```

Обновляются `SOUL.md`, `config.yaml` и скиллы из репозитория. Память, сессии, ключи и
локально добавленные скиллы не трогаются; `config.yaml` по умолчанию тоже сохраняется
(перезаписать — `sync.sh --config` или `--force-config`).

## Выпуск новой версии (владелец)

1. Смержить накопленные PR (squash), перенести строки из `## Unreleased` в раздел версии.
2. Поднять `version:` в `distribution.yaml`.
3. Закоммитить, поставить тег, запушить:

```bash
git commit -am "v1.2.0: <что изменилось>"
git tag v1.2.0
git push origin main --tags
```
