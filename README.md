# hermes-certification-assistant

Дистрибутив профиля Hermes Agent для подготовки сертификационной тестовой
документации ФСТЭК России (приказ № 76) на веб-СЗИ: прогон проверок функций
безопасности, сбор свидетельств, отчёт `.docx` со скриншотами и сводка `.md`.

Репозиторий — **источник истины** и канал доставки: скиллы, персона и конфиг
приезжают к каждому участнику команды через `hermes profile install/update`, а
изменения принимаются через pull request. Личные данные (память, сессии, ключи)
остаются у каждого свои и в репозиторий не попадают.

таблица ниже: сколько их, в тексте не пишется — набор меняется, и любое число в прозе
стареет молча и переживает не одну правку. Всё остальное — штатный набор

## Установка (новый участник)

```bash
# 1. Поставить профиль из репозитория (публичный — креды не нужны)
hermes profile install github.com/mArTi3-github/hermes-certification-assistant --alias

# 2. Заполнить ключ модели
cp ~/.hermes/profiles/hermes-certification-assistant/.env.EXAMPLE \
   ~/.hermes/profiles/hermes-certification-assistant/.env
# вписать в .env: DEEPSEEK_API_KEY=...

# 3. Запуск
hermes -p hermes-certification-assistant chat
# или, если создан alias:
hermes-certification-assistant chat
```

Требуется `git` и Hermes `>=0.12.0`.

## Как участвовать в модернизации

Короткая версия: правишь скилл в своём профиле → публикуешь ветку → владелец
мержит PR → остальные подтягивают обновление.

**Всё это делается разговором с агентом — команды вводить не нужно.**

| Скажи агенту | Что произойдёт |
|---|---|
| «опубликуй правки» | агент соберёт изменения, прогонит линт, создаст ветку, запушит и откроет PR |
| «что не синхронизировано» | агент сверит профиль с репозиторием (`publish_check.py`) и перечислит, что ещё не опубликовано |
| «что нового в репозитории» / «обнови профиль» | агент подтянет обновления (`hermes profile update` или `sync.sh`) и покажет, что изменилось |
| «проверь мой PR» | агент покажет статус CI и нужен ли ещё ревью |
| «выпускай релиз» / «выпусти версию 1.10.0» | агент выберет номер, если он не назван, поднимет версию, поставит тег и опубликует релиз |

Команды ниже — для прозрачности и ручной отладки; агент выполняет их сам:

```bash
# 0. Что в профиле ещё не опубликовано (и не разошлось ли чего): код 0 — синхронно
python3 <клон>/tools/publish_check.py

# 0.5. Чьё это: агент или фоновая ревизия — списки по авторам и готовая строка коммита
python3 <клон>/tools/attribution.py

# 1. Агент поправил скилл в профиле. Проверить, что всё валидно:
python3 <клон>/tools/skill_lint.py

# 2. Опубликовать: копирует правки в клон, коммитит в ветку (раскладывая коммит по авторам),
#    пушит и открывает PR
<клон>/tools/contribute.sh -m "stand-ftest: уточнил проверку блокировок"

# 3. Принять обновления из main к себе в профиль
<клон>/tools/sync.sh
```

Полный регламент — в скилле
[`skills/software-development/profile-contribution`](skills/software-development/profile-contribution/SKILL.md):
роли, железные правила, чек-лист ревью, разбор частых ошибок.

### Правила коротко

- `main` защищён: прямой push запрещён, нужен PR и approve владельца; мержит владелец.
- Один PR — одно смысловое изменение; строку в `CHANGELOG.md` `contribute.sh` добавляет сам,
  при PR без правки скиллов — вручную, сразу под `## Unreleased`.
- README правится в том же PR: таблица «Скиллы профиля», команды и флаги инструментов — часть
  публикации, а не задача «потом» (правило 13 в регламенте, чек-лист ревью).
- Секреты (`.env`, `auth.json`, токены, пароли) в репозиторий не попадают — проверяет CI.
- Адреса стендов в скиллах не фиксируются: только плейсхолдеры (`<узел>`, `<стенд>`).
- Незакоммиченная правка исчезнет при следующей синхронизации — правки публикуются, а не копятся.
- Профиль мог измениться после создания PR: скиллы правит не только агент, но и фоновая ревизия
  сессии. Публикуется весь накопленный дельта за один цикл — `contribute.sh` раскладывает коммит
  по авторам (`tools/attribution.py`), поэтому «моё» и «заметки куратора» не смешиваются.
  `sync.sh` с кодом 3 означает «есть что публиковать», а не ошибку; второго PR под кураторские
  заметки не заводят, тег не переставляют.

### Какие скиллы публикуются

Правило по умолчанию — **категория скилла**, исключения — явным списком (`publish.list`):

```text
[defaults]
publish_categories: certification   # вся категория уезжает в репозиторий сама

[publish]                           # публикуется, хотя категория не в списке по умолчанию
software-development/profile-contribution
productivity/docx
...

[private]                           # не публикуется никогда (сейчас пусто)
```

Приоритет правил:

1. `[private]` — скилл не публикуется ни при каких условиях.
2. `[publish]` — публикуется, даже если его категория не в списке по умолчанию (общие для
   команды скиллы: `docx`, `hermes-agent-notes`, `profile-contribution`).
3. `[defaults] publish_categories` — все скиллы категории публикуются по умолчанию:
   новый `skills/certification/*` уходит в репозиторий без единой команды.
4. Всё остальное — **локально**: в GitHub не попадает и коллегам не приезжает.

Раскладка каталогов и есть основное правило:

```text
skills/certification/                 процедуры сертификации — публикуются
skills/certification/tools/           служебные скиллы команды — тоже публикуются
skills/<любая другая категория>/      локально, если не указано явно в [publish]
```

Имена внутри `certification/` свободные: префикс `certification-` сложился исторически, но правилом
не является и линтом не проверяется. Единственное требование — `name` во фронтматтере совпадает
с именем каталога.

Что делает механизм в нужный момент:

- **при создании скилла** агент спрашивает категорию (правило №10 в скилле
  `profile-contribution`) — выбор категории и есть выбор «публикуется / локально»;
- **`contribute.sh`** находит скиллы вне политики и, если запущен в терминале, спрашивает по
  каждому: `[c]` — перенести в `certification/` и опубликовать, `[t]` — в `certification/tools/`,
  `[l]` — оставить локально,
  `[Enter]` — пропустить; в неинтерактивном режиме печатает подсказку с командой;
- **`publish_policy.py --status --profile <каталог>`** показывает текущую картину, включая
  неклассифицированные скиллы;
- **`sync.sh --prune`** убирает из профиля скиллы, которые политика перестала публиковать
  (иначе после переноса категории в профиле остались бы дубли по старым путям).

Технические подробности:

- штатные скиллы Hermes не перечисляются — они приезжают сами;
- CI падает, если в репозитории лежит скилл вне политики или нарушено правило имён;
- убрать скилл из публикации: строку из `[publish]` → в `[private]`, каталог из репозитория
  (`git rm -r skills/<путь>`), затем `sync.sh --prune` у себя.

### Версии и релизы

Версия живёт в `distribution.yaml`, описание — в `CHANGELOG.md`, метка — в теге `v<версия>`
и в GitHub Release. Все три шага делает одна команда:

```bash
python3 tools/release.py 1.10.0 --dry-run   # план: что попадёт в релиз
python3 tools/release.py 1.10.0             # Unreleased → раздел с версией, коммит, тег, Release
```

Правило: номер версии выбирает и выпускает агент — по решению владельца, в любой момент, в том
числе сразу после мержа; ждать «подходящего случая» не нужно. PR, который меняет в
`distribution.yaml` строку `version:`, CI отклоняет («Версию в PR не меняют»); остальные поля
манифеста — `distribution_owned`, `hermes_requires`, `env_requires` — правятся в PR как обычные
факты дистрибутива. `release.py` не даст поставить версию ниже текущей, работать в грязном дереве
и переиспользовать существующий тег, а `main` и тег уходят одним push — поэтому «версия без
метки» не появляется. Теги неизменяемы: ошибочный релиз исправляется следующей версией,
а не переносом тега.

### Учётные данные

| Что | Зачем | Где живёт |
|---|---|---|
| SSH-ключ | необязательно: push по SSH, если не хочется хранить PAT в `.env`; PR тогда открывается вручную по ссылке `compare` | `~/.ssh/`, публичная часть — в GitHub-профиле |
| PAT (`GITHUB_TOKEN`) | необязательно: чтобы `contribute.sh` сам открывал PR | `~/.hermes/.env`, файл `600`, срок ≤ 90 дней: владельцу — fine-grained на этот репозиторий, **коллаборатору — classic со scope `repo`** (fine-grained чужой репозиторий в списке не покажет) |

Без PAT публикация тоже работает: скрипт печатает ссылку `compare` — PR открывается
одной кнопкой в браузере.

### Скиллы в репозитории

Что делает каждый скилл и когда он применяется — в таблице [Скиллы профиля](#скиллы-профиля)
в начале README. Здесь — только правило про остальной набор.

Остальные штатные скиллы Hermes в репозиторий намеренно не вложены: они приезжают в
профиль сами при первом запуске (`sync_skills` вызывается на старте CLI/TUI/гейтвея) и
остаются в актуальной для версии Hermes редакции.

### Про изменённый штатный скилл `docx`

`docx` отличается от той редакции, что лежит в общем каталоге скиллов хоста. В текущей сборке
Hermes его в bundled-наборе уже нет, поэтому обновлений, которые можно потерять, не существует:
скилл живёт как локальный и публикуется вместе с профилем.

С остальными штатными скиллами правило другое: **их не правим**. Любая правка каталога отвязывает
скилл от апстрима (`~ <имя> (user-modified, skipping)`), и обновления Hermes перестают приезжать.
Собственные дополнения живут в отдельном скилле `hermes-agent-notes`, который дополняет штатный
`hermes-agent` (он публикуется: гигиена длинных сессий и раздача профиля нужны всей команде). Проверить расхождения:

```bash
hermes skills list-modified
hermes skills diff <имя>
hermes skills reset <имя> --restore    # вернуть стоковую редакцию
```

## Модель и секреты

- Модель по умолчанию: `deepseek-flash`, провайдер `deepseek`.
- Ключ живёт только в `.env` профиля; в репозитории его нет и быть не должно.
- Секция `dashboard.basic_auth` из `config.yaml` удалена при публикации: хеш пароля
  веб-панели и ключ подписи сессий каждому свои, задаются локально.

## Что не попадает в репозиторий

`memories/`, `sessions/`, `state.db*`, `logs/`, `.env`, `auth.json`, `vault/`, `cron/`,
кеши, `.backup/` — см. `.gitignore`. Это пользовательские данные, состояние и локальные
резервные копии, а не часть дистрибутива.

## Обновление у получателя

```bash
# нативный путь для профилей, установленных из репозитория
hermes profile update hermes-certification-assistant

# либо скриптом из клона: скиллы, SOUL.md, README.md и манифест distribution.yaml, с бэкапом в .backup/
<клон>/tools/sync.sh

# проверить, что обновление ничего не перезапишет (код 0 — чисто, 3 — есть неопубликованное)
<клон>/tools/sync.sh --check
```

`sync.sh` и `hermes profile update` обновляют одно и то же — `SOUL.md`, `README.md`, скиллы
дистрибутива и `distribution.yaml` (поэтому версия профиля больше не отстаёт от репозитория,
а README в профиле не расходится с репозиторным; старые копии уходят в `.backup/pre-sync-*`).
Память, сессии, ключи и локально добавленные скиллы не трогаются; `config.yaml` в обоих
случаях сохраняется — перезаписать его можно только явно:
`sync.sh --config` или `hermes profile update --force-config`.

**Если в профиле есть правки, которые ещё не уехали в репозиторий, обновление их затрёт.**
`sync.sh` проверяет это сам (вызывает `publish_check.py`) и при неопубликованных правках
останавливается с кодом 3, ничего не копируя; перезапись — только явным `--force`, при этом копия
профиля уходит в `.backup/pre-sync-*`.

Направление расхождения определяется меткой синхронизации — файлом `.sync-state.json` в каталоге
профиля (в `skills/` не попадает, поэтому и в публикацию тоже). После каждого успешного обновления
`sync.sh` записывает туда коммит, версию и отпечатки содержимого всех публикуемых скиллов; отпечаток
каталога — sha256 по отсортированным «путь + sha256 файла», без mtime и мусора. Дальше решение
трёхстороннее: профиль совпал с репозиторием — `=`; профиль совпал с меткой, а репозиторий ушёл
вперёд — `↓` (обновляем, терять нечего); профиль отличается и от метки, и от репозитория — `≠`
(правка в профиле, стоп). Смерженный PR коллеги приходит как `↓` и **не требует `--force`**, а
правка, сделанная в профиле после синхронизации, по-прежнему останавливает обновление.

Почему не по времени файлов: `cp -a` и `rsync` mtime сохраняют, правка через инструменты ставит
«сейчас», `hermes profile update` заменяет каталог целиком, часы на ВМ коллег расходятся. После
любой синхронизации все файлы профиля выглядят новее любого коммита — то есть «что новее, то и
правка» даёт всегда один и тот же неверный ответ. Время используется только в пояснениях отчёта
(«правка новее метки синхронизации»), а решение принимается по отпечаткам содержимого.

Метки нет (профиль старше этого инструмента) — направление неизвестно, и решение консервативное:
расхождение считается непубликованной правкой. Метка заводится первым же запуском `sync.sh`;
если в профиле на этот момент есть правки — опубликуйте их, затем один раз `sync.sh --force`.

У `hermes profile update` такого гейта нет и бэкапа тоже:
перед ним сохраняйте копию — `python3 <клон>/tools/publish_check.py --save .backup/pre-update-<дата>`
— или сначала публикуйте правки. Порядок в любом случае один: опубликовать/сохранить → обновить.

Гейт проверяется матрицей состояний — `tools/test_gate_matrix.sh` (реальный прогон на копиях клона
и профиля: восемь сценариев от «профиль отстал» до «правка с откатом») плюс `tools/test_sync_state.py`
(юнит-тесты классификации и отпечатков). Обе команды без сети и без живого профиля.

## Выпуск новой версии (владелец)

1. Смержить накопленные PR (squash) — строки `## Unreleased` копятся в `CHANGELOG.md` сами.
2. Выпустить версию одной командой:

```bash
python3 tools/release.py 1.10.0 --dry-run   # план: что попадёт в релиз
python3 tools/release.py 1.10.0             # раздел версии в CHANGELOG, version в distribution.yaml, коммит, тег v1.10.0, GitHub Release
```

Вручную `version:` в `distribution.yaml` не правится: PR, меняющий эту строку, CI отклоняет, а
`release.py` не даст поставить версию ниже текущей. Тег, поставленный релизом, не переносится —
ошибочный релиз исправляется следующей версией.
